# 1. 70. Climbing Stairs (LC 70) — Easy
🔗 [Open on LeetCode](https://leetcode.com/problems/climbing-stairs/)

**Pattern:** 1D DP — **the ROOT of the whole pattern.** `dp[i]` depends on a **fixed window of previous states** (`i-1`, `i-2`), so the table collapses to **two rolling variables**. Every other linear-DP here (`746`, `198`, `91`, `1137`) is this recurrence with the combine operator or the window size changed.
**Trigger:** "**in how many distinct ways**" + "**each move is 1 or 2 steps**" + a **single scalar `n`** as input. The tells: (a) the answer is a **count of orderings** (`1+2 ≠ 2+1`, so it's compositions, not combinations — a pure combinatorics formula won't do), (b) the choice set at every position is **identical and tiny**, and (c) the last move is either a 1-step or a 2-step ⇒ **partition by the final decision** and the recurrence writes itself. Whenever "the answer for `n` decomposes into the answers for `n-1` and `n-2`", you're here.

## Problem (1-liner)
Climb a staircase of `n` steps taking **1 or 2 steps** at a time; count the **distinct ordered ways** to reach the top.
**Examples:** `n=2 → 2` (`1+1`, `2`) · `n=3 → 3` (`1+1+1`, `1+2`, `2+1`) · `n=4 → 5` · `n=5 → 8`.
**Constraints:** `1 ≤ n ≤ 45`. **Edges:** `n == 1 → 1` (only one way) · conceptually `n == 0 → 1` (**the empty way** — this is the base case that makes the recurrence work, not a special case to bolt on). **Overflow:** the answer is `Fib(n+1)`, so `n = 45` → `1836311903 < 2³¹−1` — `int` fits with ~15% headroom; `n = 46` would overflow, which is exactly why the constraint stops at 45.

## Idea (1-liner)
`ways(i) = ways(i-1) + ways(i-2)` — it's **Fibonacci shifted by one**, computable with two variables.

## Approach
1. Base: `ways(0) = 1`, `ways(1) = 1`.
2. For `i = 2..n`: `ways(i) = ways(i-1) + ways(i-2)`.
3. Return `ways(n)`. Keep only the last two values ⇒ O(1) space.

> **Load-bearing insight #1 — partition by the LAST move.** To stand on step `i` you arrived either from `i-1` (a 1-step) or from `i-2` (a 2-step). Those two sets of paths are **disjoint** (they differ in the final move) and **exhaustive** (there is no third option) ⇒ you may simply **add** them. That "disjoint + exhaustive ⇒ sum" argument is the entire technique behind counting DP; say it out loud before writing a line.

> **Load-bearing insight #2 — `ways(0) = 1`, not 0.** There is exactly **one** way to climb zero steps: do nothing. Setting it to 0 collapses the whole chain (`n=2` → 1 instead of 2). The reason it feels wrong is that it's the *empty product* of choices, not "no ways".

> **Load-bearing insight #3 — it's Fibonacci, and naming it wins the interview.** `ways(n) = Fib(n+1)` with `Fib(1)=Fib(2)=1`. Saying this immediately explains *why* two variables suffice, and it's the hook for the O(log n) follow-up. It also warns you about overflow: Fibonacci blows past `int` at index 47.

> **Load-bearing insight #4 — the window size is the space bound.** `dp[i]` reads only `i-1` and `i-2`, so the `O(n)` table is pure waste — a **fixed-width dependency window collapses to that many scalars**. This is the single most reusable idea in 1D DP: check the window before allocating a table.

## Code (clean canonical)
```cpp
class Solution {
public:
    int climbStairs(int n) {
        int prev2 = 1, prev1 = 1;          // ways(0) = ways(1) = 1

        for (int i = 2; i <= n; i++) {
            int cur = prev1 + prev2;
            prev2 = prev1;
            prev1 = cur;
        }
        return prev1;
    }
};
```
**TC:** **O(n)** — one pass.  **SC:** **O(1)** — two ints, no table, no stack.
*`n == 1` needs no special case: the loop never runs and `prev1 == 1` falls out.*

## My Solution (top-down memoized)
```cpp
class Solution {
    int helper(int index, int n, vector<int>& mem) {
        if (index == n) return 1;          // reached the top: one complete way
        if (index > n) return 0;           // overshot: dead branch

        if (mem[index] != -1) return mem[index];
        int result = 0;
        result += helper(index + 1, n, mem);
        result += helper(index + 2, n, mem);
        mem[index] = result;
        return result;
    }
public:
    int climbStairs(int n) {
        vector<int> mem(n + 1, -1);
        return helper(0, n, mem);
    }
};
```
✅ **Correct — O(n) time, O(n) memo + O(n) stack.** The forward formulation (count paths *from* `index` *to* `n`) is a perfectly good alternative to the backward `dp[i]` one, and the `index > n` guard correctly kills the overshoot branch.
**The one subtlety worth knowing rather than getting lucky on:** `mem` has size `n+1` (indices `0..n`) but `helper(index + 2)` can reach `index == n+1`. It's in-bounds **only because both base cases return before the `mem[index]` line** — `index == n` and `index > n` both exit first, so the memo is only ever touched for `index < n`. That ordering is load-bearing; reordering the guards below the memo lookup is an out-of-bounds read.
**Refinements:** `mem[n]` is allocated but never written (the `index == n` base returns first) — harmless. The real upgrade is the **two-variable bottom-up** above: same O(n) time, drops both the memo and the 45-deep call stack.

## Other Approaches
- **Naive recursion.** `f(i) = f(i+1) + f(i+2)`, no memo. **O(2ⁿ) / O(n)** stack. Always state it first, then kill it by naming the cause: the same subtree is recomputed exponentially often (`f(n-2)` is reached from both branches). At `n = 45` that's ~10⁹ calls.
- **Top-down memoization** — **O(n) / O(n)**. Your version; the mechanical translation of the recurrence, and the right thing to write when the recurrence is complicated enough that the bottom-up order isn't obvious.
- **Bottom-up table** `dp[i] = dp[i-1] + dp[i-2]` — **O(n) / O(n)**. Removes the stack; the natural intermediate step.
- **Two rolling variables** *(canonical)* — **O(n) / O(1)**. The expected final answer.
- **Matrix exponentiation / fast doubling.** `[[1,1],[1,0]]ⁿ` by binary power. **O(log n) / O(1)**. Irrelevant at `n ≤ 45`, but it's the honest answer to *"what if `n` were 10¹⁸ (mod p)?"* and it shows range.
- **Binet's formula** (`φⁿ/√5`, rounded). **O(1)** in theory — mention it, then reject it: `double` loses exactness around `n ≈ 71`, so it's a trap answer, not a solution.
- **Follow-ups to pre-empt:** *"1, 2, or 3 steps"* → **LC 1137**, three rolling vars, base `1,1,2`. *"minimise cost instead of counting"* → **LC 746**, same recurrence with `min` and a `+cost[i]`. *"some steps are broken"* → set `dp[i] = 0` at those indices; the recurrence is unchanged. *"k step sizes"* → sliding-window sum over the last `k`, O(nk) or O(n) with a running sum. *"return the ways themselves"* → no longer DP-countable in O(n) — the output is exponential.

> **The counting-DP family to distinguish out loud:** *count paths, sum the branches* → **70**, **91 Decode Ways**, **62 Unique Paths**. *optimise, take min/max of the branches* → **746**, **198 House Robber**, **322 Coin Change**. **Same skeleton, different combine operator** — `+` counts, `min`/`max` optimises. 70 vs 198 is the sharpest pair: identical two-back window, but 198 also **skips** a state (`dp[i] = max(dp[i-1], dp[i-2] + nums[i])`) because adjacency is forbidden rather than free.

## Pitfalls
- **`ways(0) = 0`** — *the* signature bug. The empty climb is one valid way; zeroing it breaks every later value (`n=2` → 1).
- **Off-by-one on which Fibonacci it is** — `ways(n) = Fib(n+1)`, not `Fib(n)`. Anchor on `ways(2) = 2` rather than memorising the shift.
- **Reordering the base cases below the memo lookup** (top-down) — `mem[index]` is only in-bounds because `index == n` and `index > n` return first. Moving the lookup up is an OOB read at `index = n+1`.
- **Sizing the memo `n` instead of `n+1`** — same OOB, one step earlier.
- **Forgetting to write the memo before returning** — silently degrades back to O(2ⁿ); the recursion still returns the right answer, so it only shows up as a TLE.
- **Assuming order doesn't matter** — `1+2` and `2+1` are **distinct**, so this is compositions, not partitions. A `C(n,k)`-style combinatorics answer undercounts.
- **Reaching for `long long` reflexively** — unnecessary at `n ≤ 45` (`Fib(46) < 2³¹`), but state the bound out loud; if the constraint were `n ≤ 90` you'd genuinely need it, and past that only modular arithmetic.
- **Updating the rolling variables in the wrong order** — `prev2 = prev1; prev1 = cur;` must use a temporary `cur`; assigning `prev1` first destroys the value `prev2` needs.
- **Keeping the full `dp[]` table out of habit** — check the dependency window before allocating; a two-back window never needs more than two scalars.
- **Solving it with recursion in an interview and stopping there** — memoized recursion is correct but it is the *middle* of the ladder. Walk to O(1) space; that's what's being tested.
