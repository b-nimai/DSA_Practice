# 2. 746. Min Cost Climbing Stairs (LC 746) — Easy
🔗 [Open on LeetCode](https://leetcode.com/problems/min-cost-climbing-stairs/)

**Pattern:** 1D DP — **[[1-70-climbing-stairs|70 Climbing Stairs]] with the combine operator swapped.** Identical two-back dependency window (`i-1`, `i-2`), so the table again collapses to **two rolling variables**; the only changes are **`+` → `min`** (optimise instead of count) and **a per-step weight `cost[i]`** riding along. If you can write 70, you can write this in one edit.
**Trigger:** "**minimum cost**" + "**climb one or two steps**" + "**you may start at index 0 or index 1**" + "reach the **top of the floor**". The tells: (a) the objective is an **optimum, not a count** ⇒ combine with `min`, (b) the choice set at every position is **identical and tiny** (1-step or 2-step), so one recurrence covers everything, and (c) **the "top" is past the last element** — the phrase "top of the *floor*", not "last step", is the whole off-by-one warning. Whenever "the best answer at `i` is a `min` over a **fixed window** of earlier answers plus a local weight", you're here.

## Problem (1-liner)
Each `cost[i]` is the toll for **stepping onto** step `i`; once paid you move **1 or 2** steps. Start at index `0` **or** `1` (free), and return the **minimum total cost to reach index `n`** — the floor **one past the last step**.
**Examples:** `[10,15,20] → 15` (start at 1, pay 15, jump two → top) · `[1,100,1,1,1,100,1,1,100,1] → 6` (hop the 1s at `0,2,4,6,7,9`).
**Constraints:** `2 ≤ n ≤ 1000`, `0 ≤ cost[i] ≤ 999`. **Edges:** `n == 2 → min(cost[0], cost[1])` (pay one, two-step straight to the top). **Overflow:** worst case `1000 × 999 < 10⁶` — `int` is fine with four orders of magnitude to spare, and it's a **min** so it only shrinks.

## Idea (1-liner)
`dp[i] = min(dp[i-1] + cost[i-1], dp[i-2] + cost[i-2])` — Fibonacci's shape with **`min` instead of `+`**, answer at `dp[n]`.

## Approach
1. Define `dp[i]` = **min cost to *reach* step `i`** (having **not yet paid** `cost[i]`).
2. Base: `dp[0] = dp[1] = 0` — both entry points are free.
3. For `i = 2..n`: you arrived from `i-1` (paying `cost[i-1]`) or from `i-2` (paying `cost[i-2]`) ⇒ take the `min`.
4. Return `dp[n]`. The window is 2 ⇒ keep two scalars.

> **Load-bearing insight #1 — partition by the LAST move, but combine with `min`.** Same disjoint-and-exhaustive argument as 70: you reached `i` from exactly one of `i-1` or `i-2`. Counting sums the two branches; **optimising takes the better one**. That single operator swap is the entire difference between the two problems, and saying it out loud is the fastest correct answer in the interview.

> **Load-bearing insight #2 — the top is index `n`, not `n-1`.** The loop runs to `i <= n` and you return `dp[n]`. Returning `dp[n-1]` is *the* signature bug: on `[10,15,20]` it gives `10` (reach the last step) instead of `15` (reach the top). "Top of the **floor**" means the imaginary step past the array — and that's exactly why `dp[n]` needs no `cost` of its own.

> **Load-bearing insight #3 — "pay to step ON" decides where the cost sits.** Because you're charged on *arrival*, the weight belongs to the state you **leave**, not the one you enter: `dp[i-1] + cost[i-1]`, never `dp[i-1] + cost[i]`. The suffix formulation flips this cleanly (see *My Solution*) — pick one and stay consistent; mixing them is the second most common bug.

> **Load-bearing insight #4 — base is `0`, not `1`.** Mirror of 70's `ways(0) = 1`: the empty answer is the **identity of the combine operator** — `1` for a product/count, **`0` for a sum of costs**. Same reasoning, opposite value; that's the rule to carry to every DP in this pattern.

## Code (clean canonical)
```cpp
class Solution {
public:
    int minCostClimbingStairs(vector<int>& cost) {
        int n = cost.size();
        int prev2 = 0, prev1 = 0;                  // dp[0] = dp[1] = 0: both starts are free

        for (int i = 2; i <= n; i++) {             // note: <= n — the top is one past the array
            int cur = min(prev1 + cost[i - 1],     // came from i-1
                          prev2 + cost[i - 2]);    // came from i-2
            prev2 = prev1;
            prev1 = cur;
        }
        return prev1;                              // dp[n]
    }
};
```
**TC:** **O(n)** — one pass.  **SC:** **O(1)** — two ints, no table, no stack.
*`n == 2` falls out free: one iteration gives `min(cost[1], cost[0])`.*

## My Solution (top-down memoized, suffix formulation)
```cpp
class Solution {
    int helper(int index, vector<int>& cost, vector<int>& mem) {
        if (index >= (int)cost.size()) return 0;   // at or past the top: nothing left to pay
        if (mem[index] != -1) return mem[index];

        return mem[index] = cost[index] + min(helper(index + 1, cost, mem),
                                              helper(index + 2, cost, mem));
    }
public:
    int minCostClimbingStairs(vector<int>& cost) {
        vector<int> mem(cost.size(), -1);
        return min(helper(0, cost, mem), helper(1, cost, mem));
    }
};
```
✅ **Correct — O(n) time, O(n) memo + O(n) stack.** The **backward** formulation: `helper(i)` = min cost to get from `i` to the top **including** paying `cost[i]`. The cost sits on the state you *enter* here, which is the clean mirror of the canonical version — and it's why the two entry points must be combined at the call site with `min(helper(0), helper(1))`.
**The subtlety worth knowing rather than getting lucky on:** sharing one `mem` across both entry calls is safe **only because `helper(i)` doesn't depend on where you started** — it's a pure suffix answer. If the state had carried any start-dependent information (a step budget, a parity), one shared memo would silently return stale values.
**Refinements applied above:** `cost[index]` was duplicated across both branches — factored out. `index >= cost.size()` compared `int` to `size_t` (signed/unsigned warning) — cast added. The caller named it `dp` while the helper named it `mem` — unified. The real upgrade is the **two-variable bottom-up**: same O(n) time, drops both the memo and the recursion stack (harmless at `n ≤ 1000`, a genuine overflow at `n = 10⁵`).

## Other Approaches
- **Naive recursion** — `f(i) = cost[i] + min(f(i+1), f(i+2))`, no memo. **O(2ⁿ) / O(n)** stack. State it, then kill it by naming the cause: `f(i+2)` is reached from both branches, so the same suffix is recomputed exponentially often.
- **Top-down memoization** — **O(n) / O(n)**. Your version; the mechanical translation of the recurrence, and the right first move when the bottom-up order isn't obvious.
- **Bottom-up table** `dp[i] = min(dp[i-1] + cost[i-1], dp[i-2] + cost[i-2])`, size `n+1` — **O(n) / O(n)**. Removes the stack; the natural intermediate rung.
- **Two rolling variables** *(canonical)* — **O(n) / O(1)**. The expected final answer.
- **In-place mutation of `cost`** — `cost[i] += min(cost[i-1], cost[i-2])`, return `min(cost[n-1], cost[n-2])`. **O(n) / O(1)** with no extra vars, but it **destroys the input** — mention it as a trick, don't lead with it (interviewers read input mutation as a smell unless you flag it).
- **Greedy "always take the cheaper next step"** — **wrong**, and worth pre-empting out loud. On `[1,100,1,1,1,100,1,1,100,1]` a locally-cheapest walk gets trapped; the cheap step now can force a `100` later, so no exchange argument exists ⇒ you need the table.
- **Follow-ups to pre-empt:** *"1, 2, or 3 steps"* → window of 3, three rolling vars. *"k step sizes"* → `dp[i] = min` over the last `k` ⇒ O(nk), or O(n log k) with a monotonic deque / multiset. *"count the ways instead"* → swap `min` back to `+` and you're at **70**. *"return the actual path"* → store a `parent[]` of which branch won and walk it back, **O(n)** extra space. *"costs can be negative"* → the recurrence still holds (it's a DAG, no cycles), unlike a greedy or a Dijkstra-style argument.

> **The 70 / 746 / 198 triple to distinguish out loud:** identical two-back window, three different combines. **70** → `dp[i] = dp[i-1] + dp[i-2]`, `+` **counts**. **746** → `dp[i] = min(dp[i-1] + w, dp[i-2] + w)`, `min` **optimises** and **every** branch pays. **198** → `dp[i] = max(dp[i-1], dp[i-2] + nums[i])`, `max` optimises but the branches are **asymmetric** — one takes the weight, one **skips** it, because adjacency is forbidden rather than free. Name the operator and the weight placement and you've named the problem.

## Pitfalls
- **Returning `dp[n-1]` instead of `dp[n]`** — *the* signature bug: `[10,15,20]` → `10` instead of `15`. The top is **one past** the last step; loop to `i <= n`.
- **Attaching the cost to the wrong state** — `dp[i-1] + cost[i]` instead of `dp[i-1] + cost[i-1]`. You pay to **step onto** a step, so the weight belongs to the state you leave. Pick the forward or backward formulation and don't mix them mid-solution.
- **`dp[0] = cost[0]`** — no. Both entry points are **free**; you only pay once you're standing there, and `dp` is "cost to *reach*". Setting it to `cost[0]` double-charges the first step.
- **Base `1` instead of `0`** — the empty answer is the **identity of the combine operator**: `1` when counting (70), `0` when summing costs (here). Same argument, opposite value.
- **Special-casing `n == 2`** — unnecessary; the loop's single iteration already yields `min(cost[0], cost[1])`.
- **Reaching for greedy** — the locally-cheapest step is not provably optimal (example 2 is the counterexample); if you can't write an exchange argument, you need the table.
- **Sizing the bottom-up table `n` instead of `n+1`** — OOB on the final write, or a silent wrong answer if you clamp.
- **`index >= cost.size()` with `int index`** (top-down) — signed/unsigned comparison; harmless here since `index ≥ 0`, but cast it and say why.
- **Forgetting to write the memo before returning** — still correct, still O(2ⁿ); surfaces as a **TLE, not a WA**.
- **Updating the rolling variables without a temporary** — `prev2 = prev1` must come after `cur` is computed; assigning `prev1` first destroys what `prev2` needs.
- **Stopping at the memoized version in an interview** — correct but it's the *middle* of the ladder. Walk it to O(1) space; that's the thing being tested.
