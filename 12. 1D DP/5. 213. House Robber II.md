# 5. 213. House Robber II (LC 213) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/house-robber-ii/)

**Pattern:** 1D DP — **[[4-198-house-robber|198 House Robber]] with the BOUNDARY broken.** The recurrence does not change by one character: `max(skip, take + two-back)` is still the whole engine. Closing the street into a **circle** adds exactly one coupling — houses `0` and `n-1` are now adjacent — and the fix is not a new recurrence but a **case split on that one pair**, solved by **running the linear solver twice over two open sub-ranges** and taking the `max`. This is the pattern's first "**reduce to the solved problem**" problem: the skill being tested is decomposition, not DP.
**Trigger:** any 198-shaped statement — "**maximum** sum, **no two adjacent**" — plus the words "**arranged in a circle**" / "**the first is the neighbour of the last**" / "**wrap-around**". The tell: a **single pair** of elements becomes newly coupled, and a single coupling is always killable by **enumerating the O(1) ways it can resolve** and solving the remaining linear problem in each. Whenever "linear problem I already know + one wrap-around edge", reach for **two constrained passes over the same solver**, never a new state dimension.

## Problem (1-liner)
198, but the array is **circular**: `nums[0]` and `nums[n-1]` count as adjacent.
**Examples:** `[2,3,2] → 3` (**not** `2 + 2` — the ends touch) · `[1,2,3,1] → 4` (`1 + 3`) · `[1,2,3] → 3`.
**Constraints:** `1 ≤ n ≤ 100`, `0 ≤ nums[i] ≤ 1000`, all **non-negative**. Max sum `50 × 1000 = 50000` ⇒ `int` is ample.
**Edges:** `n == 1` → `nums[0]` (**mandatory special case** — see insight #3) · `n == 2` → `max(nums[0], nums[1])` (the two houses are adjacent *twice*, which the split handles for free) · `n == 3` → the max single element, since **no two** of three circular houses are non-adjacent.

## Idea (1-liner)
`max(rob198(nums[0 .. n-2]), rob198(nums[1 .. n-1]))` — drop one end, then it's a straight street.

## Approach
1. Write (or reuse) the O(1)-space **linear** robber as a helper over a half-open range `[l, r)`.
2. If `n == 1`, return `nums[0]` — both ranges below would be empty.
3. `option1 = helper(0, n-1)` — the street **without the last house**, so house `0` is free to take.
4. `option2 = helper(1, n)` — the street **without the first house**, so house `n-1` is free to take.
5. Return `max(option1, option2)`.

> **Load-bearing insight #1 — why two ranges is EXACT, not a heuristic.** In any valid circular selection, houses `0` and `n-1` are **never both** robbed. So every valid answer omits at least one of them, i.e. it lies entirely inside `[0, n-2]` **or** entirely inside `[1, n-1]` — the two cases are **exhaustive**. And the converse holds: any no-two-adjacent selection *inside* either range is automatically valid on the circle, because the wrap-around pair can't both be present when one end is missing. Exhaustive + sound ⇒ the `max` of the two optima is the true optimum. **The cases overlap** (a solution using neither end is counted twice) and that is **harmless — you are taking a `max`, not a sum**; say this out loud, because it's the objection an interviewer will raise.

> **Load-bearing insight #2 — the memo is keyed by `index` only, so the two passes MUST NOT share it.** `helper(index, lastIndex)` has a **two-part state**, but `mem[index]` records just one of them. Pass 1 stores "best suffix from `index` **stopping at `n-1`**"; pass 2 asks for "best suffix from `index` **stopping at `n`**" and would read those stale values as its own. Hence the `mem.assign(n, -1)` between calls. **Contrast [[2-746-min-cost-climbing-stairs|746]], where one shared memo across both entry points *was* safe** — there `helper(i)` was a **pure suffix answer**, independent of where you started. The rule: *a memo may be shared exactly when every dimension the answer depends on is part of the key.* Alternatives to clearing: two separate `mem` vectors, or key on `mem[index][which]`.

> **Load-bearing insight #3 — `n == 1` is the one case the split cannot express.** With `n == 1`, `[0, n-1)` and `[1, n)` are both **empty**, so both passes return `0` and you'd answer `0` instead of `nums[0]`. This is not fixable by tweaking bounds — the decomposition assumes there *are* two distinct ends to drop. Guard it explicitly, first line. (`n == 2` needs no guard: the ranges become the single houses `{0}` and `{1}`, and `max` is right.)

> **Load-bearing insight #4 — the tempting wrong fixes.** (a) **"Solve linearly, then subtract if both ends were taken"** — you can't undo a global optimum locally; removing one end may make a completely different selection optimal. (b) **"Add a boolean state `tookHouse0`"** — it works and is O(n), but it doubles the state for a problem where a boundary split is free; interviewers read it as not seeing the reduction. (c) **"`nums[0] + rob(nums[2 .. n-2])` vs `rob(nums[1 .. n-1])`"** — this is the *"must rob house 0"* split; also **correct**, but the bounds are fiddlier (`n == 2`, `n == 3` need care) and it's harder to state. The **omit-an-end** split is the clean one.

> **Load-bearing insight #5 — the general move.** "Linear DP + one wrap-around coupling" ⇒ **fix the coupling by cases, run the linear solver once per case**. The cost is a constant factor (2×), never an extra dimension. The same trick appears in circular versions of Kadane (max subarray in a circle = `max(normal Kadane, total − min subarray)`), circular queue/scheduling problems, and gas-station-style rings.

## Code (clean canonical)
```cpp
class Solution {
    int robLinear(vector<int>& nums, int l, int r) {   // half-open [l, r)
        int prev2 = 0, prev1 = 0;
        for (int i = l; i < r; i++) {
            int cur = max(prev1, nums[i] + prev2);     // skip i  |  rob i
            prev2 = prev1;
            prev1 = cur;
        }
        return prev1;
    }
public:
    int rob(vector<int>& nums) {
        int n = nums.size();
        if (n == 1) return nums[0];                    // both ranges would be empty
        return max(robLinear(nums, 0, n - 1),          // drop the last house
                   robLinear(nums, 1, n));             // drop the first house
    }
};
```
**TC:** **O(n)** — two passes, `2n` iterations.  **SC:** **O(1)** — two ints, no table, no stack.
*The rolling form needs no base cases: `prev2 = prev1 = 0` reproduces the recursion's out-of-range `0`, so an empty range correctly returns `0` and `n == 2` falls out free.*

## My Solution
**Top-down memoized, prefix-direction with an exclusive `lastIndex` — ✅ correct.**
```cpp
class Solution {
    int helper(int index, int lastIndex, vector<int>& nums, vector<int>& mem) {
        if (index >= lastIndex) return 0;
        if (mem[index] != -1) return mem[index];

        int dPick = helper(index + 1, lastIndex, nums, mem);
        int pick  = nums[index] + helper(index + 2, lastIndex, nums, mem);

        return mem[index] = max(dPick, pick);
    }
public:
    int rob(vector<int>& nums) {
        int n = nums.size();
        if (n == 1) return nums[0];

        vector<int> mem(n, -1);
        int option1 = helper(0, n - 1, nums, mem);     // houses [0, n-2]
        mem.assign(n, -1);                             // ← the load-bearing line
        int option2 = helper(1, n, nums, mem);         // houses [1, n-1]
        return max(option1, option2);
    }
};
```
**O(n) time, O(n) memo + O(n) stack.** Three things this gets right that people get wrong:
- **`mem.assign(n, -1)` between the passes** — exactly insight #2. Without it, pass 2 reads pass 1's answers, which were computed under a different `lastIndex`. Concretely, on `[1,1,1,5]` a shared memo returns **2** instead of **6**: pass 1 fills `mem[1] = 1` (best of `[1,1]` stopping before the last house), and pass 2 — which needs `1 + 5 = 6` from index 1 — reads that `1` straight out of the cache and never explores house 3. You spotted the state/key mismatch; name it that way in an interview.
- **`if (index >= lastIndex) return 0;` sits above the memo lookup** — `index + 2` can overshoot to `lastIndex + 1 == n`, so `mem[index]` would be out of bounds; it's in-bounds *only* because the guard returns first. Same ordering discipline as [[1-70-climbing-stairs|70]], [[3-91-decode-ways|91]] and [[4-198-house-robber|198]].
- **The `n == 1` guard** — the one case the decomposition can't express.

Also fine: `mem[index] != -1` as a sentinel, legal **because `nums[i] >= 0`**; `>=` rather than `==` in the base, which is what makes the two-step overshoot safe.
**Refinements:** you switched from 198's suffix form (`index - 1`, `index - 2`) to a **prefix/forward** form here — a good instinct, since a moving *left* boundary is easier to express forwards, but say why, don't switch silently. `mem` is allocated at size `n` for a range of length `n-1`; harmless, and simpler than exact sizing. The upgrade is the same as in 198: **fold each pass into two rolling variables** and drop both the memo and the 100-deep stack — `O(n)/O(1)`, and the range version of the helper is *more* natural in the rolling form, since `l` and `r` are just loop bounds.

**Bottom-up table, twice — the same two passes with the recursion unrolled.**
```cpp
class Solution {
    int robLinear(vector<int>& nums, int l, int r) {        // half-open [l, r)
        int len = r - l;
        if (len == 0) return 0;                             // empty range

        vector<int> dp(len, 0);                             // dp is LOCAL to the range
        dp[0] = nums[l];
        if (len > 1) dp[1] = max(nums[l], nums[l + 1]);     // NOT nums[l+1]

        for (int i = 2; i < len; i++)
            dp[i] = max(dp[i - 1], nums[l + i] + dp[i - 2]);   // nums[l + i], not nums[i]

        return dp[len - 1];
    }
public:
    int rob(vector<int>& nums) {
        int n = nums.size();
        if (n == 1) return nums[0];
        return max(robLinear(nums, 0, n - 1),               // drop the last house
                   robLinear(nums, 1, n));                  // drop the first house
    }
};
```
**TC:** **O(n)** — `2n` cells filled.  **SC:** **O(n)** — one `dp` per pass, no recursion stack.

**The new trap this rung adds: two coordinate systems.** `dp` is indexed **locally** (`0 .. len-1`) while `nums` is indexed **globally**, so every read of the array must be `nums[l + i]`. Writing `nums[i]` compiles, runs, and passes pass 1 (where `l = 0`, so the two coordinate systems coincide) — it only goes wrong on pass 2, reading houses shifted one to the left. Trace `[1,1,1,5]`, pass 2 (`l = 1`, `len = 3`): `dp[0] = 1`, `dp[1] = 1`, then `dp[2] = max(1, nums[2] + dp[0]) = 2` instead of `max(1, nums[3] + dp[0]) = 6` — final answer `2` instead of `6`. **A bug that only one of two otherwise-identical calls can expose is exactly the kind that survives Example 1.** If you'd rather not carry the offset, index `dp` **globally** instead — `vector<int> dp(n)`, fill from `l`, base `dp[l] = nums[l]` and `dp[l+1] = max(nums[l], nums[l+1])`, return `dp[r-1]` — one convention or the other, never a mix.

Everything else is inherited from [[4-198-house-robber|198]]: `dp[1] = nums[l+1]` instead of `max(nums[l], nums[l+1])` is the **same signature base-case bug** shifted by `l`, and the `if (len > 1)` guard is what stops `len == 1` (which happens at `n == 2`) from writing out of bounds. Note that the **explicit `if (len == 0) return 0;`** exists only because the table form needs it — the rolling version in *Code (clean canonical)* gets the empty range free, which is exactly why the O(1) form is the one to write once you trust it.

*Ladder position: this is the rung **between** your memoized version and the canonical answer — it drops the 100-deep stack but still allocates a table for a **two-wide** dependency window. Say that out loud and collapse it to `prev2/prev1` in the same breath.*

## Other Approaches
- **Brute force / subset enumeration** — every subset, reject adjacent pairs *including the wrap pair*. **O(2ⁿ·n)**. Name it, kill it.
- **Naive recursion, twice** — **O(2ⁿ)** per pass. Same Fibonacci blow-up as 198.
- **Memoized top-down, twice** — **O(n)/O(n)**. Your version; the mechanical route, and the right first move.
- **Bottom-up table, twice** — **O(n)/O(n)**. Re-derive `dp[l] = nums[l]`, `dp[l+1] = max(nums[l], nums[l+1])` per range — the offset bases are where this rung bites.
- **Two rolling variables, twice** *(canonical)* — **O(n)/O(1)**. The expected answer.
- **Single pass with an extra boolean state** `dp[i][tookFirst]` — **O(n)/O(1)** too, and correct, but it invents a dimension the case-split gives free. Worth naming as the approach you *considered and rejected*.
- **Follow-ups to pre-empt:** *"binary **tree** of houses"* → **337 House Robber III**: the take/skip split survives, but the state becomes a **`(robbed, notRobbed)` pair per node** returned bottom-up in one DFS, O(n) — the circle trick does **not** transfer, because a tree has no single coupling to enumerate. *"circular, no two picks within **k**"* → the split becomes `k` cases (which of the wrap-adjacent houses you drop), each an O(n) pass ⇒ O(nk). *"return **which** houses"* → run the winning pass again with a `parent[]`, O(n) extra. *"**must** rob at least one"* → free here, since all values are non-negative. *"values may be **negative**"* → the empty selection becomes optimal; clamp with `max(0, …)` or state the convention. *"maximum **circular subarray** sum"* → **918**, the same "ring = two cases" reflex with Kadane instead: `max(Kadane, total − minSubarray)`, plus the all-negative guard.

> **The 70 / 746 / 91 / 198 / 213 progression to state out loud:** 70 establishes the two-back window (`+`, counts). 746 swaps the combine to `min` and puts a weight on **both** branches. 91 keeps `+` but **gates** each branch on a predicate. 198 swaps to `max` and makes the branches **asymmetric** (one skips the weight). **213 changes nothing about the recurrence at all** — it changes the **domain**, and is solved by calling 198 twice. Recognising which of those four dials a new problem turns is the entire pattern.

## Pitfalls
- **Sharing one memo across the two passes** — *the* signature bug here. `mem` is keyed by `index` but the answer also depends on `lastIndex`; clear it (or use two vectors / a 2-D key). Contrast 746, where sharing was legitimate.
- **Forgetting the `n == 1` guard** — both ranges go empty and you return `0`. Not fixable by adjusting bounds.
- **Off-by-one in the ranges** — with a **half-open** helper it's `[0, n-1)` and `[1, n)`; with an inclusive one it's `[0, n-2]` and `[1, n-1]`. Pick a convention and write it on the board *before* the bounds.
- **Trying to patch a single linear run** ("subtract an end if both were taken") — a global optimum doesn't decompose that way.
- **Worrying about the overlap between the two cases** — solutions using neither end are counted in both; harmless under `max`. Know why, so you can answer it.
- **Memo lookup above the range guard** — `index + 2` overshoots past `lastIndex`; the guard is what keeps `mem[index]` in bounds.
- **Adding the weight to both branches** — inherited from 198: `max(dp[i-1] + nums[i], …)` deletes the adjacency rule.
- **`dp[l+1] = nums[l+1]` in the table form** — the offset version of 198's signature base-case bug; it must be `max(nums[l], nums[l+1])`.
- **`mem[i] != -1` with negative values** — safe only because `nums[i] >= 0`.
- **Forgetting to write the memo before returning** — TLE, not WA.
- **Reflexive `long long`** — `50 × 1000 = 50000`. State the bound.
- **Stopping at "memoized, twice"** — correct but mid-ladder; walk it to O(1) space.
