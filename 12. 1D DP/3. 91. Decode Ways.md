# 1. 91. Decode Ways (LC 91) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/decode-ways/)
*Solved as a **Mixed-Practice drill** · D78 · 2026-08-18 — drawn cold, out of pattern context. Drill log: [[../MP/0. Index|MP]].*

**Pattern:** 1D DP — **[[1-70-climbing-stairs|70 Climbing Stairs]] with the branches made CONDITIONAL.** Identical two-back dependency window (`i-1`, `i-2`) and identical `+` combine (it's a **count**), so the table again collapses to **two rolling variables**. The only change: each branch is **guarded by a validity test** instead of always firing. The recurrence is free — **the guards are the entire problem.**
**Trigger:** "**how many ways** to decode" + a **digit string** + a mapping where "**some codes are contained in other codes**" (`"2"`/`"5"` vs `"25"`). The tells: (a) the answer is a **count of groupings** ⇒ combine with `+`, (b) at every position you consume **1 or 2 characters** — a fixed, tiny choice set ⇒ one recurrence covers it, and (c) the problem statement spends its whole example budget on **`"06"` being invalid**, which is the flashing sign that **leading zeros, not the recurrence, are what's being tested**. Whenever "count the ways to segment a string, where each piece must satisfy a validity predicate", you're here — and **139 Word Break** is the same shape with `+` swapped for `||`.

## Problem (1-liner)
`"1"→'A' … "26"→'Z'`. Count the **distinct groupings** of a digit string into valid codes; **`0` if none exist**.
**Examples:** `"12" → 2` (`1|2`, `12`) · `"226" → 3` (`2|26`, `22|6`, `2|2|6`) · `"06" → 0` (leading zero) · `"11106" → 2` (`1|1|10|6`, `11|10|6` — **not** `1|11|06`).
**Constraints:** `1 ≤ n ≤ 100`, digits only, **may contain leading zeros**; the answer fits in a **32-bit int** (stated, so no overflow reasoning needed — but say that you checked).
**Edges — all of them are zeros:** `"0" → 0` · `"06" → 0` · `"30" → 0` (a `0` can only ever be eaten as part of `10` or `20`; `3` doesn't qualify) · `"100" → 0` (`1|00` and `10|0` both strand a `0`) · `"101" → 1` (`10|1` only) · `"10" → 1` · `"27" → 1` (`2|7` only — `27 > 26`).

## Idea (1-liner)
`dp[i] = dp[i-1]·[s[i-1] ≠ '0'] + dp[i-2]·[10 ≤ s[i-2..i-1] ≤ 26]` — 70's recurrence with each term **gated by a validity check**.

## Approach
1. `dp[i]` = number of ways to decode the **first `i` characters**.
2. Base: `dp[0] = 1` (the empty string decodes exactly one way), `dp[1] = (s[0] != '0')`.
3. For `i = 2..n`: add `dp[i-1]` **if** the single digit `s[i-1]` is `1..9`; add `dp[i-2]` **if** the two digits `s[i-2..i-1]` form `10..26`.
4. Return `dp[n]`. The window is 2 ⇒ two scalars.

> **Load-bearing insight #1 — zeros are the whole problem.** A `0` **cannot stand alone** and **cannot lead a two-digit code**, so the *only* way a `0` survives is as the **second digit of `10` or `20`**. Everything the problem tests reduces to that one sentence: `"30"` → 0, `"100"` → 0, `"101"` → 1. Say it out loud before writing code and the guards write themselves.

> **Load-bearing insight #2 — the two-digit guard is a RANGE, not just `≤ 26`.** It must be `10 ≤ two ≤ 26`. Checking only `two <= 26` accepts `"06"` (`two = 6`) and silently overcounts — that's the exact bug Example 3 exists to catch. The lower bound **is** the leading-zero rule, expressed arithmetically.

> **Load-bearing insight #3 — `dp[0] = 1` and the guards do the zeroing.** Mirror of 70: the empty string has one decoding (the identity of `+`). You never special-case "impossible" — an undecodable string returns `0` automatically because **both guards fail and `dp[i]` stays `0`**, and a `0` propagates forward through every later term. That's why no explicit "return 0 if invalid" branch is needed.

> **Load-bearing insight #4 — same skeleton, third combine variation.** 70 adds **both** branches unconditionally. 746 takes the **`min`** of both. 91 adds both **conditionally**. Identical window, identical states, three different rules for merging them — naming this in the interview shows you see the pattern, not the problem.

## Code (clean canonical)
```cpp
class Solution {
public:
    int numDecodings(string s) {
        int n = s.size();
        if (s[0] == '0') return 0;                      // optional fast exit; dp handles it anyway

        int prev2 = 1, prev1 = 1;                       // dp[0] = 1 (empty), dp[1] = 1 (s[0] != '0')

        for (int i = 2; i <= n; i++) {
            int cur = 0;
            if (s[i - 1] != '0') cur += prev1;          // take one digit: 1..9
            int two = (s[i - 2] - '0') * 10 + (s[i - 1] - '0');
            if (two >= 10 && two <= 26) cur += prev2;   // take two digits: 10..26

            prev2 = prev1;
            prev1 = cur;                                // cur == 0 here ⇒ undecodable, propagates
        }
        return prev1;                                   // dp[n]
    }
};
```
**TC:** **O(n)** — one pass, O(1) work per index.  **SC:** **O(1)** — two ints, no table, no stack.
*`n == 1` falls out free: the loop never runs and `prev1` is already the answer.*

## My Solution (top-down memoized, suffix formulation)
```cpp
class Solution {
    bool valid(string str) {
        if (str[0] == '0') return false;
        if (stoi(str) > 26) return false;
        return true;
    }
    int ways(int index, string& s, vector<int>& mem) {
        int n = s.size();
        if (index == s.size()) return 1;                // empty suffix = one complete decoding

        if (mem[index] != -1) return mem[index];

        int ans = 0;
        if (index < n && valid(s.substr(index, 1)))     ans += ways(index + 1, s, mem);
        if (index < n - 1 && valid(s.substr(index, 2))) ans += ways(index + 2, s, mem);

        return mem[index] = ans;
    }
public:
    int numDecodings(string s) {
        vector<int> mem(s.size(), -1);
        return ways(0, s, mem);
    }
};
```
✅ **Correct — O(n) time, O(n) memo + O(n) stack.** The suffix formulation: `ways(i)` = decodings of `s[i..]`. Both rules are enforced in the right place, and `valid()` unifies them neatly — for a 1-char string `stoi ≤ 9` is always `≤ 26`, so only the leading-zero test bites; for 2 chars **both** tests bite. That's a genuinely tidy way to express insight #2 without writing the range by hand.
**The subtlety worth knowing rather than getting lucky on:** `mem` is sized `n` (indices `0..n-1`) but `ways(index + 2)` can reach `index == n`. It's in-bounds **only because the `index == s.size()` base returns before the `mem[index]` line** — the same load-bearing guard ordering as your 70 solution. Move the memo lookup above the base case and it's an out-of-bounds read.
**Refinements:** the real cost is `s.substr(...)` — it **heap-allocates a `std::string` on every check** (twice per index), and `stoi` then runs a full parse just to compare against 26. Replace both with digit arithmetic (`s[i] != '0'` and `(s[i]-'0')*10 + (s[i+1]-'0') <= 26`) and the constant factor collapses. Also: `valid(string str)` takes **by value** — another copy on top of the substr; use `const string&`. `index < n` in the first branch is **dead** (you already returned when `index == n`). And `index == s.size()` compares `int` to `size_t` — you computed `n` on the line above, so use it. *(Safe here, but note `index < n - 1` would **wrap catastrophically** if `n` were `size_t` and the string empty — it's fine only because `n` is an `int`.)* The real upgrade is the two-variable bottom-up above: same O(n) time, drops the memo and the 100-deep stack.

## Other Approaches
- **Naive recursion** — `f(i) = [valid 1] f(i+1) + [valid 2] f(i+2)`, no memo. **O(2ⁿ) / O(n)** stack. State it, then kill it by naming the cause: `f(i+2)` is reached from both branches, so the same suffix is recomputed exponentially often (`n = 100` on all `1`s ⇒ `Fib(101)` calls).
- **Top-down memoization** — **O(n) / O(n)**. Your version; the mechanical translation, and the right first move when the guards are fiddly enough that you'd rather not think about bottom-up order.
- **Bottom-up table** `dp[]` of size `n+1` — **O(n) / O(n)**. Drops the stack; the natural intermediate rung.
- **Two rolling variables** *(canonical)* — **O(n) / O(1)**. The expected final answer.
- **Brute force enumeration** — generate every grouping and validate. **O(2ⁿ)** time *and* **O(2ⁿ)** output. Only worth naming as the thing you're avoiding.
- **Follow-ups to pre-empt:** *"return the decodings themselves"* → no longer O(n)-countable, the output is exponential; backtrack instead. *"the string may contain `*` as a wildcard `1..9`"* → **LC 639 Decode Ways II**, same skeleton but each guard becomes a **weighted count** (`*` contributes 9 single-digit ways, `1*` contributes 9, `2*` contributes 6) with answers mod `10⁹+7` — the classic hard follow-up. *"mapping goes to 'ZZ' (1..702)"* → window widens to 3, three rolling vars. *"is it decodable at all (yes/no)?"* → swap `+` for `||` and you're at **139 Word Break** in miniature.

> **The 70 / 746 / 91 / 198 quartet to distinguish out loud:** same two-back window, four merge rules. **70** → `dp[i-1] + dp[i-2]`, `+` counts, branches **unconditional**. **746** → `min(dp[i-1] + w, dp[i-2] + w)`, `min` optimises, **both** branches pay. **91** → `dp[i-1] + dp[i-2]`, `+` counts, branches **conditional on a validity predicate**. **198** → `max(dp[i-1], dp[i-2] + nums[i])`, `max` optimises with **asymmetric** branches (one skips the weight). Name the combine operator, the weight placement, and the guard — you've named the problem.

## Pitfalls
- **Two-digit guard written as `two <= 26` only** — *the* signature bug. It accepts `"06"` (`two = 6`) and overcounts. The check is a **range**: `10 <= two <= 26`; the lower bound *is* the leading-zero rule.
- **Forgetting a lone `0` is undecodable** — `"30"` → 0, `"100"` → 0. A `0` survives only as the second digit of `10` or `20`; there is no other escape.
- **`dp[0] = 0`** — inherited straight from 70: the empty string decodes **one** way (identity of `+`). Zeroing it collapses everything to 0.
- **Adding an explicit "if undecodable return 0" branch** — unnecessary and a source of bugs. When both guards fail `dp[i]` stays `0` and propagates forward on its own.
- **Sizing the memo `n` and reordering the base case below the lookup** (top-down) — `index` reaches `n`, so it's in-bounds *only* because `index == n` returns first. Same trap as 70.
- **`substr` + `stoi` inside the hot loop** — correct but allocates a string and parses an int per check. Digit arithmetic is the interview-grade version; mention the difference even if you write the readable one first.
- **`index < n - 1` with an unsigned `n`** — wraps to a huge value when the string is empty. Safe only because `n` is an `int` here; say why.
- **Forgetting to write the memo before returning** — still correct, still O(2ⁿ); surfaces as a **TLE, not a WA**.
- **Updating rolling variables without a temporary** — stage in `cur` first; assigning `prev1` before `prev2` destroys the value `prev2` needs.
- **Reflexive overflow panic** — the problem *states* the answer fits in 32 bits. Note that you noticed, then move on; `long long` here is reflex, not reasoning.
- **Stopping at the memoized version in an interview** — correct but the middle of the ladder. Walk it to O(1) space.
