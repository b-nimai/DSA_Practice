# 8. 121. Best Time to Buy and Sell Stock (LC 121) — Easy
🔗 [Open on LeetCode](https://leetcode.com/problems/best-time-to-buy-and-sell-stock/)

**Pattern:** 1D DP — **[[6-53-maximum-subarray|53]] in disguise: Kadane run on the DIFFERENCE array.** The problem asks for `max(prices[j] − prices[i])` over `i < j`, and the single move that makes it trivial is noticing that `prices[j] − prices[i] = Σ_{k=i+1..j} (prices[k] − prices[k-1])` — **a difference of two elements telescopes into a sum of consecutive deltas.** So "best pair with `i < j`" **is** "maximum-sum contiguous subarray of `d[k] = prices[k] − prices[k-1]`", and Kadane solves it verbatim. The other, equivalent framing — the one you actually write — is the **prefix-extremum sweep**: fix the sell day `j`, and the best partner is forced to be the **cheapest day seen so far**, so one running `minSoFar` plus one running `bestProfit` closes it in a single pass. **The transferable move: when an answer is `max over pairs f(j) − g(i)` with `i < j`, you never need both loops — sweep `j` forward and carry the running optimum of `g` over the prefix.** That reduction (O(n²) pairs → O(n) with one carried extremum) is the single most reused trick in the whole array section.
**Trigger:** "**buy on one day, sell on a LATER day**", "**a single transaction**", "**maximum profit**, return `0` if none is possible" — the shape is **`max(a[j] − a[i])` subject to `i < j`**, i.e. an optimum over an **ordered pair**, not over a window or a subset. Two tells separate it from its neighbours: **"choose ONE day to buy and ONE day to sell"** (exactly one transaction ⇒ this is *not* [[../11. Greedy & Intervals/11. 122. Best Time to Buy and Sell Stock II|122]]'s delta-sum) and **"if you cannot achieve any profit, return 0"** (the empty transaction is **legal**, which is precisely where it diverges from 53's non-empty subarray). Reflex: **one pass, carry `minSoFar`, answer `max(0, best)`.**

## Problem (1-liner)
Pick one buy day and one strictly later sell day to maximise `prices[sell] − prices[buy]`; return **`0`** if every choice loses money.
**Examples:** `[7,1,5,3,6,4] → 5` (buy day 2 @ `1`, sell day 5 @ `6`; note the max `6` and the min `7` are in the **wrong order**, which is the whole difficulty) · `[7,6,4,3,1] → 0` (**monotonically falling** ⇒ no transaction at all, *not* `-1` and not `1 − 7 = −6`).
**Constraints:** `1 ≤ n ≤ 10⁵`, `0 ≤ prices[i] ≤ 10⁴`. Max possible profit is `10⁴ − 0 = 10⁴` ⇒ **`int` is wildly sufficient**, no bound-hunting needed (contrast [[6-53-maximum-subarray|53]], where you had to compute `10⁵ × 10⁴`). `n = 10⁵` kills the **O(n²)** pair loop (5×10⁹ comparisons) and demands O(n) or O(n log n).
**Edges:** `n == 1` → **`0`** (you cannot sell later than the only day) · **strictly decreasing** → `0` · **all equal** `[3,3,3]` → `0` · the **global max before the global min** (`[7,1]` style) → the naive `max − min` answer is flat wrong · `prices[i] = 0` is allowed, so a `minSoFar` sentinel of `0` is a bug.

## Idea (1-liner)
Sweep left to right carrying the **cheapest price seen so far**; at every day take `profit = max(profit, price − minSoFar)`, seeded at `0` so "no transaction" is always on the table.

## Approach
1. Reframe: the answer is `max over j of ( prices[j] − min over i < j of prices[i] )`. The **inner min depends only on the prefix**, so it can be maintained incrementally instead of recomputed.
2. Initialise `minSoFar = prices[0]` and `profit = 0` — the `0` **is** the "return 0 if no profit" clause encoded as a base case, not a post-hoc clamp.
3. For each day `i`: update `minSoFar = min(minSoFar, prices[i])`, then `profit = max(profit, prices[i] − minSoFar)`.
4. Return `profit`. One pass, two scalars, no table.
5. *(Equivalent derivation to say out loud)* Build `d[k] = prices[k] − prices[k-1]` and run plain Kadane on it with the answer floored at `0`. Same numbers, same complexity — the difference array makes the family resemblance visible, the prefix-min makes the code shorter.

> **Load-bearing insight #1 — why `max − min` is WRONG, and it's the first thing an interviewer checks.** The naive answer "find the largest and smallest price and subtract" ignores the **temporal ordering** `i < j`. Example 1 is built to punish exactly this: `max = 7` at index 0, `min = 1` at index 1, so `max − min = 6` — but the `7` comes **before** the `1`, and that trade is illegal. **The problem is not "the spread of the array", it is "the largest rise that goes forward in time"**, which is why a *sweep* is required and sorting is catastrophic (it destroys the only structure that matters). The moment you say "the constraint `i < j` means the min must be taken over the **prefix**, not the whole array", you have solved it.

> **Load-bearing insight #2 — the telescoping identity that makes this literally [[6-53-maximum-subarray|53]].** `prices[j] − prices[i] = Σ_{k=i+1..j} d[k]` where `d[k] = prices[k] − prices[k-1]`. Every legal transaction is a **contiguous run** of daily deltas, and its profit is that run's **sum** — so "best transaction" ≡ "**maximum-sum contiguous subarray of `d`**". On `[7,1,5,3,6,4]`, `d = [-6, 4, -2, 3, -2]` and Kadane returns `4 + (−2) + 3 = 5`. ✅ **This is the sentence that unlocks the entire stock family**, because the same delta view instantly explains [[../11. Greedy & Intervals/11. 122. Best Time to Buy and Sell Stock II|122]]: unlimited transactions means you may take **any set** of non-overlapping runs, so you just take **every positive delta** — `Σ max(0, d[k])`. **121 = the best single run · 122 = the sum of all positive runs.** One picture, two problems.

> **Load-bearing insight #3 — the ONE place 121 and 53 genuinely differ: the empty case is LEGAL here.** 53 forbids the empty subarray, so seeding `best = 0` was *the* signature bug (all-negative arrays wrongly returned `0`). 121 **requires** that behaviour: "if you cannot achieve any profit, return `0`" is the problem *asking* for the empty transaction. So the exact initialisation that was a bug in 53 is the **specification** in 121 — `profit = 0`, never `INT_MIN`. **Naming this inversion out loud is the highest-value thing you can say about this problem**, because it proves you understand that Kadane's seed encodes *whether the empty selection is allowed*, rather than having memorised one incantation. (Equivalently: 121's answer is `max(0, kadane(d))`, which is exactly 53's stated "allow the empty subarray" follow-up.)

> **Load-bearing insight #4 — why updating `minSoFar` BEFORE reading it is safe (and the subtle same-day question).** Updating the min first means index `i` is a candidate buy day for a sale on day `i` itself, contributing `prices[i] − prices[i] = 0`. Since `profit` is already seeded at `0`, that candidate **can never change the answer** — so the "buy and sell on the same day" leak is harmless, and both orderings of the two lines are correct here. **But say why, don't hand-wave it**: if the problem had *forbidden* the zero-profit no-op (e.g. "return `-1` if no profit is possible", as **LC 2016** does), the order would become load-bearing and you would have to read the min from the *strict* prefix — compute `profit` first, *then* update `minSoFar`. Knowing which invariants your line order depends on is the difference between a solution that survives a follow-up and one that quietly breaks.

> **Load-bearing insight #5 — the state-machine DP you don't need here but must have ready.** Model it as two states: `hold` = best balance while **owning** a share, `free` = best balance while owning **nothing**. Then `hold = max(hold, −prices[i])` (with **one** transaction you buy from a balance of `0`, so it's `−prices[i]`, not `free − prices[i]`) and `free = max(free, hold + prices[i])`; seed `hold = −prices[0]`, `free = 0`, answer `free`. It is the same O(n)/O(1) numbers by a longer road — **but it is the only formulation that survives the follow-ups**, because `hold`/`free` generalises verbatim to a fee (**714**), a cooldown (**309**), and `k` transactions (**123 / 188**, `2k` states, O(nk)). One line covers the whole family: ***the greedy delta-sum is the `k = ∞` case, 121 is the `k = 1` case, and the `hold`/`free` machine is what interpolates between them.*** Lead with the prefix-min sweep; offer this the instant a follow-up lands.

## Code (clean canonical)
```cpp
class Solution {
public:
    int maxProfit(vector<int>& prices) {
        int minSoFar = prices[0], profit = 0;   // 0 = the legal "no transaction"

        for (int p : prices) {
            minSoFar = min(minSoFar, p);        // cheapest buy day in the prefix
            profit   = max(profit, p - minSoFar);
        }
        return profit;
    }
};
```
**TC:** **O(n)** — one pass.  **SC:** **O(1)** — two ints.
*Seeding `minSoFar = prices[0]` (not `INT_MAX`) avoids any overflow question in `p - minSoFar` and makes `n == 1` fall out free: the single iteration yields `0`.*

**Kadane-on-deltas form** — same problem, family resemblance made explicit:
```cpp
int cur = 0, best = 0;                                  // 0 seed ⇒ empty run allowed
for (int i = 1; i < prices.size(); i++) {
    cur  = max(0, cur + prices[i] - prices[i - 1]);     // extend | drop the run
    best = max(best, cur);
}
return best;
```

## My Solution
**Prefix-min sweep — ✅ correct, and it is the canonical answer.**
```cpp
class Solution {
public:
    int maxProfit(vector<int>& prices) {
        int mini = prices[0], profit = 0;

        for (int i = 0; i < prices.size(); i++) {
            mini = min(mini, prices[i]);
            profit= max(profit, prices[i] - mini);
        }
        return profit;
    }
};
```
**O(n) time, O(1) space.** Verified: `[7,1,5,3,6,4] → 5` · `[7,6,4,3,1] → 0` · `[1] → 0` · `[2,4,1] → 2` (the trap case where the *later* min is worthless) · `[3,3,3] → 0`.

Three things this gets right, each worth naming rather than leaving implicit:
- **`profit = 0`, not `INT_MIN`** — this is the "return 0 if no profit" clause living in the initialiser. Exactly the seed that was a **bug** in [[6-53-maximum-subarray|53]] and is the **spec** here; see insight #3.
- **`mini = prices[0]`, not `0`** — `0 ≤ prices[i]` is in the constraints, so a `0` sentinel would make `profit` collapse to `max(prices)`. (`INT_MAX` also works but invites a needless overflow discussion on `p - mini`.)
- **`mini` updated before the read** — safe here for the reason in insight #4 (the same-day trade contributes `0`, which the seed already dominates), **not** by luck. Be ready to say that; it's the one line an interviewer will poke at.

**Refinements:** the loop can start at `i = 1` since day `0` only ever sets `mini` to itself — or drop the index entirely for a range-`for` (`for (int p : prices)`), which removes the only place an off-by-one could hide; `prices.size()` is `size_t`, so comparing it to `int i` emits a signed/unsigned warning on a strict local build (LeetCode hides this). Add the spacing on `profit =`, and add the one comment that carries the whole idea — `// best sell today = today's price − cheapest day so far`. **Say the alternative before you're asked:** "this is Kadane on the difference array with the answer floored at 0", and "if a follow-up adds a fee, a cooldown, or `k` transactions I'd switch to the `hold`/`free` state machine". That sentence is what turns an Easy into a signal.

## Other Approaches
- **Brute force, all ordered pairs** — two loops over `i < j`, track `max(prices[j] − prices[i])`, floor at `0`. **O(n²) / O(1)**. At `n = 10⁵` that is ~5×10⁹ operations — name the bound, then kill it. It *is* worth writing on the board for one line as the definition of correctness you then optimise.
- **Suffix-max mirror** — precompute `suffMax[i] = max(prices[i..n-1])`, then answer `max over i of (suffMax[i] − prices[i])`. **O(n) / O(n)**. Same answer from the other end; strictly worse in space, but it is the version that generalises when you also need *"for each buy day, what was the best exit"*.
- **Prefix-min sweep** *(canonical, the user's)* — **O(n) / O(1)**. The expected answer.
- **Kadane on the difference array** — **O(n) / O(1)**. Identical cost; the value is conceptual, since it makes 121 a one-line corollary of [[6-53-maximum-subarray|53]] and 122 a one-line corollary of *the same picture*.
- **`hold` / `free` state-machine DP** — **O(n) / O(1)**. Overkill standalone, mandatory once follow-ups arrive (see insight #5).
- **Divide and conquer** — `max(bestLeft, bestRight, maxRight − minLeft)`, `T(n) = 2T(n/2) + O(n)` ⇒ **O(n log n) / O(log n)**. Strictly worse, but it is the **segment-tree merge rule** over `(min, max, bestProfit)` per node, and therefore the only route to *"best profit within day range `[l, r]`, with price updates"* in O(log n). Mention it only if updates or range queries appear.
- **Follow-ups to pre-empt:** *"return the buy/sell days"* → record `buyIdx` whenever `mini` improves and commit `(buyIdx, i)` whenever `profit` improves — O(n), no second pass. *"**unlimited** transactions"* → [[../11. Greedy & Intervals/11. 122. Best Time to Buy and Sell Stock II|122]], `Σ max(0, d[k])`; the greedy is valid **only** because same-day buy/sell is allowed. *"**at most two** transactions"* → **123**: four rolling states `buy1, sell1, buy2, sell2`, O(n)/O(1). *"**at most k**"* → **188**: `2k` states, O(nk), with the `k ≥ n/2` shortcut falling back to 122's greedy. *"**cooldown** of one day after selling"* → **309**, a third state. *"**transaction fee**"* → **714**, `free = max(free, hold + p − fee)`. *"**maximum drawdown** instead"* → the exact mirror: carry `maxSoFar`, take `max(maxSoFar − prices[i])`. *"return `-1` if no profit exists"* → **2016**, where the zero-profit no-op must be excluded and the min must come from the **strict** prefix (insight #4). *"prices arrive as a **stream**"* → the sweep is already online: two scalars, one price at a time, answer available at every instant.

> **The 70 / 746 / 91 / 198 / 213 / 53 / 152 / 121 progression to state out loud:** 70 sets the skeleton (`+`, counts) · 746 swaps the combine to `min` with weights on **both** branches · 91 keeps `+` but **gates** the branches · 198 swaps to `max` with **asymmetric** branches · 213 changes the **domain**, not the recurrence · 53 changes the **state definition** (prefix optimum → *ending exactly here*) · 152 changes the **operator's algebra** (a point state widens to an **interval**) · **121 changes the INPUT**: the recurrence, the state and the operator are all 53's, untouched — you simply run them on the **difference array**, and flip the seed because **the empty selection is now legal**. Combine operator · weight placement · guard · domain · state definition · operator algebra · **the input transform**: seven dials, and naming which one a new problem turns *is* the pattern.

## Pitfalls
- **Answering `max(prices) − min(prices)`** — *the* signature error: it ignores `i < j`. Example 1 punishes it directly (`7` precedes `1`, giving an illegal `6` instead of `5`). The min must be over the **prefix**.
- **Sorting the array** — order **is** the problem; sorting yields `max − min` and destroys the question outright. The same "never sort" reflex as [[../11. Greedy & Intervals/11. 122. Best Time to Buy and Sell Stock II|122]].
- **Seeding `profit = INT_MIN`** (carrying 53's habit across) — returns a **negative** profit on a falling market instead of `0`. Here the empty transaction is **legal**; the seed is the spec, not a bug. The inversion is the whole point of insight #3.
- **Seeding `mini = 0`** — prices can be `0`, so the answer collapses to `max(prices)`. Use `prices[0]` (or `INT_MAX`).
- **Applying 122's delta-sum here** — `[7,1,5,3,6,4]` gives **7**, but only **one** transaction is allowed, so the answer is `5`. The single most common cross-wiring in the stock family, and it fires in both directions.
- **Forgetting `n == 1`** — free with the `prices[0]` seed (the sole iteration yields `0`), but an implementation that starts from an "empty" state must special-case it.
- **Assuming the optimal buy is the GLOBAL minimum** — it is only the minimum of the prefix *before* the optimal sell day. On `[2,10,1,5]` the answer is **8** (buy `2`, sell `10`), while the global min `1` can only reach `5` for a profit of `4`. The sweep considers every sell day against its own prefix min, so it never has to reason about which run wins — that is exactly what you are buying with it.
- **Two nested loops "because n looks small"** — `10⁵` ⇒ 5×10⁹ ops ⇒ TLE. State the bound before writing it.
- **Reflexive `long long`** — the profit is bounded by `10⁴`. Say the bound out loud rather than guessing (the mirror of [[7-152-maximum-product-subarray|152]], where the *problem* hands you the guarantee).
- **In the delta form, forgetting the `max(0, …)` clamp on `cur`** — without it you have plain 53 on `d`, which may return a negative and violates "return 0".
