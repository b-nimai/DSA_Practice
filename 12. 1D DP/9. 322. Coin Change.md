# 9. 322. Coin Change (LC 322) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/coin-change/)

**Pattern:** 1D DP — **the first problem in the pattern where `dp`'s index is NOT an index into the input array.** In 70/746/91/198/53/152/121 the state was "position `i` in `nums`/`s`" and the transitions were a **fixed, tiny** set (`i-1`, `i-2`). Here the state is the **amount of money itself** — a value in `[0, amount]` that has nothing to do with `coins.size()` — and `coins` is demoted from *the domain* to *the **transition set***: `dp[a] = 1 + min over c in coins of dp[a - c]`. Two things change at once and both are load-bearing: **(a)** the table is sized by a **constraint bound**, not by the input length, and **(b)** the branching factor becomes **`|coins|`**, so the fixed 2-back window — and with it the rolling-variables collapse that ended every previous note — is **gone**: `dp[a]` can reach back as far as `max(coins)`, so you keep the whole array. This is the textbook **unbounded knapsack** shape (**min** flavour), and the tell that it's *unbounded* rather than 0/1 is that `dp[a]` reads `dp[a - c]` **from the same row being written** — reusing a coin is not just allowed, it's automatic.
**Trigger:** "**fewest / minimum number of** items summing to a **target**" + "**infinite supply** of each kind" + "return **-1** if it's impossible". The three tells, in order of decisiveness: **(1)** the answer is a **count of items**, not of ways ⇒ combine with `min`, base `dp[0] = 0`; **(2)** "you may assume you have an **infinite number** of each coin" ⇒ **unbounded**, so one 1-D table suffices and the loop order is free; **(3)** the constraints hand you a **small target (`amount ≤ 10⁴`) and a tiny item set (`≤ 12` coins)** while coin *values* run to `2³¹−1` — a deliberate shape that says *"pseudo-polynomial DP over the amount is intended"*. **The reflex that matters most: the instant you catch yourself reaching for the biggest coin first, stop — greedy is wrong here**, and knowing the 6-line counterexample cold is the actual test (see insight #1). Whenever you see "make exactly `T` from an unlimited multiset, optimising a count", you are here; swap `min` for `+` and you're in **518 Coin Change II**.

## Problem (1-liner)
Given denominations `coins` (**unlimited** supply of each) and a target `amount`, return the **fewest coins** that sum to **exactly** `amount`, or **`-1`** if no combination does.
**Examples:** `coins = [1,2,5], amount = 11 → 3` (`5+5+1`; note `5+2+2+2` also works with 4 coins — you want the *minimum*, so a single valid combination is not an answer) · `coins = [2], amount = 3 → -1` (**parity** makes it unreachable, not just "hard") · `coins = [1], amount = 0 → 0` (**zero coins**, the empty selection — *not* `-1`).
**Constraints:** `1 ≤ coins.length ≤ 12`, `1 ≤ coins[i] ≤ 2³¹−1`, `0 ≤ amount ≤ 10⁴`. Read all three together: `amount × coins.length ≤ 10⁴ × 12 = 1.2×10⁵` operations ⇒ **the O(amount·n) table is trivially fast**, which is the whole reason the bounds look like this. **`coins[i]` up to `2³¹−1` is a planted trap** — a coin can be astronomically larger than `amount`, so any expression of the form `amount − coins[i]` must be written so it cannot overflow (insight #4). Coins are **distinct** and **positive** (no `0` coin ⇒ no infinite loop, no zero-weight cycle).
**Edges:** `amount == 0` → **`0`** for *any* coin set, including one where nothing else is reachable · a **single coin `[2]` with odd amount** → `-1` · **every coin > amount** → `-1` · `coins = [1]` → always solvable, answer `amount` (so the answer is bounded by `10⁴`, which hands you the perfect ∞ sentinel) · `coins = [2³¹−1]` with `amount = 10⁴` → `-1`, and the subtraction must survive it.

## Idea (1-liner)
`dp[a]` = fewest coins making exactly `a`; **partition by the LAST coin spent** — `dp[a] = 1 + min over c ≤ a of dp[a − c]` — with `dp[0] = 0` and unreachable amounts held at **∞** (use `amount + 1`, never `INT_MAX`).

## Approach
1. Allocate `dp` of size `amount + 1`, filled with the sentinel **`amount + 1`** meaning *unreachable*. Set `dp[0] = 0` — making zero costs zero coins.
2. Sweep `a = 1 … amount` in increasing order. For each `a`, try **every** coin `c`: if `c <= a`, relax `dp[a] = min(dp[a], dp[a - c] + 1)`.
3. Because `a - c < a` always (coins are `≥ 1`), every value read is already final when you read it — **increasing order of `a` is the dependency order**, no second pass needed.
4. Return `dp[amount] > amount ? -1 : dp[amount]` — the sentinel survives untouched exactly when no combination exists, so the `-1` is a **read-off**, not a special case you have to detect.

> **Load-bearing insight #1 — greedy is WRONG, and the counterexample is the single most important thing to have memorised.** "Take the largest coin that fits, repeat" is correct for real currencies and **fails in general**. `coins = [1, 3, 4], amount = 6`: greedy takes `4`, then `1`, then `1` ⇒ **3 coins**; the optimum is `3 + 3` ⇒ **2 coins**. Also `coins = [1, 5, 6, 9], amount = 11`: greedy `9+1+1 = 3`, optimum `5+6 = 2`. **Why it breaks:** greedy assumes the largest coin is in *some* optimal solution — an exchange argument — and that only holds for **canonical** coin systems (each coin a multiple-ish of the next, like `[1,5,10,25]`). The problem hands you an **arbitrary** set, so no exchange argument exists and you must search. **State this out loud before writing a line** — an interviewer's first probe is almost always "why not just take the biggest coin?", and having the 4-token counterexample ready is worth more than the code. (Corollary worth knowing: deciding *whether* a given coin system is canonical is itself a non-trivial problem — you cannot test for it at the whiteboard, which is why DP is the only safe answer.)

> **Load-bearing insight #2 — the sentinel is `amount + 1`, not `INT_MAX`, and that is a correctness fix, not a style tweak.** You need an "infinity" that (a) **loses every `min`** against any real answer and (b) **survives `+ 1` without overflowing**. `INT_MAX` fails (b) instantly: `dp[a-c] + 1` wraps to `INT_MIN`, which then *wins* every `min` and silently poisons the table with garbage negatives. `amount + 1` is airtight because **every coin is `≥ 1`, so any reachable amount needs at most `amount` coins** — `amount + 1` is therefore strictly greater than every legal answer, and `(amount + 1) + 1` is nowhere near overflow. *The transferable rule: pick your ∞ from the **problem's own bound**, not from the type's — then the arithmetic that would break `INT_MAX` is free.* This also collapses the final test to one comparison instead of a flag. (The user's `INT_MAX - 1` is the same instinct and *is* safe here because the `+ 1` is guarded behind an explicit `req != -1` check — but it needs that guard to be safe, while `amount + 1` needs nothing.)

> **Load-bearing insight #3 — "unbounded" is exactly the statement that `dp[a]` may read `dp[a − c]` from the ROW IT IS WRITING.** In **0/1 knapsack** each item is usable once, so the transition must read the *previous* item's row (`dp[i-1][w]`), and the 1-D collapse only works if you iterate the weight **downward**. Here reuse is unlimited, so reading the *current* row is not a bug — it is the feature: `dp[a - c]` may itself already contain a `c`, and stacking another one is legal. That single sentence tells the interviewer you know which knapsack you're in. **Consequence: the loop order is completely free** — `for a { for c }` and `for c { for a }` give identical answers, because `min` is associative/commutative and every path to `a` is considered either way. **This freedom evaporates in [518 Coin Change II](https://leetcode.com/problems/coin-change-ii/)**, where you *count* combinations: coins-outer counts **combinations** (`1+2` ≡ `2+1`, the intended answer), amounts-outer counts **permutations** (that's **377 Combination Sum IV**). *So the loop-order question is meaningless for `min`/`max` and decisive for `+`* — knowing **why** is a much stronger signal than knowing the rule.

> **Load-bearing insight #4 — `coins[i] ≤ 2³¹−1` means you must write the guard, not the subtraction.** Write `if (a - coins[j] >= 0)` and you have computed `a - coins[j]` **before** testing it: with `a = 10⁴` and `coins[j] = 2³¹−1` that's `−2147473647`, which fits in `int` by about ten thousand — i.e. it is correct here **by a hair**, and would be signed-overflow UB if the constraint were one order looser. Write `if (coins[j] <= a)` instead and the comparison happens on the **original** values, so the question never arises. Same in the top-down form: the `if (amount < 0) return -1;` base must sit **above** the `mem[amount]` lookup, or a huge coin drives a **negative index** into the vector — the exact same guards-before-memo trap as [[1-70-climbing-stairs|70]] and [[3-91-decode-ways|91]], just with a much bigger blast radius. **Cheap habit that removes a whole class of bugs: test the coin against the amount, never the difference against zero.**

> **Load-bearing insight #5 — this is literally BFS on an unweighted graph, and saying so is free credit.** Model amounts `0 … amount` as nodes with an edge `a → a + c` for every coin `c`. Every edge costs **one coin**, so "fewest coins" is **shortest path in an unweighted graph** ⇒ **BFS from `0`, and the first time you dequeue `amount` its level IS the answer.** Same `O(amount · n)` worst case and same `O(amount)` space, but it **stops the moment it finds the target** instead of filling the entire table, which makes it dramatically faster on small answers with big amounts. It also explains the DP for free: BFS levels *are* the `dp` values, and the increasing-`a` sweep is just the topological order of the same DAG. **Say "this is unweighted shortest path" out loud** — it reframes an unbounded-knapsack question as a graph question and shows you see the structure rather than the template. (If coins had *different costs* per use, the levels stop being uniform and you'd need **Dijkstra** — which is exactly what `dp` with a `min` already is.)

> **Load-bearing insight #6 — the "unset" sentinel in a memo must not collide with a LEGAL answer.** In the memoized form the answer set is `{0, 1, 2, …} ∪ {−1}`, so the usual `mem[a] == -1 → not computed` idiom is **broken**: a genuine "impossible" result of `−1` would be recomputed forever (exponential blow-up, seen as TLE, not WA — the nastiest failure mode). The user's `-2` sentinel is precisely the right fix. The cleaner alternative is to keep the table in the **∞ = `amount + 1`** convention internally and translate to `−1` **once**, at the return — then "unset" can be `−1` again with no collision. *General rule: the memo's "empty" marker must live **outside the codomain of the function**; if the function can return every int you care about, use a parallel `visited` array or `optional`.*

## Code (clean canonical)
```cpp
class Solution {
public:
    int coinChange(vector<int>& coins, int amount) {
        const int INF = amount + 1;                 // > any real answer (min coin >= 1)
        vector<int> dp(amount + 1, INF);
        dp[0] = 0;                                  // zero coins make zero

        for (int a = 1; a <= amount; a++)
            for (int c : coins)
                if (c <= a)                         // compare coin vs amount, never a - c vs 0
                    dp[a] = min(dp[a], dp[a - c] + 1);

        return dp[amount] > amount ? -1 : dp[amount];
    }
};
```
**TC:** **O(amount · n)** — `10⁴ × 12 ≈ 1.2×10⁵`.  **SC:** **O(amount)** — one table; **the rolling-variable collapse does NOT apply**, because `dp[a]` reaches back up to `max(coins)`, not a fixed 2.
*`amount == 0` falls out free: the loop never runs and `dp[0] = 0` is returned. The `dp[a - c] + 1` cannot overflow — `INF + 1 = amount + 2 ≤ 10002`.*

**BFS form** — same bounds, early exit, and it makes the shortest-path reading explicit:
```cpp
int coinChange(vector<int>& coins, int amount) {
    if (amount == 0) return 0;
    vector<char> seen(amount + 1, 0);
    queue<int> q; q.push(0); seen[0] = 1;

    for (int level = 1; !q.empty(); level++)
        for (int sz = q.size(); sz > 0; sz--) {
            int cur = q.front(); q.pop();
            for (int c : coins) {
                if (c > amount - cur) continue;         // no overflow, no negative index
                int nxt = cur + c;
                if (nxt == amount) return level;        // first arrival = fewest coins
                if (!seen[nxt]) { seen[nxt] = 1; q.push(nxt); }
            }
        }
    return -1;
}
```

## My Solution
**Both forms are ✅ correct.** The bottom-up one is the expected answer; the memoized one shows you can derive it top-down. Verified on `[1,2,5]/11 → 3` · `[2]/3 → -1` · `[1]/0 → 0` · `[1,3,4]/6 → 2` (the greedy trap) · `[2³¹−1]/10000 → -1`.

**(a) Bottom-up table**
```cpp
vector<int> mem(amount + 1, -1);
mem[0] = 0;
for (int i = 1; i <= amount; i++) {
    int mini = INT_MAX - 1;
    for (int j = 0; j < coins.size(); j++)
        if (i - coins[j] >= 0) {
            int req = mem[i - coins[j]];
            if (req != -1) mini = min(mini, req + 1);   // -1 means unreachable, don't extend it
        }
    mem[i] = mini == INT_MAX - 1 ? -1 : mini;
}
return mem[amount];
```
Three things this gets **right**, each worth naming rather than leaving implicit:
- **`mem[0] = 0` as the base** — the identity of "sum of coin counts", the same *"the empty answer is the operator's identity"* move as `ways(0) = 1` in [[1-70-climbing-stairs|70]] and `cost = 0` in [[2-746-min-cost-climbing-stairs|746]].
- **The `req != -1` guard** — you must never do `-1 + 1 = 0` and report an unreachable amount as *free*. This is the single most common wrong answer on this problem.
- **`INT_MAX - 1`, not `INT_MAX`** — the `- 1` is there so the `+ 1` can't overflow, which is the right instinct even though the `req != -1` guard already makes the add unreachable.

**Refinements, in the order I'd make them:**
1. **Carry `-1` inside the table and you pay for it twice** — with the `amount + 1` sentinel the inner body is one line (`dp[a] = min(dp[a], dp[a-c] + 1)`), the `mini` temporary disappears, and the ternary moves to a single translation at the `return`. Fewer places to forget the guard (insight #2).
2. **`if (coins[j] <= i)` instead of `if (i - coins[j] >= 0)`** — with `coins[j]` up to `2³¹−1` the subtracted form is correct only by a ten-thousand-wide margin; the compare-first form can't be wrong (insight #4).
3. **`for (int c : coins)`** — `coins.size()` is `size_t`, so `int j < coins.size()` emits a signed/unsigned warning on a strict local build (LeetCode hides it), and the range-`for` deletes the only place an off-by-one could live.
4. **Add the one comment that carries the whole idea** — `// dp[a] = fewest coins for a; partition by the LAST coin spent`.

**(b) Top-down memoization** — same recurrence, mechanical direction:
```cpp
int helper(vector<int>& coins, int amount, vector<int>& mem) {
    if (amount == 0) return 0;
    if (amount < 0)  return -1;              // MUST be above the mem lookup: negative index otherwise
    if (mem[amount] != -2) return mem[amount];
    int mini = INT_MAX - 1;
    for (int i = 0; i < coins.size(); i++) {
        int req = helper(coins, amount - coins[i], mem);
        if (req != -1) mini = min(mini, req + 1);
    }
    return mem[amount] = (mini == INT_MAX - 1 ? -1 : mini);
}
// caller: vector<int> mem(amount + 1, -2); ...
```
**The `-2` sentinel is the sharpest thing in this solution and you should say why out loud:** `-1` is a *legal return value* here, so using it as "not yet computed" would make every impossible sub-amount recompute forever — an exponential TLE that hides as a performance bug rather than a wrong answer (insight #6). Two notes: the `amount < 0` guard sitting **above** the memo read is what keeps a `2³¹−1` coin from indexing `mem` out of bounds; and recursion depth reaches `amount / min(coins) = 10⁴` in the worst case (`coins = [1]`), which is fine on LeetCode but is the reason to prefer the iterative table in production. The early `if (amount == 0) return 0;` in the caller is redundant — the base case already handles it.

## Other Approaches
- **Brute force — try every coin at every step** (`f(a) = 1 + min f(a − c)`, no memo). **O(nᵃᵐᵒᵘⁿᵗ/ᵐⁱⁿᶜᵒⁱⁿ) / O(amount)** stack. At `amount = 10⁴` with `coins = [1,2,5]` this is astronomically dead. Write the recurrence, name the bound, then memoize it — the recurrence itself is *already the answer*, which is the point to make.
- **Greedy, largest coin first.** **O(n log n) / O(1)** — and **wrong**: `[1,3,4], amount = 6` → 3 instead of 2 (insight #1). Worth 15 seconds precisely so you can kill it.
- **Top-down memoization** *(the user's (b))* — **O(amount · n) / O(amount)** table + up to **O(amount)** stack. Correct and often the fastest way to *arrive* at the recurrence under pressure; convert to a table if asked about stack depth.
- **Bottom-up table** *(canonical, the user's (a))* — **O(amount · n) / O(amount)**. The expected answer. **No O(1)-space collapse exists** — unlike every earlier problem in this pattern, since the reach-back is `max(coins)`, not 2.
- **BFS / unweighted shortest path** — **O(amount · n) / O(amount)** worst case, but **exits at the first arrival**, so it is much faster when the answer is small relative to `amount` (e.g. `coins = [1, 9999], amount = 9999` finds `1` immediately). Same asymptotics, better constant, and a genuinely different framing (insight #5).
- **DFS with sorted-descending coins + pruning** (`if (curCount + ceil(remaining / c) >= best) prune`) — exponential worst case, but in practice the **fastest accepted** solution on this problem because the bound cuts almost everything. Mention it only as a "when `amount` is huge and `n` is tiny" remark; never lead with it, since you cannot state a polynomial bound.
- **Follow-ups to pre-empt:** *"return the actual coins used"* → keep `from[a] = c` whenever `dp[a]` improves, then walk back from `amount` — O(amount) extra space, no second pass. *"how many **combinations** sum to the amount"* → **518**, `min` → `+` and the **coins loop must be outer** (insight #3). *"count **permutations**"* → **377**, amounts outer. *"can it be made at all"* → the boolean version, i.e. **139 Word Break** with strings in place of coins. *"each coin usable **once**"* → 0/1 knapsack, iterate the amount **downward**. *"coins are perfect squares"* → **279 Perfect Squares** (answer always exists — Lagrange's four-square theorem caps it at 4). *"amount up to 10⁹"* → the pseudo-polynomial table dies; that's a **number-theory / matrix-power** problem, not this one, and saying so is the right answer. *"minimise the **cost** of coins, not the count"* → same table with `+ cost[c]` instead of `+ 1` — i.e. **983 Minimum Cost For Tickets**.

> **The 70 → 322 progression to state out loud:** 70 sets the skeleton (`+`, counts) · 746 swaps the combine to `min` with weights on both branches · 91 **gates** the branches · 198 makes them **asymmetric** · 213 changes the **domain** · 53 changes the **state definition** · 152 changes the **operator's algebra** · 121 changes the **input** · **322 changes what the STATE MEASURES** — it is no longer a position in the input but a **value** (`amount`), the input array becomes the **transition set**, the branching factor grows from 2 to `|coins|`, and with it the two-rolling-variable collapse that closed all eight previous problems **finally dies**. Eight dials: combine operator · weight placement · guard · branch symmetry · domain · state definition · operator algebra · input transform · **and now the state's meaning itself**. Naming which dial a new problem turns *is* the pattern.

## Pitfalls
- **Reaching for greedy.** `[1,3,4], amount = 6` → 3 instead of 2. Non-canonical coin systems have no exchange argument. *The* pitfall.
- **`INT_MAX` as the ∞ sentinel** — `INT_MAX + 1` wraps to `INT_MIN`, which then **wins** every `min` and fills the table with negative garbage. Use **`amount + 1`** (insight #2), or guard the add.
- **Extending an unreachable state** — doing `dp[a-c] + 1` when `dp[a-c]` is the `-1`/∞ marker reports impossible amounts as cheap. Either guard the read (`req != -1`) or make the sentinel so large it can never win a `min`. **Pick one convention and hold it through the whole function** — mixing `-1` and `∞` in one table is where this breaks.
- **Returning `dp[amount]` without translating the sentinel** — `[2], amount = 3` returns `4` instead of `-1`.
- **`-1` used as the memo's "not computed" marker** — collides with the legal answer `-1`, so impossible sub-amounts are recomputed on every visit ⇒ exponential. Manifests as **TLE, not WA** (insight #6). Use `-2`, a separate `visited`, or the ∞ convention.
- **Testing `a - coins[j] >= 0` instead of `coins[j] <= a`** — with `coins[i] ≤ 2³¹−1` the subtraction is inside `int` range only by a hair here, and is a genuine overflow in the general version of this problem (insight #4).
- **Putting the `amount < 0` base **below** the memo lookup** in the recursive form — a coin larger than the amount then indexes the vector negatively. Exactly the [[1-70-climbing-stairs|70]] / [[3-91-decode-ways|91]] guards-before-memo trap, with a real segfault instead of a benign over-read.
- **Forgetting `amount == 0` → `0`** — the empty selection is legal (contrast [[6-53-maximum-subarray|53]], where the empty subarray is forbidden, and matching [[8-121-best-time-to-buy-and-sell-stock|121]], where it's the spec). The `dp[0] = 0` base gives it for free; only hand-rolled early returns get it wrong.
- **Trying to collapse to rolling variables** — the reflex that finished the previous eight problems is **actively wrong here**: `dp[a]` reaches back `max(coins)`, so nothing smaller than the full `O(amount)` table works. *Check the dependency window* still applies — it just returns a different answer this time.
- **Carrying 518's loop-order anxiety here** — for `min` the order is genuinely free; it only matters when the combine is `+` and you're counting (insight #3). Being confidently wrong in *either* direction reads badly.
- **`dp` sized `amount` instead of `amount + 1`** — the answer lives at index `amount`, so the table is one longer than the target. Same off-by-one as [[2-746-min-cost-climbing-stairs|746]]'s "top of the floor".
