# 6. 53. Maximum Subarray (LC 53) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/maximum-subarray/)

**Pattern:** 1D DP — **Kadane's algorithm, which is nothing but the pattern's core skeleton applied to a NEW state definition.** Every problem so far defined `dp[i]` as *"the answer for the prefix `0..i`"*; here that definition **fails**, because the best subarray of a prefix tells you nothing about whether it can be **extended**. The fix — and the whole lesson of this problem — is to define `dp[i]` as **the best subarray that ENDS exactly at `i`**, a *constrained* quantity that composes, and then take a **separate global `max` over all `dp[i]`**. That split — **a local state you can recur on, plus a global answer you accumulate alongside it** — is the single most transferable move in DP, and it is why 53 is the gateway to 152, 121, 918 and the entire "best window ending here" family.
**Trigger:** "**maximum/minimum sum of a contiguous subarray**" — the words **contiguous / subarray / consecutive elements** next to an **optimum**, with **negative numbers present** (if all values were positive the answer is trivially the whole array, and the constraints say `-10⁴ ≤ nums[i]`, which is the problem announcing itself). The tell that it is Kadane and not sliding-window: **negatives** mean the running sum is **not monotonic**, so no two-pointer shrink rule exists — you cannot decide to drop a left element by a local test. The reflex: **"best ending here" + running global max.**

## Problem (1-liner)
Find the **contiguous** subarray with the largest sum and return that sum. The subarray must be **non-empty**.
**Examples:** `[-2,1,-3,4,-1,2,1,-5,4] → 6` (`[4,-1,2,1]` — note it **contains a negative**, which is exactly the point) · `[1] → 1` · `[5,4,-1,7,8] → 23` (the whole array).
**Constraints:** `1 ≤ n ≤ 10⁵`, `-10⁴ ≤ nums[i] ≤ 10⁴`. Max magnitude `10⁵ × 10⁴ = 10⁹ < 2³¹−1 ≈ 2.1×10⁹` ⇒ **`int` fits**, with about 2× headroom. `n = 10⁵` rules out **O(n²)** (10¹⁰ ops) and permits O(n log n), but O(n) exists.
**Edges:** `n == 1` → `nums[0]`, **even if negative** · **all-negative** array → the **largest single element** (`[-3,-1,-2] → -1`), *not* `0` — the empty subarray is **not allowed**, and this is the case every buggy Kadane fails · all-positive → the whole array.

## Idea (1-liner)
`best_ending_here = max(nums[i], best_ending_here + nums[i])` — extend or restart — and take the running `max` of that over all `i`.

## Approach
1. Define **`dp[i]` = the maximum sum of a subarray that ends exactly at index `i`** (so `nums[i]` is **mandatorily** included).
2. Partition by the **last decision**: the subarray ending at `i` either **is just `nums[i]`** (a fresh start) or **extends** the best subarray ending at `i-1`. Disjoint + exhaustive ⇒ `dp[i] = max(nums[i], dp[i-1] + nums[i])`.
3. Base: `dp[0] = nums[0]`.
4. The answer is **`max over all i of dp[i]`** — *not* `dp[n-1]`.
5. The window is **1** (`dp[i]` reads only `dp[i-1]`) ⇒ collapse the table to **one scalar** `cur`, and carry a second scalar `best` for the global max.

> **Load-bearing insight #1 — why the prefix definition BREAKS, and this is the real content of the problem.** For 70/746/91/198, `dp[i] = "answer for prefix 0..i"` worked because the answer for a prefix could be **combined** with the next element. Here it cannot: knowing "the best subarray in `[-2,1,-3]` is `1`" tells you **nothing** about `[-2,1,-3,4]`, because the winning subarray may not touch index `2` and therefore **cannot absorb** `nums[3]`. Contiguity means only a subarray that **reaches the boundary** is extendable. So you constrain the state — *"ending at `i`"* — which restores composability, and pay for it by **losing the answer from the state**, which you buy back with a separate running max. **Say this out loud; it is what the problem tests.** The general rule: *when the natural state doesn't compose, add a constraint that makes it compose, then aggregate the constrained states.*

> **Load-bearing insight #2 — `max(nums[i], dp[i-1] + nums[i])` is EXACTLY "drop a negative prefix".** Factor it: `nums[i] + max(0, dp[i-1])`. So the decision isn't about `nums[i]` at all — it's **"is the baggage I'm carrying helping or hurting?"** If `dp[i-1] < 0`, any subarray running through `i-1` starts at a deficit, and **cutting it away strictly improves** every subarray that continues past it. That is why the reset test is on the **running sum**, never on the current element: a negative element inside a strong run (`[4,-1,2,1]`) is worth keeping; a negative *run* never is. **Confusing "negative element" with "negative running sum" is the #1 conceptual error here.**

> **Load-bearing insight #3 — the all-negative case, and the ORDER of the two lines.** In the reset formulation (`sum += num; best = max(best, sum); if (sum < 0) sum = 0;`) the update **must** come **before** the reset. Reset first and you have silently allowed the **empty** subarray (sum `0`), so `[-3,-1,-2]` returns `0` instead of `-1`. Equivalently: initialise `best = INT_MIN` (or `nums[0]`), **never `0`** — a `0` initialiser is the same bug wearing a different hat. In the `max(nums[i], cur + nums[i])` formulation this is free, because `cur` is never allowed to represent an empty subarray in the first place — which is a decent reason to prefer it.

> **Load-bearing insight #4 — greedy vs DP, and why O(n²) is the trap answer.** The brute force is "every `(i, j)` pair", O(n²) even with prefix sums, and at `n = 10⁵` that is 10¹⁰ operations — **state the bound, then kill it**. Kadane is not a greedy in the exchange-argument sense; it is a DP whose table happens to collapse to one variable. The proof obligation is insight #2 (dropping a negative prefix is never worse), and being able to state it is what separates "I memorised Kadane" from "I derived it".

> **Load-bearing insight #5 — where this generalises.** The `dp[i]` = *"best ending here"* trick reappears verbatim in **152 Maximum Product Subarray** (where you must carry **two** states, `maxEnd` and `minEnd`, because a negative flips them), **121 Best Time to Buy/Sell Stock** (Kadane on the difference array — the two problems are *literally the same problem*), **918 Circular** (`max(Kadane, total − minKadane)`, with the all-negative guard), and the 2D **maximum-sum rectangle** (fix a row pair, compress columns, run Kadane — O(n³)). Recognising "best ending here" as a **state design move**, not an algorithm, is what makes all of those free.

## Code (clean canonical)
```cpp
class Solution {
public:
    int maxSubArray(vector<int>& nums) {
        int cur = nums[0], best = nums[0];        // subarray must be NON-EMPTY

        for (int i = 1; i < nums.size(); i++) {
            cur  = max(nums[i], cur + nums[i]);   // restart  |  extend
            best = max(best, cur);                // answer is the max over ALL i
        }
        return best;
    }
};
```
**TC:** **O(n)** — one pass.  **SC:** **O(1)** — two ints, no table, no stack.
*Seeding both at `nums[0]` and starting the loop at `1` is what makes the non-empty requirement structural rather than a special case; `n == 1` falls out free (the loop never runs).*

## My Solution
**Reset-form Kadane — ✅ correct.**
```cpp
class Solution {
public:
    int maxSubArray(vector<int>& nums) {
        int sum = 0, maxi = INT_MIN;

        for (int num : nums) {
            sum += num;
            maxi = max(maxi, sum);      // ← record BEFORE resetting
            if (sum < 0) sum = 0;       // ← drop a prefix that only hurts
        }

        return maxi;
    }
};
```
**O(n) time, O(1) space.** Verified: ex1 → `6`, ex2 → `1`, ex3 → `23`, `[-3,-1,-2]` → `-1`.

Two things this gets right that most people get wrong, and both are worth naming out loud:
- **`maxi = max(maxi, sum)` sits ABOVE `if (sum < 0) sum = 0;`** — exactly insight #3. Swap those two lines and every all-negative array returns `0`, because the reset lets the empty subarray sneak into the running max. On `[-2,-1,-3]` the correct order gives `-2 → -1 → -1` ⇒ `-1`; the wrong order gives `0`.
- **`maxi = INT_MIN`, not `0`** — the same bug from the other direction. `0` pre-loads the empty subarray as a candidate.

**Refinements:** annotate the reset line (`// a negative running sum can only hurt what follows`) — it's the one line an interviewer will make you justify. `INT_MIN` needs `<climits>`, which LeetCode includes implicitly but a local build may not; `nums[0]` is a portable alternative and arguably states the non-emptiness better. The range-`for` is right — you never index, so there's no off-by-one to make. **The two formulations are mathematically identical** (`cur` in the canonical form equals `sum` *after* the reset in yours); the canonical one carries the invariant "`cur` is always a real non-empty subarray" and so cannot express the empty-subarray bug at all, which is why it's the safer one to write under pressure. Say you know both and why they agree.

**Bottom-up table — the same recurrence with the collapse undone.**
```cpp
class Solution {
public:
    int maxSubArray(vector<int>& nums) {
        int n = nums.size();
        vector<int> dp(n);               // dp[i] = best subarray ENDING at i
        dp[0] = nums[0];
        int best = dp[0];

        for (int i = 1; i < n; i++) {
            dp[i] = max(nums[i], dp[i - 1] + nums[i]);
            best  = max(best, dp[i]);    // NOT dp[n-1]
        }
        return best;
    }
};
```
**TC:** **O(n)**.  **SC:** **O(n)** — the table, which the one-wide dependency window makes pure waste.
*The trap this rung exposes: **returning `dp[n-1]`**. On `[5,4,-1,7,8,-100]`, `dp[n-1] = -77` while the answer is `23`. This is the structural difference from 70/746/91/198 — there the last cell **was** the answer because the state was a prefix optimum; here the state is constrained, so the answer lives in the **aggregate**, not the final cell. If you take one thing from this problem, take that.*

## Other Approaches
- **Brute force, all pairs** — sum every `(i, j)` subarray. **O(n³)** naively, **O(n²)** with a running inner sum or prefix sums. **O(1)/O(n)** space. At `n = 10⁵` that's 10¹⁰ ops — name it, state the bound, kill it.
- **Prefix-sum reformulation** — `answer = max over j of (P[j] − min over i<j of P[i])`, one pass keeping the **running minimum prefix**. **O(n)/O(1)**. This is Kadane in a different coordinate system and is the **cleanest bridge to 121 Best Time to Buy/Sell Stock**, which is *exactly* "max `P[j] − P[i]`, `i < j`". Worth knowing, because some follow-ups (return the indices, or the circular variant) are easier to state this way.
- **Kadane, one pass** *(canonical)* — **O(n)/O(1)**. The expected answer.
- **Divide and conquer** *(the stated follow-up)* — split at `mid`; the answer is `max(bestLeft, bestRight, bestCrossing)`, where `bestCrossing` = **best suffix of the left half + best prefix of the right half**, computed by two linear scans outward from `mid`. Recurrence `T(n) = 2T(n/2) + O(n)` ⇒ **O(n log n)**, **O(log n)** stack. Strictly worse than Kadane, **but know it**: it's the merge rule of a **segment tree** storing `(total, bestPrefix, bestSuffix, best)` per node, which is the only way to answer *"max subarray sum in range `[l, r]`, with point updates"* in O(log n) — and that is the real follow-up behind the "more subtle" hint.
- **Follow-ups to pre-empt:** *"return the subarray, not the sum"* → track `start` at every restart and record `(start, i)` whenever `best` improves; O(n), no extra pass. *"the array is **circular**"* → **918**: `max(Kadane, total − minSubarrayKadane)`, with a **mandatory all-negative guard** (otherwise the second term picks the empty subarray and returns `0`) — the same "ring ⇒ two cases" reflex as [[5-213-house-robber-ii|213]]. *"**product** instead of sum"* → **152**: carry `maxEnd` **and** `minEnd`, because multiplying by a negative swaps them; the single-state Kadane is simply wrong there. *"at most **k** elements"* → sliding window with a monotonic deque over prefix sums, O(n). *"**at least** k elements"* → prefix sums + running min of `P[i−k]`, O(n). *"**2D**, maximum-sum submatrix"* → fix a top/bottom row pair, compress each column to a single sum, run Kadane on the compressed row: **O(rows² × cols)**. *"allow the **empty** subarray"* → answer becomes `max(0, kadane)`, and note that this is exactly the assumption the buggy orderings accidentally make.

> **The 70 / 746 / 91 / 198 / 213 / 53 progression to state out loud:** 70 establishes the two-back window (`+`, counts) · 746 swaps the combine to `min` with a weight on **both** branches · 91 keeps `+` but **gates** the branches · 198 swaps to `max` with **asymmetric** branches · 213 changes the **domain**, not the recurrence · **53 changes the STATE DEFINITION itself** — from *"best over the prefix"* to *"best ending exactly here"* — and therefore is the first problem in the pattern where **the answer is not the last cell of the table**. Combine operator, weight placement, guard, domain, **state definition**: five dials, and naming which one a new problem turns *is* the pattern.

## Pitfalls
- **Initialising `maxi = 0`** (or resetting before recording) — *the* signature bug: it admits the **empty** subarray, so every all-negative array returns `0` instead of the largest element. Use `INT_MIN` or `nums[0]`, and record before you reset.
- **Returning `dp[n-1]` in the table form** — the state is *"ending at `i`"*, so the answer is the **max over all cells**, never the last one. The structural break from 198/213.
- **Resetting on a negative ELEMENT instead of a negative RUNNING SUM** — `[4,-1,2,1]` proves a negative element can belong to the optimum. The test is on the accumulated sum.
- **Defining `dp[i]` as "best subarray within `0..i`"** — it doesn't compose, because the winner may not reach the boundary and so cannot be extended. This is the whole reason for the constrained state.
- **Reaching for two pointers / sliding window** — negatives make the running sum non-monotonic, so there is no valid shrink rule. Sliding window needs monotonicity; Kadane doesn't.
- **Settling for O(n²) prefix sums** — correct but TLE at `n = 10⁵`; state the bound out loud before you write it.
- **Reflexive `long long`** — `10⁵ × 10⁴ = 10⁹` fits in `int`. State the bound instead of guessing. *(But do reach for it in **152**, where products explode.)*
- **Forgetting the `n == 1` case** — it's free in both canonical forms, but only because they seed from `nums[0]`; an implementation that starts from an "empty" state has to special-case it.
- **Carrying single-state Kadane into 152** — products need `maxEnd` **and** `minEnd`; the habit is the trap.
- **In the D&C version, computing the crossing sum by re-scanning the whole range** — it must be two outward scans from `mid` (`O(n)` total), or the recurrence degrades.
