# 7. 152. Maximum Product Subarray (LC 152) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/maximum-product-subarray/)

**Pattern:** 1D DP — **Kadane with a TWO-STATE "ending here", because the combine operator is no longer monotonic.** [[6-53-maximum-subarray|53]] taught the state-design move: define `dp[i]` = *"best subarray **ending exactly** at `i`"* and aggregate a separate global max. 152 keeps that move **verbatim** and breaks a different assumption — the one nobody notices they were relying on. Under `+`, "bigger input ⇒ bigger output": the best sum ending at `i` can only ever be built from the **best** sum ending at `i-1`. Under `×` that collapses, because **a negative multiplier reverses the order** — the *most negative* product ending at `i-1` becomes the *largest* product ending at `i` the instant it meets a negative number. So a single state is not just suboptimal, it is **provably insufficient**: you must carry **`maxEnd` and `minEnd` together**, and **swap them on a negative**. The transferable lesson: *when the combine operator is not order-preserving, the state must carry both extremes of the range it can be pushed to.*
**Trigger:** "**maximum PRODUCT of a contiguous subarray**" — the word **product** where 53 said sum, plus **negatives and zeros in the constraints** (`-10 ≤ nums[i] ≤ 10`, so both are guaranteed present). The tell that single-state Kadane is wrong: **an even count of negatives makes a huge positive**, i.e. `[-2,-3]` beats both of its parts, so the running optimum can *jump up from below*. Reflex: **track the min alongside the max, and remember that a `0` hard-resets both.**

## Problem (1-liner)
Find the **contiguous, non-empty** subarray with the largest **product** and return that product.
**Examples:** `[2,3,-2,4] → 6` (`[2,3]`; the answer is **not** `[2,3,-2,4] = -48`) · `[-2,0,-1] → 0` (**not** `2` — `[-2,-1]` is **not contiguous**, the `0` sits between them) · `[-2,3,-4] → 24` (the whole array — **two negatives cancel**, which is precisely why one state fails) · `[0,2] → 2`.
**Constraints:** `1 ≤ n ≤ 2×10⁴`, `-10 ≤ nums[i] ≤ 10`, and the problem **guarantees every subarray product fits in a 32-bit int** — read that clause out loud, it is the licence to use `int`. *Without* it, `10^(2×10⁴)` would need bignums, so **the guarantee is doing real work**; say so, then use `int`.
**Edges:** `n == 1` → `nums[0]`, **even if negative or zero** · **zeros** split the array into independent segments and must reset the running state · **all-negative** `[-2,-3,-4]` → `12` (an even prefix/suffix wins) · a **single negative** `[-3]` → `-3`, since empty is not allowed · leading/trailing zeros `[0,-3,0]` → `0`.

## Idea (1-liner)
Carry **both** `maxEnd` and `minEnd` for subarrays ending at `i`; on a **negative `nums[i]` swap them first**, then `maxEnd = max(nums[i], maxEnd*nums[i])`, `minEnd = min(nums[i], minEnd*nums[i])`, and take a running global max of `maxEnd`.

## Approach
1. Define **two** states: `maxEnd[i]` = the **largest** product of a subarray ending exactly at `i`, and `minEnd[i]` = the **smallest** (most negative) such product.
2. Partition by the **last decision**, same as 53: the subarray ending at `i` is either **just `nums[i]`** (restart) or **extends** something ending at `i-1`.
3. Because `×` can flip sign, the extension candidates are **both** `maxEnd[i-1] * nums[i]` **and** `minEnd[i-1] * nums[i]`:
   `maxEnd[i] = max(nums[i], maxEnd[i-1]*nums[i], minEnd[i-1]*nums[i])`, and `minEnd[i]` is the same three candidates under `min`.
4. Base: `maxEnd[0] = minEnd[0] = nums[0]`. Answer: **`max over all i of maxEnd[i]`** — never the last cell.
5. Window is 1 ⇒ collapse to **two scalars** — but **stage the old `maxEnd` in a temporary**, because `minEnd` still needs it.

> **Load-bearing insight #1 — why one state is not merely weaker but WRONG.** Kadane's correctness under `+` rests on a monotonicity argument: `a > b ⇒ a + x > b + x`, so the best predecessor stays the best successor and it is safe to throw `b` away. Multiplication has **no such guarantee**: `x < 0` reverses the inequality outright. Concretely on `[-2,3,-4]`, after index 1 the best-ending-here is `3` and the worst is `-6`; at index 2 (`-4`) the winner is `-6 × -4 = 24`, produced **entirely by the state a single-state Kadane discarded**. So `minEnd` is not a heuristic or an optimisation — it is the **other half of the reachable range**, and under a sign-flipping operator you must carry the whole interval `[minEnd, maxEnd]` because the multiplier decides which end becomes the new top. **This is the sentence the problem is testing.**

> **Load-bearing insight #2 — the swap, and the temporary that everyone forgets.** `if (nums[i] < 0) swap(maxEnd, minEnd);` before the update is just insight #1 made mechanical: a negative multiplier maps the top of the interval to the bottom. If you instead write the three-candidate `max`/`min` form, the swap is implicit — but then **`maxEnd` must be saved before it is overwritten**, or `minEnd` is computed from the *new* `maxEnd` and the whole thing silently rots. `int prevMax = maxEnd;` costs one line and removes an entire class of bug. *(Same "stage the new value in a temporary" discipline as the rolling variables in [[1-70-climbing-stairs|70]] — this pattern keeps charging for it.)*

> **Load-bearing insight #3 — zero is a third case hiding in plain sight.** `0` is neither positive nor negative and it **annihilates**: any subarray containing it has product `0`. Both canonical forms handle it for free — `max(nums[i], …)` and `min(nums[i], …)` include the **restart** candidate, so at a zero both states become `0`, and at the *next* element the restart candidate dominates the two `0 × nums[i]` products. The zero effectively **partitions the array into independent segments**, and `0` itself is always a legitimate answer candidate (Example 2 returns `0`). **The version that breaks is the reset-form one that resets to `1` without recording first** — see the pitfalls.

> **Load-bearing insight #4 — the prefix/suffix trick, and why it is genuinely correct.** The optimal subarray must be **bounded by zeros or by the array ends** (it can never contain a `0` unless the answer *is* `0`). Inside one zero-free segment, the product of the whole segment is either positive — in which case the whole segment is the best — or negative, in which case **exactly one negative must be dropped**, and dropping it means cutting at that negative, leaving either a **prefix** or a **suffix** of the segment. So scanning **running prefix products left→right and running suffix products right→left**, resetting each to `1` at a zero, is **guaranteed to see the answer**. That is the user's solution, and it is a real, quotable proof — not a coincidence.

> **Load-bearing insight #5 — where 53 and 152 diverge, in one line.** 53 changed the **state definition** (prefix optimum → ending-here). 152 changes the **combine operator's algebra** (from a monotone group to one with sign-flips and an annihilator), and the state has to widen from a **point** to an **interval** in response. Combine operator · weight placement · guard · domain · state definition · **operator algebra**: six dials, and naming which one a new problem turns *is* the pattern.

## Code (clean canonical)
```cpp
class Solution {
public:
    int maxProduct(vector<int>& nums) {
        int maxEnd = nums[0], minEnd = nums[0], best = nums[0];

        for (int i = 1; i < nums.size(); i++) {
            int x = nums[i];
            if (x < 0) swap(maxEnd, minEnd);          // a negative flips the interval

            maxEnd = max(x, maxEnd * x);              // restart | extend
            minEnd = min(x, minEnd * x);              // the other half of the range

            best = max(best, maxEnd);                 // answer is the max over ALL i
        }
        return best;
    }
};
```
**TC:** **O(n)** — one pass.  **SC:** **O(1)** — three ints.
*The explicit `swap` makes the temporary unnecessary and states insight #1 in code. Seeding all three at `nums[0]` makes non-emptiness structural and gives `n == 1` for free.*

**Three-candidate form** (no swap; needs the temporary — this is the one that bites):
```cpp
int prevMax = maxEnd;                                  // ← MUST stage it
maxEnd = max({x, prevMax * x, minEnd * x});
minEnd = min({x, prevMax * x, minEnd * x});
```

## My Solution
**Prefix × suffix sweep in a single loop — ✅ correct, and genuinely clever.**
```cpp
class Solution {
public:
    int maxProduct(vector<int>& nums) {
        int n = nums.size(), maxi = INT_MIN, leftP = 1, rightP = 1;

        for (int i = 0; i < n; i++){
            leftP  = leftP  * nums[i];          // prefix product, left → right
            rightP *= nums[n - 1 - i];          // suffix product, right → left
            maxi = max(leftP, max(rightP, maxi));
            if (rightP == 0) rightP = 1;        // ← reset AFTER recording
            if (leftP  == 0) leftP  = 1;        // (zero already counted as a candidate)
        }
        return maxi;
    }
};
```
**O(n) time, O(1) space.** Verified: `[2,3,-2,4] → 6` · `[-2,0,-1] → 0` · `[-2,3,-4] → 24` · `[-3] → -3` · `[0,2] → 2`.

Why it works — and this is worth being able to defend, because it looks like a trick: by insight #4, the optimal subarray is a **prefix or a suffix of some zero-bounded segment**. The left sweep enumerates every prefix of the current segment, the right sweep every suffix, and the `if (… == 0) … = 1` lines are what make "segment" work — they restart the running product at each zero. Both sweeps run in **one** loop over the same index, so it is one pass, not two.

Two things this gets right that the equivalent buggy versions get wrong, both inherited straight from [[6-53-maximum-subarray|53]]:
- **`maxi = max(...)` sits ABOVE the two resets** — so a genuine `0` product is recorded as a candidate before the state is reset to `1`. Swap the order and `[-2,0,-1]` returns `-1` instead of `0`. Exactly the record-then-reset discipline from 53, with `1` playing the role `0` played there.
- **`maxi = INT_MIN`, not `1`** — seeding with `1` pre-loads the **empty** subarray, so `[-3]` would return `1`. Same bug, different identity element.

**Refinements:** `INT_MIN` needs `<climits>` (implicit on LeetCode, not necessarily locally); `nums[0]` is the portable seed and states non-emptiness better. The `leftP = leftP * nums[i]` line should match the `*=` on the next line for symmetry. Add the one comment an interviewer will demand — `// optimum is a prefix or suffix of a zero-free segment` — because without it the reset-to-`1` looks like a hack. **Trade-off to state out loud:** this form is shorter and has no swap-and-temporary trap, but the two-state Kadane is the one that **generalises** (it is the same shape as the "carry both extremes" fix in many other problems) and it extends cleanly to "return the indices". Know both; lead with the two-state form, then offer this as "there's also a neat prefix/suffix argument".

**Bottom-up table — the same recurrence with the collapse undone.**
```cpp
class Solution {
public:
    int maxProduct(vector<int>& nums) {
        int n = nums.size();
        vector<int> mx(n), mn(n);            // best / worst product ENDING at i
        mx[0] = mn[0] = nums[0];
        int best = nums[0];

        for (int i = 1; i < n; i++) {
            int x = nums[i];
            mx[i] = max({x, mx[i-1] * x, mn[i-1] * x});
            mn[i] = min({x, mx[i-1] * x, mn[i-1] * x});
            best  = max(best, mx[i]);        // NOT mx[n-1]
        }
        return best;
    }
};
```
**TC:** **O(n)**.  **SC:** **O(n)** — two tables the one-wide window makes pure waste.
*Useful as the derivation step on a whiteboard: write this, point at the window, collapse it. Note the table form has **no** temporary bug, because `mx[i-1]` is a different cell from `mx[i]` — the trap is created by the collapse, which is exactly why you mention the temporary when you collapse.*

## Other Approaches
- **Brute force, all subarrays** — multiply out every `(i, j)`. **O(n³)** naive, **O(n²)** with a running inner product. **O(1)** space. At `n = 2×10⁴` that is 4×10⁸ products — borderline-to-TLE; name the bound, then kill it.
- **Prefix products + division** — the `+`-world trick (`product(i..j) = P[j] / P[i-1]`) that **does not transfer**: any zero destroys the prefix chain and there is no "subtract" inverse across it. Mention it only to reject it — knowing *why* division fails here is a small credibility win.
- **Two-state Kadane, one pass** *(canonical)* — **O(n)/O(1)**. The expected answer.
- **Prefix/suffix sweep** *(the user's)* — **O(n)/O(1)**. Equally optimal, shorter, rests on the zero-segment argument in insight #4.
- **Split on zeros, then count negatives per segment** — for each zero-free segment: if it has an **even** number of negatives, the whole segment wins; otherwise take the better of *(segment up to just before the last negative)* and *(segment just after the first negative)*. **O(n)/O(1)**. The most *explanatory* solution and the cleanest thing to say if the interviewer asks "why is prefix-or-suffix enough?".
- **Divide and conquer** — possible (`max(left, right, crossing)` with best-suffix/best-prefix products, carrying **both** extremes across the merge) at **O(n log n)**, and it is the segment-tree merge rule if the follow-up adds updates. Strictly worse standalone; know it exists.
- **Follow-ups to pre-empt:** *"return the subarray, not the product"* → track a `start` at each restart in the two-state form and record `(start, i)` when `best` improves. *"no 32-bit guarantee"* → products blow past `long long` too, so switch to **logs** — `log|x|` turns `×` into `+` and lets you run plain Kadane over magnitudes, with the **sign handled separately** by the negative-count argument (zeros need their own case, and floating point costs you exactness — say the trade-off). *"maximum product of any **k** elements"* / *"of a **subsequence**"* → not this problem at all: sort and pair off the extremes, greedy, **O(n log n)**. *"**circular** array"* → run the segment argument on the doubled array, or handle the wrap as a separate case, the same "ring ⇒ two cases" reflex as [[5-213-house-robber-ii|213]]. *"count subarrays with **positive** product"* → a running parity-of-negatives count, O(n).

## Pitfalls
- **Carrying single-state Kadane over from 53** — *the* signature error, and the one 53's own pitfall list warns about. `[-2,3,-4]` returns `3` instead of `24`. Under `×` you must carry **both** extremes.
- **Overwriting `maxEnd` before `minEnd` reads it** — in the three-candidate form, `minEnd` would then be computed from the *new* `maxEnd`. **Stage `prevMax` in a temporary**, or use the explicit `swap` form where the problem cannot arise.
- **Resetting before recording** (prefix/suffix form) — `maxi = max(...)` must come **above** `if (p == 0) p = 1;`, or `[-2,0,-1]` returns `-1` instead of `0`. The identical record-then-reset trap as 53, with a different identity element.
- **Seeding the answer with `1` (or `0`)** — `1` admits the **empty** subarray (`[-3] → 1`); `0` breaks all-negative inputs. Seed with `INT_MIN` or `nums[0]`.
- **Returning the last cell in the table form** — the state is *"ending at `i`"*, so the answer is the **max over all cells**. Inherited straight from 53.
- **Forgetting zeros entirely** — they annihilate, they split the array into independent segments, and `0` is itself a valid answer (Example 2).
- **Assuming "all negatives ⇒ answer is negative"** — `[-2,-3,-4] → 12`. An even-length run of negatives is a *large positive*.
- **Reaching for prefix products with division** — no inverse across a zero; the `+`-world trick does not transfer.
- **Ignoring the 32-bit guarantee** — it is stated *for you*; quote it to justify `int` instead of reflexing to `long long`. (The opposite of 53, where you justified `int` by computing the bound yourself.)
- **Thinking the prefix/suffix sweep is two passes** — it is one loop reading from both ends, `O(n)` total.
