# 5. 39. Combination Sum (LC 39) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/combination-sum/)

**Pattern:** Backtracking — **combinations with unlimited reuse**; the problem where the recursion index stays put (`i`, not `i + 1`)
**Trigger:** "all combinations summing to **target**, each number may be used an **unlimited** number of times, candidates are **distinct**" → [[1-78-subsets|Subsets]] template with **two deltas**: recurse with **`i`** (reuse) instead of `i + 1`, and record at the **`remain == 0`** base case instead of at every node.

## Problem (1-liner)
Given **distinct** `candidates` and a `target`, return every **unique multiset** of candidates summing to `target`; each candidate may be reused **unlimited** times, any order.
**Examples:** `[2,3,6,7], t=7 → [[2,2,3],[7]]` · `[2,3,5], t=8 → [[2,2,2,2],[2,3,3],[3,5]]` · `[2], t=1 → []`.
**Constraints:** `1 ≤ n ≤ 30`, `2 ≤ candidates[i] ≤ 40`, **all distinct**, `1 ≤ target ≤ 40`, and fewer than 150 answers.
**Edge case:** empty output is legal (`[2], t=1`). Note `candidates[i] ≥ 2` — this is the constraint that makes "recurse with `i`" **terminate**; a `0` in the input would loop forever.

## Idea (1-liner)
Two combinations differ only by the **frequency** of each value, so order inside a combination is meaningless — fix a canonical order by only ever moving the index **forward**, and allow reuse by recursing at the **same** index. Depth is bounded because every pick shrinks `remain` by at least `min(candidates)`.

## Approach
1. Sort `candidates` (optional for correctness — the input is distinct — but it enables the `break` prune).
2. Loop `i` from `start`; if `candidates[i] > remain`, **`break`** (everything after is bigger too).
3. **Choose:** `temp.push_back(candidates[i])`.
4. **Explore:** `helper(i, remain - candidates[i])` — **`i`, not `i + 1`**, that single character *is* "unlimited reuse".
5. **Un-choose:** `temp.pop_back()`.
6. Base case `remain == 0` → record `temp`. (`remain < 0` can't happen if you prune in step 2.)

> **Load-bearing insight:** the `start` index is not about "which elements are left" — it's a **canonical-order device**. By never going backwards you guarantee each multiset is emitted with its values in non-decreasing index order, i.e. **exactly once**. That's why no `set`, no sort-based dedup and no `used[]` are needed here even though the same value appears many times in one answer — the duplicates live *inside* a combination, not *across* combinations.

## Code (clean canonical)
```cpp
class Solution {
    vector<vector<int>> ans;
    vector<int> temp;

    void helper(int start, int remain, vector<int>& c) {
        if (remain == 0) { ans.push_back(temp); return; }

        for (int i = start; i < (int)c.size(); ++i) {
            if (c[i] > remain) break;        // sorted ⇒ the rest are bigger too
            temp.push_back(c[i]);            // choose
            helper(i, remain - c[i], c);     // explore — `i` ⇒ reuse allowed
            temp.pop_back();                 // un-choose
        }
    }
public:
    vector<vector<int>> combinationSum(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end());   // enables the break-prune
        helper(0, target, candidates);
        return ans;
    }
};
```
**TC:** **O(N^(T/M))** where `M = min(candidates)` — the tree is `N`-ary and at most `T/M` deep; each leaf copies `O(T/M)`. **SC:** **O(T/M)** auxiliary (`temp` + recursion depth). Output separate.
**Say it as:** "exponential in `target/min`, and that's inherent — the output itself is exponential."

## My Solution
```cpp
class Solution {
private:
    vector<vector<int>> ans;
    vector<int> temp;
    int sum = 0;
    void helper(int index, int target, vector<int>& nums) {
        if (index >= nums.size() || sum > target) return;
        if (sum == target) { ans.push_back(temp); return; }

        helper(index + 1, target, nums);      // not pick
        temp.push_back(nums[index]);          // pick
        sum += nums[index];
        helper(index, target, nums);          // stay at index ⇒ reuse
        temp.pop_back();
        sum -= nums[index];
    }
public:
    vector<vector<int>> combinationSum(vector<int>& candidates, int target) {
        helper(0, target, candidates);
        return ans;
    }
};
```
**Correct** — brute-verified against a reference recursion on 3,000 random inputs (n ≤ 4, values 2–9, target ≤ 15): **0 mismatches**. This is the **pick/not-pick** shape of the same tree: not-pick advances the index, pick stays — exactly the `i` vs `i + 1` distinction, expressed as two calls instead of a loop.

**Refinement 1 — the base-case order is fragile.** `index >= nums.size()` is checked **before** `sum == target`, so an answer completed at the last index would be dropped. It survives only by luck of construction: `sum` can reach `target` **only** immediately after a pick, and a pick recurses with the *same* (still-valid) `index`. Flip them so the success check is unconditional:
```cpp
if (sum == target) { ans.push_back(temp); return; }
if (index >= (int)nums.size() || sum > target) return;
```
**Refinement 2 — `sum` as a member is stateful.** `ans`, `temp` and `sum` persist on the object, so a second call to `combinationSum` returns garbage. Pass the **remaining** target down instead — one less mutable thing to unwind, and `remain == 0` reads better than `sum == target`:
```cpp
helper(index + 1, remain, nums);
temp.push_back(nums[index]);
helper(index, remain - nums[index], nums);
temp.pop_back();
```
**Refinement 3 — prefer the loop form in an interview.** The loop template is a one-line delta away from [[6-40-combination-sum-ii|40]] and [[7-216-combination-sum-iii|216]]; the pick/not-pick shape makes the "skip equal siblings" dedup step much clumsier (you must decline the element's **whole run**, and `continue` won't even compile — the same trap as in [[2-90-subsets-ii|90]]).

## Other Approaches
- **Generate every subset of a padded array, then filter** *(brute)* — replicate each candidate `target/c[i]` times, run [[1-78-subsets|78]], keep the sums that hit `target`, dedupe with a `set<vector<int>>`. **O(2^(N·T/M) · T)**. Only worth one sentence: "correct but does exponentially more work than the answer count."
- **Pick / not-pick recursion** *(the solution above)* — same complexity as canonical, no loop, no `start`. Fine, but doesn't upgrade to the dedup variants.
- **Loop-from-`start` + recurse with `i`** *(canonical)* — **O(N^(T/M))** / **O(T/M)**. The default. Add `sort` + `if (c[i] > remain) break;` and the tree collapses dramatically on adversarial inputs like `[2,3,...,40], t=40`.
- **Sort descending + prune** *(micro-opt)* — bigger values first shrinks `remain` faster, so branches die sooner. Same asymptotics, noticeably fewer nodes. Mention it only if asked to optimise further.
- **DP if the question changes to *count* / *shortest*** — the moment they ask "**how many** combinations" or "**fewest coins**", stop backtracking: this is **unbounded knapsack** (Coin Change / Coin Change II), `dp[t] += dp[t - c]` in **O(N·T)**. The tell: enumeration is only mandatory because they want the **combinations themselves**. Note the loop order — `for c: for t` counts **combinations**, `for t: for c` counts **permutations** (that's LC 377).

## Pitfalls
- **`helper(i + 1, ...)` instead of `helper(i, ...)`** — silently solves the *no-reuse* problem (you'd get `[[7]]` instead of `[[2,2,3],[7]]`). The single most common slip here.
- **`helper(start, ...)` instead of `helper(i, ...)`** — the other direction: the index never advances, so you re-emit permutations of the same multiset.
- **Deduping with a `set`** — unnecessary. Distinct input + forward-only index ⇒ uniqueness is **structural**. Reaching for a `set` signals you don't see why the template works.
- **Checking `index >= n` before the success case** — see Refinement 1. Works here by accident; breaks the moment you refactor.
- **Assuming `candidates[i] ≥ 2` is decoration** — it's the termination proof. If a `0` were allowed, `helper(i, remain)` recurses forever; you'd have to special-case it.
- **Mutable member state (`sum`, `ans`, `temp`)** — fine on LeetCode, wrong in a class you call twice. Prefer parameters.
- **Quoting the complexity as O(2ⁿ)** — it's **O(N^(T/M))**; `n` doesn't bound the depth here because elements repeat.
- **Inherited from the pattern:** missing `pop_back()`; recording at the wrong place (every node ⇒ you'd emit partial sums); passing the buffer by value.
