# 6. 40. Combination Sum II (LC 40) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/combination-sum-ii/)

**Pattern:** Backtracking — **combinations, each element used once, input has duplicates**; the problem that fuses [[5-39-combination-sum|39]]'s target-sum recursion with [[2-90-subsets-ii|90]]'s dedup guard
**Trigger:** "all **unique** combinations summing to **target**, each number may be used **only once**, candidates **may contain duplicates**" → [[5-39-combination-sum|39]] with `i + 1` instead of `i`, **plus** `sort` + `if (i > start && c[i] == c[i-1]) continue;`.

## Problem (1-liner)
Given `candidates` (**duplicates allowed**) and a `target`, return every **unique** combination summing to `target`, where each **array position** may be used at most once.
**Examples:** `[10,1,2,7,6,1,5], t=8 → [[1,1,6],[1,2,5],[1,7],[2,6]]` · `[2,5,2,1,2], t=5 → [[1,2,2],[5]]` · `[2,2], t=3 → []`.
**Constraints:** `1 ≤ n ≤ 100`, `1 ≤ candidates[i] ≤ 50`, `1 ≤ target ≤ 30`.
**Edge case:** empty output is legal. Note `[1,1,6]` **is** valid — two `1`s exist in the input; duplicates *inside* an answer are allowed, duplicate *answers* are not.

## Idea (1-liner)
Same forward-only index that makes combinations canonical in [[5-39-combination-sum|39]], but advance it (`i + 1`) so each position is consumed once — then, because equal values build the **same multiset**, sort and let only the **first copy at each depth** take the branch.

## Approach
1. **Sort** `candidates` — mandatory here (not optional like in 39): it makes equal values adjacent so the guard can see them, and enables the `break` prune.
2. Loop `i` from `start`. **Skip equal siblings:** `if (i > start && c[i] == c[i-1]) continue;`.
3. **Prune:** `if (c[i] > remain) break;` — sorted ⇒ everything after is bigger too.
4. **Choose** `c[i]` → **explore** `helper(i + 1, remain - c[i])` → **un-choose** `pop_back()`.
5. Base case `remain == 0` → record `temp`.

> **Load-bearing insight:** `n ≤ 100` with `target ≤ 30` is a trap deliberately set for the `set<vector<int>>` solution. The `set` dedups the **output** but never prunes the **tree** — on `[1]×100, t=30` there is exactly **one** answer that the recursion reaches C(100,30) ≈ 3×10²⁵ different ways. The guard in step 2 dedups *during* the search, collapsing that to a single path. **Dedup must happen in the recursion, not after it.**

## Code (clean canonical)
```cpp
class Solution {
    vector<vector<int>> ans;
    vector<int> temp;

    void helper(int start, int remain, vector<int>& c) {
        if (remain == 0) { ans.push_back(temp); return; }

        for (int i = start; i < (int)c.size(); ++i) {
            if (i > start && c[i] == c[i - 1]) continue;  // equal sibling ⇒ same subtree
            if (c[i] > remain) break;                     // sorted ⇒ rest are bigger

            temp.push_back(c[i]);                         // choose
            helper(i + 1, remain - c[i], c);              // explore — i + 1 ⇒ used once
            temp.pop_back();                              // un-choose
        }
    }
public:
    vector<vector<int>> combinationSum2(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end());       // duplicates must be adjacent
        helper(0, target, candidates);
        return ans;
    }
};
```
**TC:** **O(2ⁿ · k)** worst case (`k` = answer length) — but the dedup + `break` prune collapse the real search to roughly the number of distinct valid combinations. **SC:** **O(n)** auxiliary (`temp` + stack); output separate.
**Say it as:** "bounded by 2ⁿ subsets, but the equal-sibling skip means we never walk the same multiset twice."

## My Solution
```cpp
class Solution {
    set<vector<int>> st;
    vector<int> temp;

    void helper(int index, int target, vector<int>& nums) {
        if (target == 0) { st.insert(temp); return; }
        if (index >= nums.size()) return;

        helper(index + 1, target, nums);            // not pick
        if (target - nums[index] >= 0) {
            temp.push_back(nums[index]);            // pick
            helper(index + 1, target - nums[index], nums);
            temp.pop_back();
        } else return;
    }
public:
    vector<vector<int>> combinationSum2(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end());
        helper(0, target, candidates);
        return vector<vector<int>>(st.begin(), st.end());
    }
};
```
**Output is correct — but it TLEs**, and the reason is the whole point of the problem. The `set` is a **post-filter**: every one of the 2ⁿ subsets is still enumerated, and identical combinations are re-derived thousands of times before being thrown away. Adversarial input inside the constraints: `[1]×100, target = 30` → one answer, **C(100,30) ≈ 3×10²⁵** leaves. Even `[2]×100, t=30` gives C(100,15) ≈ 2.5×10¹⁷.

**Refinement 1 — prune duplicates in the tree.** In the pick/not-pick shape the fix is on the **not-pick** branch: declining a value means declining its **entire run**, otherwise the second copy rebuilds the same subtree.
```cpp
// pick
temp.push_back(nums[index]);
helper(index + 1, remain - nums[index], nums);
temp.pop_back();
// not pick — jump past every duplicate of nums[index]
int next = index;
while (next < (int)nums.size() && nums[next] == nums[index]) ++next;
helper(next, remain, nums);
```
Then `set<vector<int>>` → `vector<vector<int>>` and the `O(k log N)` insert disappears too.

**Refinement 2 — the `else return;` is dead weight.** By the time it runs both branches are already done, so it returns from a frame that was returning anyway. In the loop form the same intent becomes a real prune: `if (c[i] > remain) break;`.

**Refinement 3 — prefer the loop shape in an interview.** `i > start && c[i] == c[i-1]` is one line and is the *same* line you wrote in [[2-90-subsets-ii|90]]; the skip-the-whole-run version is three lines and is easy to get wrong under pressure (`continue` doesn't even compile there — no loop).

## Other Approaches
- **All subsets, then filter + dedup** *(brute)* — run [[1-78-subsets|78]], keep the ones summing to `target`, push into `set<vector<int>>`. **O(2ⁿ · n log n)**. Your solution is this with early pruning; both die on `n = 100`.
- **Loop-from-`start` + `i + 1` + equal-sibling skip** *(canonical)* — the answer above. Only one line differs from [[5-39-combination-sum|39]] (`i` → `i + 1`) and one line from [[2-90-subsets-ii|90]] (record at `remain == 0` instead of every node).
- **Frequency map** *(dedup by construction)* — compress to `(value, count)` pairs, then at each level pick how many copies `j ∈ [0, count]` of the current distinct value to take. Never *creates* a duplicate, so no guard is needed; branching factor is the number of **distinct** values. Same asymptotics, nicer if the input is heavily repeated (`[1]×100`) — worth naming as the follow-up optimisation.
- **`used[]` array instead of the index guard** — `if (i > 0 && c[i] == c[i-1] && !used[i-1]) continue;`, the [[4-47-permutations-ii|47]] rule. Correct but pointless here: `used[]` only earns its keep when order matters and you loop from 0.
- **DP if the question changes to *count*** — "how many subsets sum to `target`" with each item used once is **0/1 knapsack**, `for item: for t descending: dp[t] += dp[t - c]`, **O(n·T)**. The tell, as always: enumeration is mandatory only because they want the combinations themselves.

## Pitfalls
- **Deduping with a `set` instead of in the recursion** — the bug that produced the TLE. The `set` fixes the *output*, not the *work*.
- **`i > 0` instead of `i > start`** — kills the first copy at every depth, so `[1,1,6]` never forms. Always `start`: it's "first choice **at this depth**".
- **Forgetting to `sort`** — the guard compares `c[i]` to `c[i-1]`, which is meaningless unless equal values are adjacent. Input can be `[2,5,2,1,2]`.
- **`helper(i, ...)` instead of `helper(i + 1, ...)`** — silently solves LC 39 (unlimited reuse) instead.
- **Validating the guard only on `[1,1,2]`** — too forgiving. Test a duplicate pair that is **non-adjacent before sorting** (`[2,5,2,1,2]`) — the same lesson as [[4-47-permutations-ii|47]].
- **`continue` vs `break`** — the dedup skip is `continue` (a later, larger value may still work); the size prune is `break` (nothing after can work). Swapping them silently loses answers.
- **Inherited from the pattern:** missing `pop_back()`; recording at every node instead of at `remain == 0`; passing the buffer by value.
