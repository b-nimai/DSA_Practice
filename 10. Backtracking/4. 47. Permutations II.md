# 4. 47. Permutations II (LC 47) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/permutations-ii/)

**Pattern:** Backtracking — **permutations with duplicates**; the problem that proves the dedup guard is **template-specific**, not universal
**Trigger:** "all **unique** permutations, input **may contain duplicates**" → [[3-46-permutations|Permutations]] + a dedup rule — but **which** rule depends on your template. `used[]` shape ⇒ **sort + `!used[i-1]`**. Swap shape ⇒ **per-level `unordered_set` of values**, no sort. Mixing them up is the whole trap.

## Problem (1-liner)
Given `nums` that **may contain duplicates**, return all possible **unique** permutations, any order.
**Examples:** `[1,1,2] → [[1,1,2],[1,2,1],[2,1,1]]` (**3**, not 3! = 6) · `[1,2,3] → 6` (no dups ⇒ plain 46).
**Constraints:** `1 ≤ n ≤ 8`, `-10 ≤ nums[i] ≤ 10`. Input is **not sorted** — `[1,2,3,2]` is legal, and that exact input breaks the naive guard (below).
**Edge case:** all-identical input `[2,2,2]` → **1** permutation. Answer count is **n! / Π(count(v)!)** — `[1,1,2]` → 3!/2! = 3. Interviewers ask for this formula.

## Idea (1-liner)
Two equal values are **interchangeable**, so swapping which copy you place produces a byte-identical arrangement. Kill it by fixing a **canonical choice per slot**: for each position, try each **distinct value** at most once. Everything below is just two different ways to answer *"have I already tried this value in this slot?"* — by **position** (sorted array + adjacency) or by **value** (a set).

## Approach
**Shape A — `used[]` + sort (canonical):**
1. **`sort(nums)`** — mandatory; the guard is an adjacency check.
2. Base case `temp.size() == n` → record.
3. Loop `i` from 0: `if (used[i]) continue;`
4. **`if (i > 0 && nums[i] == nums[i-1] && !used[i-1]) continue;`**
5. Choose → recurse → un-choose **both** (`used[i] = false`, `pop_back()`).

**Shape B — swap + per-level set (the user's):**
1. Declare **`unordered_set<int> seen;` inside the function** — one per frame.
2. Loop `i` from `index`: `if (!seen.insert(nums[i]).second) continue;`
3. `swap(nums[index], nums[i])` → recurse `index+1` → **swap back**.
4. **No sort needed** — the set tracks values, not positions.

> **Load-bearing insight:** the 90/47 guard `nums[i] == nums[i-1]` is a **positional** rule that is only valid **while the array stays sorted**. Shape B *mutates the array* — `swap` drops the old `nums[index]` back down **into position `i`**, right in the middle of the remaining pool, where it can land **between two equal values**. From that moment the adjacency check is comparing the wrong neighbour. Mutating template ⇒ you need a **value** rule (a set), not a positional one.

## Code (clean canonical)
```cpp
class Solution {
    vector<vector<int>> ans;
    vector<int> temp;
    vector<bool> used;

    void helper(vector<int>& nums) {
        if (temp.size() == nums.size()) { ans.push_back(temp); return; }

        for (int i = 0; i < (int)nums.size(); ++i) {
            if (used[i]) continue;                                    // already in the path
            if (i > 0 && nums[i] == nums[i-1] && !used[i-1]) continue; // the guard
            used[i] = true;  temp.push_back(nums[i]);
            helper(nums);
            used[i] = false; temp.pop_back();
        }
    }
public:
    vector<vector<int>> permuteUnique(vector<int>& nums) {
        sort(nums.begin(), nums.end());          // mandatory
        used.assign(nums.size(), false);
        helper(nums);
        return ans;
    }
};
```
**TC:** O(n!/Π(cnt!) · n) — one leaf per *unique* permutation, each copied in O(n). **SC:** **O(n)** auxiliary. Output separate.
**Why `!used[i-1]`:** equal copies must be consumed **left-to-right**. If the identical copy to my left is *not* in the path, it was already tried and undone **at this level** — starting with `nums[i]` would rebuild the same arrangement. The `used[i-1]` variant (no `!`) is also *correct* — it just fixes the opposite canonical order — but it prunes **one level deeper**, entering branches that die at the next call instead of never entering them. Say `!used[i-1]`.

## My Solution
```cpp
class Solution {
    void permuteHelper(int index, vector<int>& nums, vector<vector<int>>& ans) {
        if (index == (int)nums.size()) { ans.push_back(nums); return; }

        unordered_set<int> seen;                          // per LEVEL, not global
        for (int i = index; i < (int)nums.size(); i++) {
            if (!seen.insert(nums[i]).second) continue;   // this value already filled this slot
            swap(nums[index], nums[i]);
            permuteHelper(index + 1, nums, ans);
            swap(nums[index], nums[i]);
        }
    }
public:
    vector<vector<int>> permuteUnique(vector<int>& nums) {
        vector<vector<int>> ans;
        permuteHelper(0, nums, ans);
        return ans;
    }
};
```
**Correct** — brute-verified against `next_permutation` on **all 25,377** inputs of length ≤ 7 over alphabets of size 2–4: **0 failures**. `sort` is genuinely unnecessary here (correctly left commented out) because the set keys on **values**, so it never depends on ordering.
**`.second` explained:** `unordered_set::insert` returns `pair<iterator, bool>`; `.second` is `true` only if the value was **actually inserted** (i.e. new). So `!…second` reads *"insert failed because it's already there → skip."* One hash lookup instead of the two that `count()` + `insert()` would cost. C++17 alternative if the member name reads cryptic: `auto [it, ok] = seen.insert(nums[i]); if (!ok) continue;`.
**Cost:** each frame holds up to `n - index` entries ⇒ **O(n²)** total auxiliary across the stack, vs O(n) for Shape A. You trade the `used[]` array for a bigger, slower (hashing) structure — so this is *not* the "space-optimal" variant it was in 46.
**Refinement:** `seen` **must** stay inside the function. Hoist it to a member and values used at other depths report "already seen" — you silently **lose** valid permutations. Also cast `nums.size()` (`int` vs `size_t`). Lead with Shape A in an interview; offer this as "if you'd rather not carry a `used[]` array."

### ❌ The attempt that looked right (worth remembering)
```cpp
if (i > index && nums[i] == nums[i - 1]) continue;   // adjacency — dies under swap
if (i > index && nums[i] == nums[index]) continue;   // only catches equality with the FRONT
```
**Wrong.** `[1,2,3,2]` → emits **18**, answer is **12**: at `index=0` the `2` at position 3 passes *both* guards (`nums[3]=2 ≠ nums[2]=3`, and `2 ≠ nums[0]=1`), so the same value fills slot 0 twice over the same remaining multiset → 6 exact duplicates.
**Adding `sort` does not fix it** — brute force found **2,700 failing inputs** out of 25,377 even when sorted, smallest `[0,0,1,2,2,3]` → 192 emitted vs 180. Both guards are *conservative* (they never over-prune, so nothing is missing) — they're simply **insufficient**, which is why small cases like `[1,1,2]` and `[1,2,1]` pass and lull you into trusting it. **Never validate a dedup guard on n ≤ 3.**

## Other Approaches
- **Run LC 46, dedupe with a `set<vector<int>>`** *(brute)* — generates all **n!** then filters. **O(n! · n log n)** / **O(n! · n)**. Passes at n ≤ 8; it's the "I didn't find the guard" answer. One sentence, then move on.
- **`used[]` + sort + `!used[i-1]`** *(canonical)* — **O(n!/Π(cnt!) · n)** / **O(n)**. Default. Zero duplicate branches ever entered.
- **Swap + per-level `unordered_set`** *(the solution above)* — same time, **O(n²)** auxiliary, **no sort**. Use it when you're already in the swap template.
- **Counting / frequency-map** *(cleanest, and the best answer to "handle 10⁶ duplicates of few values")* — build `map<int,int> freq`, then at each slot loop over **distinct values** with `cnt > 0`: decrement → recurse → restore. The duplicate problem **disappears by construction** — no guard, no sort, no set:
  ```cpp
  void helper(map<int,int>& freq, int n) {
      if (temp.size() == n) { ans.push_back(temp); return; }
      for (auto& [v, c] : freq) {
          if (!c) continue;
          c--; temp.push_back(v);
          helper(freq, n);
          c++; temp.pop_back();
      }
  }
  ```
  **O(n!/Π(cnt!) · n)** time, **O(n + d)** space. Branching factor is **d = #distinct**, not n — a real win when duplicates dominate.
- **`sort` + `next_permutation` loop** *(library)* — `do { ans.push_back(nums); } while (next_permutation(...))`. **O(n!/Π(cnt!) · n)**, **O(1)** auxiliary, output **lexicographic**, and it handles duplicates **for free** (identical code solves 46). The "in production I'd write this" closer — never your only answer.

## Pitfalls
- **Reusing the 90/46 adjacency guard inside the swap template** — the headline trap of this problem. Positional rules require a sorted array; `swap` unsorts it mid-flight. See the ❌ block.
- **Testing a dedup guard on `[1,1,2]` only** — passes with broken logic. You need a duplicate pair that is **non-adjacent** *and* **not equal to the front** (`[1,2,3,2]`) to expose it.
- **Forgetting `sort` in Shape A** — the guard silently never fires on `[1,2,1]` and you emit duplicates.
- **`used[i-1]` vs `!used[i-1]`** — both correct, but only `!used[i-1]` prunes at the top of the branch. Know why, don't guess.
- **Hoisting `seen` out of the frame** — cross-level contamination; you **lose** valid permutations (the opposite failure mode from the broken guards, and much harder to spot).
- **Forgetting the restore-`swap`** — the pool stays permuted for every later branch.
- **Quoting the answer count as n!** — it's **n! / Π(count(v)!)**. `[1,1,2]` → 3.
- **Inherited from [[3-46-permutations|46]]:** looping from `start` instead of 0 in the `used[]` shape; recording at every node instead of at the leaf; half un-choosing; saying O(n!) when it's O(n! · n).
