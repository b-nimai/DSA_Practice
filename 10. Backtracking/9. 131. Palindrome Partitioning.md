# 9. 131. Palindrome Partitioning (LC 131) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/palindrome-partitioning/)

**Pattern:** Backtracking — the **partition / "where do I cut?" shape**: the choice at each node isn't *which element to take* but *where the current piece ends*
**Trigger:** "**partition** the string so that **every** substring is a palindrome, return **all** such partitionings" → `index` = start of the un-cut suffix; loop the **end** `i` of the next piece, keep it only if `s[index..i]` is a palindrome, recurse at **`i + 1`**, pop.

## Problem (1-liner)
Given a string `s`, cut it into contiguous pieces such that **every** piece is a palindrome, and return **all** distinct ways to do it.
**Examples:** `s = "aab" → [["a","a","b"], ["aa","b"]]` · `s = "a" → [["a"]]`
**Constraints:** `1 ≤ s.length ≤ 16` · lowercase letters only.
**Edge case:** the answer is **never empty** — every single character is a palindrome, so the all-singletons cut always works. `n = 1` ⇒ exactly one answer. The **worst case is `"aaaa…a"`**: every piece is a palindrome, so *all* `2^(n-1)` cut-sets survive — that's exactly why `n ≤ 16` (`2¹⁵ = 32 768`).

## Idea (1-liner)
A partition of an `n`-char string is nothing but a **subset of the `n − 1` gaps** between characters — so this *is* [[1-78-subsets|Subsets]], with "cut here / don't cut here" replacing "take / don't take", and the palindrome test as the **prune** that kills a branch the moment a piece is invalid.

## Approach
1. `helper(index)` means: *everything before `index` is already cut into valid palindromes; partition the suffix `s[index..]`.*
2. **Base case:** `index == s.size()` ⇒ the suffix is empty, every piece was valid ⇒ `res.push_back(path)`. Record **only here**, never at an internal node (a partial path is not a partition).
3. **Loop the end of the piece:** `for (i = index; i < n; ++i)` — the candidate piece is `s[index..i]`.
4. **Prune:** keep the branch only `if (isPal(index, i))`. This is the whole algorithm — an invalid prefix kills its entire subtree instantly.
5. **Choose → explore → un-choose:** `path.push_back(s.substr(index, i - index + 1))` → `helper(i + 1)` → `path.pop_back()`.

> **Load-bearing insight:** the recursion is on **`i + 1`, the character after the piece you just cut** — not on `index + 1` (that would only ever cut single chars) and not on `i` (infinite recursion, you'd re-cut the same char forever). And **no dedup guard is needed anywhere**: a partition is *uniquely determined* by its set of cut positions, and the loop enumerates each cut-set exactly once. Reaching for `sort` + skip-equal-siblings here (the [[2-90-subsets-ii|90]] / [[6-40-combination-sum-ii|40]] reflex) is pure noise — even though `"aa"` has repeated characters, `["a","a"]` and `["aa"]` are *different* answers.

## Code (clean canonical)
```cpp
class Solution {
    int n;
    vector<vector<bool>> pal;                    // pal[i][j] = s[i..j] is a palindrome
    vector<string> path;
    vector<vector<string>> res;

    void helper(int index, const string& s) {
        if (index == n) { res.push_back(path); return; }

        for (int i = index; i < n; ++i) {
            if (!pal[index][i]) continue;                        // prune
            path.push_back(s.substr(index, i - index + 1));      // choose
            helper(i + 1, s);                                    // explore (i + 1, not index + 1)
            path.pop_back();                                     // un-choose
        }
    }
public:
    vector<vector<string>> partition(string s) {
        n = s.size();
        pal.assign(n, vector<bool>(n, false));
        for (int i = n - 1; i >= 0; --i)                         // i descending ⇒ pal[i+1][j-1] is ready
            for (int j = i; j < n; ++j)
                pal[i][j] = (s[i] == s[j]) && (j - i < 2 || pal[i + 1][j - 1]);

        helper(0, s);
        return res;
    }
};
```
**TC:** **O(n · 2ⁿ)** — `2^(n-1)` partitions in the worst case, each costing O(n) to build and copy; the `O(n²)` palindrome precompute is dwarfed by it. **SC:** **O(n²)** for the DP table + **O(n)** recursion/path (output excluded).
**Say it as:** "the output is already exponential, so I can't beat 2ⁿ — the only thing I control is making each palindrome test **O(1)** instead of O(n), which is what the DP table buys."

## My Solution
```cpp
class Solution {
    bool palindrome(string &s, int start, int end) {
        while (start <= end) {
            if (s[start++] != s[end--]) return false;
        }
        return true;
    }
    void helper(int index, string &s, vector<string>&path, vector<vector<string>>&res) {
        if (index == s.size()) { res.push_back(path); return; }

        for (int i = index; i < s.size(); i++) {
            if (palindrome(s, index, i)) {
                path.push_back(s.substr(index, i - index + 1));
                helper(i + 1, s, path, res);
                path.pop_back();
            }
        }
    }
public:
    vector<vector<string>> partition(string s) {
        vector<vector<string>>res;
        vector<string>path;

        helper(0, s, path, res);

        return res;
    }
};
```
**Correct — accepted, and it gets all three structural decisions right:** recursion at **`i + 1`**, recording **only** at `index == s.size()`, and a clean `push_back` / `pop_back` pair on every branch. The two-pointer `while (start <= end)` is fine — at the exact middle of an odd-length piece it compares `s[m]` with itself, which is harmless (`start < end` is the tighter-but-equivalent bound).

**Refinement 1 — precompute the palindrome table (the expected follow-up).** Your `palindrome()` re-scans overlapping substrings across sibling branches; on `"aaaa…a"` the same test is repeated thousands of times. The O(n²) DP above makes every check O(1) — see the canonical code. This is the single thing an interviewer will ask for.

**Refinement 2 — `i < s.size()` and `index == s.size()` compare `int` to `size_t`.** Compiles with a sign-compare warning. Hoist `int n = s.size();` once and use it in both places — same class of nit as in [[8-79-word-search|79]].

**Refinement 3 — `s.substr(...)` copies on every kept branch.** Pushing `(start, len)` pairs and materialising the strings only at the base case avoids the copies on branches that die later. Worth **saying out loud** in an interview; not worth writing — it makes the code noticeably harder to read for no asymptotic win.

## Other Approaches
- **Bitmask brute force** *(name it, then reject it)* — enumerate all `2^(n-1)` cut-sets over the gaps, materialise each partition, and check every piece. **O(2ⁿ · n)** / **O(n)**. Same asymptotics as the backtracking, but it has **zero pruning**: `"zabcd…"` still explores all `2^(n-1)` masks even though the very first piece already fails. The backtracking's entire value is abandoning that subtree at depth 1.
- **Backtracking with an on-the-fly two-pointer check** *(the natural first answer — yours)* — **O(n² · 2ⁿ)** worst case / **O(n)** auxiliary. Each of the O(2ⁿ) nodes may spend up to O(n) per candidate piece. Perfectly fine at `n ≤ 16`; state the bound honestly rather than quoting O(n·2ⁿ) for it.
- **Backtracking + DP palindrome table** *(canonical / optimal)* — **O(n · 2ⁿ)** / **O(n²)**. Precompute `pal[i][j]` in O(n²), then every prune is O(1). This is the answer to write.
- **Expand-around-centre precompute** — same `pal` table, built by expanding from each of the `2n − 1` centres. Also O(n²) but O(1) extra reasoning; some prefer it because it needs no fill-order argument. Use whichever you can derive under pressure.
- **Memoised DFS returning `vector<vector<string>>` per suffix** — caches the partitions of every suffix so shared suffixes aren't re-expanded. **Does not improve worst-case TC** (the output itself is exponential) and blows up memory by storing exponentially many string vectors. Mention only to show you considered it and saw why it doesn't pay.
- **Ask for the *minimum* number of cuts instead ⇒ stop enumerating.** That's **LC 132 Palindrome Partitioning II**: pure DP, `cut[i] = min over j (cut[j-1] + 1)` where `s[j..i]` is a palindrome, **O(n²)** / **O(n)** — and it handles `n ≤ 2000`. The moment the question says "how **many** / **fewest** / **can it be done**" instead of "return **all**", enumeration is the wrong family (same fork as [[5-39-combination-sum|39]] → knapsack DP).

## Pitfalls
- **Recursing at `index + 1` instead of `i + 1`** — you'd only ever emit the all-singletons partition, since the next call always starts one char after the *old* start rather than after the *piece*. Silently returns 1 answer instead of `2^(n-1)`.
- **Recursing at `i`** — the piece is never consumed; infinite recursion / stack overflow. (Contrast [[5-39-combination-sum|39]], where `i` is *deliberately* correct because reuse is allowed.)
- **`substr` off-by-one** — the length is `i - index + 1`, not `i - index`. Writing the latter silently drops the last character of every piece and still "runs".
- **Recording at every node** instead of at `index == n` — emits partial partitions like `[["a"]]` for `"aab"`. Same trap as [[7-17-letter-combinations-of-a-phone-number|17]]: fixed-length/complete-consumption problems record at the **leaf only**.
- **Checking the palindrome of the wrong range** — it's the **new piece** `s[index..i]`, not the whole prefix `s[0..i]` and not the accumulated `path`.
- **Adding a dedup guard** — there are no duplicate answers to remove; a `sort` here would also destroy the string. Uniqueness is structural (one answer per cut-set).
- **Assuming the result can be empty** and special-casing it — it never is, the all-singletons partition always exists.
- **Quoting O(2ⁿ) flat** — each answer costs O(n) to copy, so it's **O(n · 2ⁿ)**; and if you check palindromes on the fly, say **O(n² · 2ⁿ)** rather than borrowing the DP version's bound.
- **Inherited from the pattern:** missing the `pop_back()`; passing `path` by value (correct but copies at every frame).
