# 10. 93. Restore IP Addresses (LC 93) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/restore-ip-addresses/)

**Pattern:** Backtracking — the **partition shape with a fixed piece count**: same "where does the current piece end?" choice as [[9-131-palindrome-partitioning|131]], but the depth is **pinned at exactly 4** and the piece test is *numeric* instead of structural
**Trigger:** "insert dots into a digit string so it becomes a **valid IP** — **exactly 4** parts, each **0–255**, **no leading zeros**, return **all** ways" → `index` = start of the un-cut suffix, `seg` = how many parts are already placed; loop the piece **length 1..3**, keep it only if it's a legal octet, recurse at **`index + len`**, and when `seg == 3` the **last part is forced** to be the whole remaining suffix.

## Problem (1-liner)
Given a digit-only string `s`, insert three dots (no reordering, no deleting) so the result is a valid IPv4 address — four integers in `[0, 255]`, none with a leading zero — and return **all** such addresses.
**Examples:** `s = "25525511135" → ["255.255.11.135","255.255.111.35"]` · `s = "0000" → ["0.0.0.0"]` · `s = "101023" → ["1.0.10.23","1.0.102.3","10.1.0.23","10.10.2.3","101.0.2.3"]`
**Constraints:** `1 ≤ s.length ≤ 20` · digits only.
**Edge case:** the answer is **very often empty** — the opposite of [[9-131-palindrome-partitioning|131]]. Any `n < 4` or `n > 12` is instantly impossible (`"1"`, `"1111111111111"` → `[]`), and even in range `"0000"` yields exactly one and `"9999999999"` yields none. Note the constraint says **20**, not 12 — the problem *deliberately* hands you unsolvable inputs.

## Idea (1-liner)
Same cut-loop as Palindrome Partitioning, but with **two hard bounds baked in**: every piece is **1–3 chars** (so the branching factor is 3, not `n`) and there are **exactly 4** pieces — which makes the whole search tree at most `3³ = 27` leaves, i.e. **constant**.

## Approach
1. `helper(index, seg)` means: *`s[0..index)` is already cut into `seg` valid octets; finish the suffix `s[index..]` using the remaining `4 − seg` octets.*
2. **Reject impossible inputs up front:** `n < 4 || n > 12 ⇒ []`. Four octets hold at least 4 and at most 12 digits.
3. **Prune every frame** by the same arithmetic: with `left = n − index` chars and `slots = 4 − seg` octets to fill, `left < slots || left > 3 * slots ⇒ return`. This kills dead branches at depth 1 instead of at the leaf.
4. **Base case `seg == 3`:** the fourth octet isn't a *choice* — it is whatever remains. Validate that remainder and record. (The prune in step 3 already guarantees `1 ≤ left ≤ 3`.)
5. **Choice loop:** `for (len = 1; len <= 3 && index + len <= n; ++len)` — keep the piece only if it's a legal octet, then `ip += piece + '.'` → `helper(index + len, seg + 1)` → **`ip.resize(oldSize)`** to undo.
6. **Octet validity, in this exact order:** length `1..3` → **no leading zero** (`len > 1 && s[start] == '0'`) → **value ≤ 255**.

> **Load-bearing insight:** the last segment is **not** enumerated, it's **forced** — and that single decision is what makes the code correct *and* dot-free. If you looped all four segments you'd have to accept only when `seg == 4 && index == n` **and** strip a trailing `.` on every push. Handling the tail as a base case does both for free. The flip side is the trap it creates: that forced tail still needs the **full** validity check — length ≤ 3, no leading zero, ≤ 255 — because nothing else constrains it. Forgetting the length check is the #1 wrong answer here: `"255255111135"` would happily emit `"2.5.5.255111135"`.

## Code (clean canonical)
```cpp
class Solution {
    int n;
    vector<string> res;

    // s[start .. start+len-1] is a legal octet
    bool valid(const string& s, int start, int len) {
        if (len > 1 && s[start] == '0') return false;                 // leading zero
        if (len == 3) {                                               // only 3 digits can exceed 255
            int v = (s[start] - '0') * 100 + (s[start+1] - '0') * 10 + (s[start+2] - '0');
            if (v > 255) return false;
        }
        return true;
    }

    void helper(int index, int seg, string& ip, const string& s) {
        int left = n - index, slots = 4 - seg;
        if (left < slots || left > 3 * slots) return;                 // feasibility prune

        if (seg == 3) {                                               // 4th octet is forced
            if (valid(s, index, left)) res.push_back(ip + s.substr(index));
            return;                                                   // note: ip untouched
        }

        for (int len = 1; len <= 3 && index + len <= n; ++len) {
            if (!valid(s, index, len)) continue;
            size_t keep = ip.size();                                  // choose
            ip += s.substr(index, len);
            ip += '.';
            helper(index + len, seg + 1, ip, s);                      // explore
            ip.resize(keep);                                          // un-choose (drops piece + dot)
        }
    }
public:
    vector<string> restoreIpAddresses(string s) {
        n = s.size();
        if (n < 4 || n > 12) return {};
        string ip;
        helper(0, 0, ip, s);
        return res;
    }
};
```
**TC:** **O(1)** — at most `3³ = 27` leaves, each O(1) to build, since `n ≤ 12` is a *constant*. Say **O(3⁴ · n)** if you want the shape rather than the number. **SC:** **O(1)** — depth 4, buffer ≤ 15 chars (output excluded).
**Say it as:** "the input is capped at 12 digits and every piece is 1–3 digits, so this is a constant-size search — `3³` candidates. The interesting part isn't complexity, it's the **validity predicate** and the fact that the fourth octet is forced, not chosen."

## My Solution
```cpp
class Solution {
    bool valid(string &str) {
        if (str.empty() || str.size() > 3) return false;
        if (str.size() > 1 && str[0] == '0') return false;
        if (stoi(str) > 255) return false;
        return true;
    }
    void helper(int index, int dots, string& ip, string &s, vector<string>&res) {
        if (dots == 3) {
            string last = s.substr(index, s.size() - index);
            if (!valid(last)) return;
            ip += last;
            res.push_back(ip);
            return;
        }

        for (int i = index; i < s.size() && i < index + 3; i++) {
            string part = s.substr(index, i - index + 1);
            if (valid(part)) {
                size_t ip_size = ip.length();
                ip += part;
                ip += ".";
                helper(i + 1, dots + 1, ip, s, res);
                ip.resize(ip_size);
            }
        }
    }
public:
    vector<string> restoreIpAddresses(string s) {
        vector<string>result;
        if(s.size() > 12) return result;

        string ip = "";
        helper(0, 0, ip, s, result);

        return result;
    }
};
```
**Correct — accepted, and every structural decision in the recursion is right.** `(index, dots)` fully describes the subproblem; the base case forces the 4th octet instead of enumerating it; the window `i < s.size() && i < index + 3` gives lengths 1..3 and never runs past the end; `size_t keep = ip.length(); … ip.resize(keep);` is the correct undo on a shared buffer (it drops the piece **and** its dot in one call); and `index` strictly advances with `dots` capped at 3, so depth is exactly 4. The empty-tail case (`index == s.size()` at `dots == 3`) is caught by `str.empty()` — the check most people leave out.

**Refinement 1 — add the feasibility prune (the one real improvement).** You currently walk into branches that provably can't finish, e.g. `"1111111111"` with `dots == 2` and 8 chars left for 2 octets. Two lines at the top of `helper`:
```cpp
int left = s.size() - index, slots = 4 - dots;
if (left < slots || left > 3 * slots) return;
```
This also makes the caller's `if (s.size() > 12)` guard redundant, and it's what an interviewer means by "can you cut the search?"

**Refinement 2 — the base case mutates `ip` and leans on the caller to clean up.** `ip += last; res.push_back(ip);` leaves the buffer dirty on return; it only works because every caller `resize`s afterwards (and the root never records). One character of change makes the frame self-contained: `if (valid(last)) res.push_back(ip + last);`.

**Refinement 3 — `valid` takes `string&` and forces a `substr` per candidate.** Passing `(s, start, len)` and comparing digits arithmetically (see canonical) drops ~27 small allocations and, more importantly, removes `stoi` — which throws on non-digit input and would overflow on a long piece if the `size() > 3` guard were ever reordered above it. Your ordering is correct today; making it structurally impossible to get wrong is better.

**Refinement 4 — nits.** `dots` counts *placed segments*, not dots — `seg` reads truer against the `seg == 3` base. `s.substr(index, s.size() - index)` is just `s.substr(index)`. `i < s.size()` compares `int` to `size_t` (sign-compare warning) — hoist `int n = s.size();`, same nit as in [[8-79-word-search|79]] and [[9-131-palindrome-partitioning|131]].

## Other Approaches
- **Brute force over all dot placements** *(name it, then note it's actually fine here)* — choose 3 cut positions `i < j < k` out of `n − 1` gaps, split, validate all four parts. **O(n³ · n)** / **O(1)**. On `n ≤ 12` that's ~165 splits; it passes. The reason it's still the *worse* answer: it does **zero early rejection** — a bad first octet is re-tested inside every one of the remaining combinations, and the same code shape doesn't generalise to "k parts".
- **Triple nested loop over lengths 1..3** *(the iterative twin of the recursion — genuinely competitive)* —
  ```cpp
  for (int a = 1; a <= 3; ++a) for (int b = 1; b <= 3; ++b) for (int c = 1; c <= 3; ++c) { int d = n-a-b-c; if (d < 1 || d > 3) continue; /* validate 4 pieces */ }
  ```
  **O(1)** / **O(1)**, no recursion at all. Because the depth is **fixed at 4**, unrolling is legal here — unlike [[9-131-palindrome-partitioning|131]], where depth is `n`. Worth saying out loud: "the recursion is only buying me readability, not power, since the depth is a constant." Write the backtracking version anyway; it's the one that survives the follow-up.
- **Backtracking, last octet forced** *(canonical — this note)* — **O(1)** / **O(1)**. Depth 4, branching 3, base case at `seg == 3`.
- **Backtracking, all four octets enumerated** — accept only at `seg == 4 && index == n`. Same complexity, one uniform loop, but you must strip the trailing `.` (`ip.pop_back()` or `ip.substr(0, ip.size()-1)`) and you lose the "the tail is forced" insight. Correct, slightly noisier.
- **DP / memoisation** — pointless. There is no overlapping subproblem worth caching at depth 4, and the output is what you're asked for, not a count.
- **Ask for the *count* of valid IPs instead ⇒ still just count the leaves** (or `dp[i][seg]` = ways to split `s[i..]` into `seg` octets, O(n·4·3)). Unlike [[5-39-combination-sum|39]] → knapsack, the "how many" variant here doesn't change family, because the search is already constant-size. **The real escalation is IPv6** (8 groups, 1–4 hex chars, `::` compression) — same skeleton, a much richer validity predicate; that's LC 468 *Validate IP Address* territory.

## Pitfalls
- **Not validating the forced last octet fully** — it must be length ≤ 3, leading-zero-free **and** ≤ 255. Checking only "non-empty" emits `"2.5.5.255111135"`. This is the single most common wrong submission.
- **Leading zeros** — `"0"` is **valid**, `"00"` and `"01"` are **not**. The guard is `len > 1 && s[start] == '0'`, not `s[start] == '0'` (which would kill `"0.0.0.0"`).
- **`stoi` before the length check** — a 10-digit piece overflows `int`. Order matters: size → leading zero → value.
- **Missing the `n > 12` / `n < 4` rejection** — without it you still terminate (the prune or the `> 3` length check saves you), but you burn the whole tree on inputs the constraints explicitly allow (`n ≤ 20`).
- **Recursing at `index + 1` instead of `i + 1` / `index + len`** — you'd only ever cut single digits, emitting at most one answer.
- **Forgetting the dot in the undo** — `ip.resize(keep)` after appending *piece + dot* is right; `pop_back()`-ing only the dot, or restoring before the dot was added, silently corrupts sibling branches.
- **Enumerating all four segments and forgetting the trailing dot** — outputs `"1.0.10.23."`.
- **Recording at every node** — a partial path isn't an IP. Record only when all four octets are placed (same trap as [[7-17-letter-combinations-of-a-phone-number|17]] and [[9-131-palindrome-partitioning|131]]).
- **Reaching for a dedup guard** — as in 131, uniqueness is structural (one answer per cut-set); the [[2-90-subsets-ii|90]]/[[6-40-combination-sum-ii|40]] sort+skip reflex is noise, and sorting would destroy the string.
- **Assuming the answer is non-empty** — unlike 131, `[]` is a common and correct output.
- **Inherited from the pattern:** missing the un-choose; passing the buffer by value (correct but copies every frame).
