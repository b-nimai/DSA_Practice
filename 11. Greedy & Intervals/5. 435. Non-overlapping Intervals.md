# 5. 435. Non-overlapping Intervals (LC 435) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/non-overlapping-intervals/)

**Pattern:** Greedy / Intervals — **earliest-finish-first**. Sort by **end** (not start) and keep every interval that starts at-or-after the last kept one's end; everything skipped is a removal. This is classic **Activity Selection** wearing a "minimum removals" mask.
**Trigger:** "**minimum number of intervals to remove** so the rest don't overlap" / "**maximum number of non-overlapping intervals** you can keep" → the two are complements: `removals = n − kept`. The tell versus [[3-252-meeting-rooms|252]] (bool) and [[4-253-meeting-rooms-ii|253]] (count of rooms) is that here you **choose which intervals survive** — and the moment you're choosing, the sort key flips from **start** to **end**.

## Problem (1-liner)
Given `intervals[i] = [startᵢ, endᵢ]`, return the **minimum number of intervals to remove** so the remaining ones are pairwise non-overlapping.
**Note:** intervals that only **touch at a point are non-overlapping** — `[1,2]` and `[2,3]` are fine. So the keep test is `s >= end`, never `s > end`.
**Examples:** `[[1,2],[2,3],[3,4],[1,3]] → 1` (drop `[1,3]`) · `[[1,2],[1,2],[1,2]] → 2` (duplicates all conflict; keep one) · `[[1,2],[2,3]] → 0`.
**Constraints:** `1 ≤ n ≤ 10⁵` ⇒ **O(n log n) is the target**, O(n²) TLEs. `−5·10⁴ ≤ startᵢ < endᵢ ≤ 5·10⁴` — coordinates are **negative-capable** (so `INT_MIN`, not `0`, is the only safe sentinel), and `startᵢ < endᵢ` guarantees **no zero-length intervals**. Never empty ⇒ `intervals[0]` is safe, and the answer is `0` for `n == 1`.

## Idea (1-liner)
Maximise how many intervals you **keep**, then answer `n − kept`. Among all intervals still available, always keep the one that **finishes earliest** — it consumes the least of the timeline and so leaves the most room for everything after it. Sorting by **end** makes "finishes earliest" the natural scan order, so one linear pass does it.

## Approach
1. **Sort by end** ascending: `a[1] < b[1]`.
2. Keep a running `end = INT_MIN` — the end of the last interval you decided to **keep**.
3. For each `[s, e]` in that order: if `s >= end` it doesn't conflict → **keep**, set `end = e`. Otherwise it overlaps the kept one → **remove**, `numOfErase++` (leave `end` alone — the kept interval already finishes no later).
4. Return `numOfErase`.

> **Load-bearing insight — why sort by END, not START.** The greedy choice must be "the interval that blocks the future least", and that is the one with the **smallest end**. Sorting by end makes the first element the globally earliest finisher, and inductively each kept element is the earliest finisher compatible with the prefix — the standard **exchange argument**: swap any optimal solution's first interval for the earliest-finishing one and it stays valid and the same size. Start-order does **not** give you that, which is exactly where the classic wrong answer comes from (see *My Solution*).
>
> **Load-bearing insight #2 — why `end` never needs updating on a removal.** In end-sorted order every interval you meet has `e >= end`, so the one you already kept still finishes earliest — no `min` needed. In **start**-sorted order this is false and you **must** write `end = min(end, e)`.
>
> **Load-bearing insight #3 — removals and keeps are the same problem.** `answer = n − (max non-overlapping subset)`. Say this out loud in an interview: it turns an unfamiliar "minimum deletions" phrasing into textbook **Activity Selection** in one sentence.

## Code (clean canonical)
```cpp
class Solution {
public:
    int eraseOverlapIntervals(vector<vector<int>>& intervals) {
        sort(intervals.begin(), intervals.end(),
             [](const vector<int>& a, const vector<int>& b) { return a[1] < b[1]; });

        int numOfErase = 0, end = INT_MIN;      // end of the last KEPT interval
        for (auto& it : intervals) {
            if (it[0] >= end) end = it[1];      // no conflict (touching allowed) → keep
            else numOfErase++;                  // overlaps → drop this one
        }
        return numOfErase;
    }
};
```
**TC:** O(n log n) — the sort dominates; the scan is O(n).  **SC:** O(1) extra (in-place sort, O(log n) introsort stack). It **mutates the caller's vector** — worth saying out loud.

## My Solution
**Final (end-sorted) — correct, and identical to the canonical form:**
```cpp
sort(intervals.begin(), intervals.end(),
     [](vector<int>&a, vector<int>&b) { return a[1] < b[1]; });

int numOfErase = 0, end = INT_MIN;
for (auto &it : intervals) {
    if (it[0] >= end) end = it[1];
    else numOfErase++;
}
return numOfErase;
```
Every load-bearing detail is right: sorted by **end**, `>=` implements the touching rule, `INT_MIN` survives negative coordinates. Only polish: take the lambda params by `const&`.

**Second version (start-sorted, after the fix) — also correct:**
```cpp
sort(intervals.begin(), intervals.end());               // by START
int numOfErase = 0;
vector<int> taken = intervals[0];
for (int i = 1; i < intervals.size(); i++) {
    if (taken[1] > intervals[i][0]) {
        numOfErase++;
        taken[1] = min(taken[1], intervals[i][1]);      // ← the fix
    } else taken = intervals[i];
}
```

**The bug that was fixed — worth remembering.** The original start-sorted version had no `min`: on every overlap it unconditionally dropped the **current** interval and kept `taken`. That's only optimal when `taken` is the earlier finisher; when the current interval ends **sooner**, keeping `taken` blocks more of the future than necessary.
Failing case — `[[-52,31],[-73,-26],[82,97],[-65,-11],[-62,-49],[95,99],[58,95],[-31,49],[66,98],[-63,2],[30,47],[-40,-26]]` → **8**, expected **7**:
```
taken=[-73,-26]
[-65,-11] overlap → e1
[-63,  2] overlap → e2
[-62,-49] overlap → e3   ← ends at -49, EARLIER than -26; should have become `taken`
[-52, 31] overlap → e4
[-40,-26] overlap → e5   ← would have fit after [-62,-49]
[-31, 49] overlap → e6   ← would have fit too
[30,47] kept … [66,98] e7, [82,97] e8, [95,99] kept   ⇒ 8
```
Keeping `[-62,-49]` saves two removals ⇒ **7**. **Prefer the end-sort in an interview**: the `min` disappears and the correctness argument is one sentence instead of two.

## Other Approaches
- **Brute force — enumerate every subset**, keep the largest non-overlapping one, answer `n − |best|`. **O(2ⁿ · n) / O(n)**. Name it only as the baseline that motivates the greedy.
- **DP — longest non-overlapping chain** (LIS-shaped): sort by end, `dp[i] = 1 + max(dp[j])` over `j` with `end[j] <= start[i]`; answer `n − max(dp)`. **O(n²) / O(n)**, or **O(n log n)** with binary search over the sorted ends. Correct, and the honest fallback if you can't justify greedy — but over-engineering here. Reach for it when intervals gain **weights** (*Weighted Interval Scheduling*, LC 1235), where greedy genuinely breaks.
- **Sort by end + earliest-finish-first greedy** *(canonical)* — **O(n log n) / O(1)**. The expected answer.
- **Sort by start + `min` on the end** *(alt-optimal)* — **O(n log n) / O(1)**. Equally correct, one extra moving part. Worth knowing because start-sorting is the shared skeleton of [[1-56-merge-intervals|56]] / [[2-57-insert-interval|57]] / [[4-253-meeting-rooms-ii|253]], so it's the sort your hands reach for by reflex — just remember the `min`.

> **The trio to distinguish out loud:** *can one room take them all?* → [[3-252-meeting-rooms|252]], sort by **start**, adjacent-pair scan, **bool**. *How many rooms?* → [[4-253-meeting-rooms-ii|253]], **peak concurrency**, min-heap / sweep, **count**. *Which do I drop so one room suffices?* → **435**, sort by **end**, earliest-finish-first, **count of removals**. Same input shape, three sorts, three answers. Near-twin: [[6-452-minimum-number-of-arrows-to-burst-balloons|452 Burst Balloons]] — identical greedy, except balloons **touch = overlap**, so the test becomes `s > end` (strict) and it counts the **groups kept** rather than the ones dropped. Aliases: **Activity Selection**, *maximum non-overlapping intervals*, LC 646 *Maximum Length of Pair Chain* (literally this problem asking for `kept`).

## Pitfalls
- **Sorting by start and always dropping the current interval** — the #1 wrong submission on 435 (traced above). Either sort by **end**, or keep `end = min(end, e)` on every removal.
- **Sorting by the wrong key, generally** — start for *merge / detect / count concurrency*, end for *keep-the-most*. Inherited straight from the pattern index.
- **`>=` vs `>` on the boundary** — the statement says touching is **allowed**, so keep on `s >= end`. Using `s > end` drops `[1,2],[2,3]` needlessly and returns 1 instead of 0 — and that rule **flips** for [[6-452-minimum-number-of-arrows-to-burst-balloons|452]].
- **Initialising `end = 0`** — coordinates go down to `−5·10⁴`, so `0` wrongly rejects a first interval that ends negative. Use `INT_MIN`, or seed from `intervals[0]` and start at `i = 1`.
- **Forgetting the comparator** — plain `sort(intervals.begin(), intervals.end())` sorts lexicographically **by start**, silently changing the algorithm rather than erroring.
- **Returning the kept count instead of the removed count** — they're complements (`n − kept`); LC 646 asks for the other one. Read which is wanted.
- **Counting overlapping *pairs*** — three mutually overlapping intervals are 3 pairs but only **2** removals.
- **Leaving debug `cout` in the loop** — at `n = 10⁵` the I/O alone can TLE, quite apart from failing the judge's diff.
- **An O(n²) pairwise check** — TLEs at `n = 10⁵`. Sorting is what collapses the all-pairs question into one pass.

**Family map:** the **sort-by-end** half of the pattern, shared with [[6-452-minimum-number-of-arrows-to-burst-balloons|452 Burst Balloons]] · contrast the **sort-by-start** scan of [[1-56-merge-intervals|56 Merge Intervals]], [[2-57-insert-interval|57 Insert Interval]] and [[3-252-meeting-rooms|252 Meeting Rooms]] · complement of the peak-concurrency heap in [[4-253-meeting-rooms-ii|253 Meeting Rooms II]] · the weighted-interval DP escalation is LIS-shaped, same machinery as the Binary Search / DP patterns.
