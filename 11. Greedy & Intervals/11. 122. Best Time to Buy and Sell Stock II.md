# 11. 122. Best Time to Buy and Sell Stock II (LC 122) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/best-time-to-buy-and-sell-stock-ii/)

**Pattern:** Greedy — **one pass, sum the positive consecutive differences**. Same "collapse the input into a `diff[]` and reason about prefix sums" move as [[10-134-gas-station|134]], but with the constraint *removed* instead of tightened: there is no ordering/feasibility condition to satisfy, so every profitable delta can be taken independently. The parent idea is **telescoping** — a multi-day trade equals the sum of its daily deltas, so an arbitrary set of trades decomposes into per-day decisions.
**Trigger:** "**unlimited transactions**" + "**hold at most one share**" + "**you may buy and sell on the same day**". Those three phrases together are the whole giveaway: same-day buy/sell means the daily deltas are *independently choosable*, so the answer is `Σ max(0, p[i] − p[i-1])`. The moment the statement adds "**at most k transactions**" (121/123/188), a "**cooldown**" (309), or a "**fee**" (714), the decomposition breaks and you must switch to the hold/free DP.

## Problem (1-liner)
Given daily `prices[]`, you may buy and sell any number of times but may **hold at most one share at a time** (same-day sell-then-rebuy allowed); return the **maximum total profit**.
**Examples:** `[7,1,5,3,6,4] → 7` (buy@1 sell@5, buy@3 sell@6 = 4+3) · `[1,2,3,4,5] → 4` (one trade 1→5, *or* four daily trades — same total) · `[7,6,4,3,1] → 0` (monotone down ⇒ never buy).
**Constraints:** `1 ≤ n ≤ 3·10⁴`, `0 ≤ prices[i] ≤ 10⁴`. **Edges:** `n == 1` → `0` (no pair exists) · all-equal `[5,5,5]` → `0` · profit is never negative (doing nothing is always legal). **Overflow:** max profit ≤ `3·10⁴ × 10⁴ = 3·10⁸` ⇒ **`int` is safe**, no `long long`.

## Idea (1-liner)
Add up every **upward step** between consecutive days: `profit = Σ max(0, prices[i] − prices[i-1])`.

## Approach
1. `profit = 0`.
2. Sweep `i = 1 .. n-1`.
3. `profit += max(0, prices[i] - prices[i-1])` — i.e. bank the day's gain, ignore the day's loss.
4. Return `profit`.

> **Load-bearing insight #1 — telescoping makes the deltas independent.** Any single trade `buy@i, sell@j` earns `p[j] − p[i] = Σ_{k=i+1..j} (p[k] − p[k-1])`. So **every** legal strategy is just *some* set of non-overlapping day-ranges, and its profit is the sum of the daily deltas inside them. The best such sum obviously takes every **positive** delta and no negative one — and because same-day buy/sell is allowed, that set of deltas is **actually achievable** (chain adjacent up-days into one trade). Upper bound + achievability = optimality; that's the whole proof, and it's two sentences in an interview.

> **Load-bearing insight #2 — "unlimited transactions" is what kills the DP.** With a cap of `k`, choosing *which* rises to take becomes a real optimisation (you'd want the largest ones, but they must be non-overlapping) and greedy dies. With no cap, there is nothing to choose — every rise is free. **Say this out loud**, because it's exactly why the identical-looking **LC 121** (one transaction) is **not** solvable this way.

> **Load-bearing insight #3 — the "peak–valley" view is the same algorithm.** Walk down to a local valley `v`, walk up to a local peak `p`, add `p − v`, repeat. It gives the identical number because a run of consecutive positive deltas telescopes back into `p − v`. Prefer the delta form to *write* (fewer moving parts, no peak/valley state), but keep the peak–valley phrasing to *explain* — and note that it's the version that survives when a **transaction fee** is added (you then compare `p − v − fee` against merging runs).

## Code (clean canonical)
```cpp
class Solution {
public:
    int maxProfit(vector<int>& prices) {
        int n = prices.size();
        int profit = 0;

        for (int i = 1; i < n; i++)
            profit += max(0, prices[i] - prices[i - 1]);   // bank every rise

        return profit;
    }
};
```
**TC:** **O(n)** — one pass, no sort (order *is* the problem).  **SC:** **O(1)** — a single accumulator.
*`n == 1` needs no special case — the loop simply never runs and `0` falls out.*

## My Solution
```cpp
class Solution {
public:
    int maxProfit(vector<int>& prices) {
       int profit = 0;

       for(int i = 1; i < prices.size(); i++) {
            if (prices[i] > prices[i - 1]) profit += prices[i] - prices[i - 1];
       }

       return profit;
    }
};
```
✅ **Correct and optimal — O(n)/O(1)**, the canonical greedy. Starting at `i = 1` and looking backwards is the right shape (it sidesteps the `size() - 1` unsigned trap), the `>` test correctly ignores flat days (`p[i] == p[i-1]` contributes 0 either way), and `n == 1` is handled for free.
**Refinements:** `i < prices.size()` compares `int` with `size_t` ⇒ `-Wsign-compare`; hoist `int n = prices.size()`. Folding the branch into `profit += max(0, prices[i] - prices[i-1])` makes the *sentence you'd say in the interview* ("take only the gains") literally visible in the code.

## Other Approaches
- **Brute force — try every buy/sell schedule.** Recurse on each day with "buy / sell / skip". **O(2ⁿ) / O(n)**. Say it, then kill it at `n = 3·10⁴`; it's only useful as a random-test oracle on tiny arrays.
- **Peak–valley scan.** Two inner `while` loops: descend to a valley, ascend to a peak, `profit += peak − valley`. **O(n) / O(1)**. Same answer, more state, easier to get the boundary wrong — but it's the *narratable* version and the one that generalises to a fee.
- **Greedy delta sum** *(canonical)* — **O(n) / O(1)**. The expected answer; write this.
- **State-machine DP — the general form worth naming.** `hold = max(hold, free − p[i])`, `free = max(free, hold + p[i])`, seed `hold = −p[0], free = 0`, answer `free`. **O(n) / O(1)**. Overkill here, but **this is the one to reach for the instant a follow-up lands**: it extends verbatim to **714** (fee: `free = max(free, hold + p[i] − fee)`), **309** (cooldown: carry a third state), and **123 / 188** (`k` transactions: `2k` states, O(nk)). Framing to use: *"the greedy is the `k = ∞` special case of this DP"* — that single sentence covers the whole stock family.
- **Follow-ups to pre-empt:** *"at most one transaction?"* → **LC 121**, track `minPrice` and `best = max(best, p[i] − minPrice)`; the delta-sum greedy is **wrong** there. *"add a fee?"* → 714, greedy breaks because chopping a rise into daily trades now pays the fee repeatedly. *"cooldown after selling?"* → 309. *"how many transactions did you make?"* → count maximal ascending runs, not positive deltas. *"better than O(n)?"* → no, every price must be read.

> **The one-pass-accumulator family to distinguish out loud:** *extend a frontier, **cut** when the index catches it* → [[9-763-partition-labels|763]] / [[8-45-jump-game-ii|45]]. *Extend a frontier, **fail** when the index outruns it* → [[7-55-jump-game|55]]. *Accumulate a signed sum, **restart** when it goes negative* → [[10-134-gas-station|134]] / Kadane. *Accumulate a signed sum, **clamp each term at 0**, never restart* → **122**. 134 vs 122 is the sharp pair: both collapse the input into daily deltas, but 134's deltas are **chained** (a prefix constraint ⇒ order matters, you must find a start) while 122's are **independent** (no constraint ⇒ order is irrelevant to the total).

## Pitfalls
- **Solving LC 121 with this code (or vice versa)** — *the* signature confusion. On `[7,1,5,3,6,4]`, 122 → `7` but 121 → `5`. One transaction ⇒ track a running minimum; unlimited ⇒ sum the deltas. Read which one you're in.
- **Starting the loop at `i = 0`** — `prices[i - 1]` is an out-of-bounds read on the first iteration. Either start at `1` and look back, or end at `n - 2` and look forward; never mix the two.
- **`i < prices.size() - 1` on an empty vector** — `size()` is unsigned, so `0 - 1` wraps to a huge value and the loop runs away. Constraints say `n ≥ 1` here, but the habit is what bites elsewhere; loop from `1` instead.
- **Thinking you must find the actual buy/sell days** — the problem asks only for the *number*. Reconstructing trades is extra work and an extra chance to be wrong; mention that the runs are recoverable if asked, don't compute them.
- **Adding negative deltas "and letting it cancel out"** — dropping the `max(0, …)` / `if` turns the sum into `p[n-1] − p[0]`, which is the profit of a single forced trade (`[7,1,5,3,6,4]` → `−3`). The clamp *is* the algorithm.
- **`<` vs `<=` anxiety on flat days** — a zero delta contributes nothing either way, so both are correct here. Know that it's genuinely free rather than guessing.
- **Sorting the array** — order *is* the problem; sorting produces `p[n-1] − p[0]` and destroys the question. Same reflex to suppress as in [[10-134-gas-station|134]] and [[7-55-jump-game|55]].
- **Reflexive `long long`** — unnecessary at `≤ 3·10⁸`, but state the bound out loud instead of guessing; at `prices[i] ≤ 10⁹` it would genuinely be needed.
- **Reaching for DP first** — it's correct and it's the right *follow-up* tool, but leading with a state machine on the unconstrained version signals you missed the decomposition. Lead with the greedy, then name the DP as its generalisation.
