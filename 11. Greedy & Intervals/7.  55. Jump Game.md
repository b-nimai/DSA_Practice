# 7. 55. Jump Game (LC 55) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/jump-game/)

**Pattern:** Greedy — **furthest-reach frontier**. Not an interval problem at all: each index `i` *is* an interval `[i+1, i+nums[i]]` of landing spots, and "can I reach the end" collapses to "does the **union of the prefixes' reaches** ever break". One pass, one variable, no sort.
**Trigger:** "**each element is a max jump length from that position — can you reach the last index?**" (a **bool**). Whenever the question is *reachability along a line where every position advertises a range*, track a single **`reach` = furthest index reachable so far**; the instant you stand on `i > reach`, you're behind a wall and the answer is `false`. Ask "**how many jumps**" instead ⇒ [[8-45-jump-game-ii|45]], same frontier but layered (BFS-on-an-array).

## Problem (1-liner)
Given `nums` where `nums[i]` is the **maximum** jump length from index `i` (you may jump `1..nums[i]` steps, or 0), starting at index `0`, return **true** iff you can reach index `n-1`.
**Examples:** `[2,3,1,1,4] → true` (0→1, then 3 steps to the end) · `[3,2,1,0,4] → false` (every path lands on index 3, whose value is 0 — a wall) · `[0] → true` (**already at the last index, no jump needed**) · `[2,0,0] → true` (jump straight over the zeros) · `[1,0,1,0] → false`.
**Constraints:** `1 ≤ n ≤ 10⁴` — **never empty**, so `n == 1` must return `true`, not `false`. `0 ≤ nums[i] ≤ 10⁵` — values are **non-negative** (no going backwards) and can be **≫ n**, so `i + nums[i]` can shoot far past the array: clamp or use a wider type if you index with it. `n ≤ 10⁴` looks like it tolerates O(n²), but the intended answer is **O(n)**.

## Idea (1-liner)
Sweep left to right carrying `reach` = the furthest index reachable using anything seen so far; at each `i`, **if `i > reach` you can't even be standing here ⇒ return false**, otherwise widen the frontier with `reach = max(reach, i + nums[i])`. Survive the sweep ⇒ true.

## Approach
1. `reach = 0` — index 0 is reachable by definition.
2. For `i = 0 .. n-1`:
   - `if (i > reach) return false;` — a gap the frontier never crossed (the zero-wall).
   - `reach = max(reach, i + nums[i]);` — extend.
3. Return `true` (an early `if (reach >= n-1) return true;` is a legal fast exit, not required).

> **Load-bearing insight — reachability is an INTERVAL, not a set.** Because you may jump **any** length `1..nums[i]`, everything in `[i+1, i+nums[i]]` is reachable, with **no holes**. So the reachable set is always a **contiguous prefix `[0, reach]`** — which is why a single integer, not a boolean array or a DP table, is enough state. This is exactly why the greedy is safe: there is nothing to "choose", only a frontier to extend.
>
> **Load-bearing insight #2 — `i > reach` is the *only* failure mode.** The sweep can only die at a position it can't stand on. Equivalently: `false` ⟺ there exists a **wall index `k < n-1`** with `max(i + nums[i]) ≤ k` for all `i < k` (the `[3,2,1,0,4]` shape). Checking "is `nums[i] == 0`" is **not** the test — you can jump *over* zeros (`[2,0,0]` is true).
>
> **Load-bearing insight #3 — greedy beats DP because the choice is fake.** Recursion asks "which of the `nums[i]` jumps do I take?", producing O(2ⁿ) → O(n²) memoized. But taking the **longest** jump never hurts: reach is monotone in the jump length, so the max-reach choice dominates every other. Once you see that, the whole DP table collapses into `reach`.

## Code (clean canonical)
```cpp
class Solution {
public:
    bool canJump(vector<int>& nums) {
        int n = nums.size(), reach = 0;
        for (int i = 0; i < n; i++) {
            if (i > reach) return false;          // wall: this index is unreachable
            reach = max(reach, i + nums[i]);      // extend the frontier
        }
        return true;
    }
};
```
**TC:** O(n) — one pass.  **SC:** O(1) — a single int, no recursion, no table. Does **not** mutate the input.

*Backwards twin (same cost, sometimes asked):* start `goal = n-1`; for `i = n-2 .. 0`, `if (i + nums[i] >= goal) goal = i;` return `goal == 0`. Reads as "shrink the target to the leftmost index that can still hit it".

## My Solution
```cpp
bool helper(int index, vector<int>&nums, vector<int>&cache) {
    if (index == nums.size() - 1) return true;
    if (index >= nums.size()) return false;
    if (cache[index] != -1) return cache[index];

    for (int i = nums[index]; i > 0; i--)
        if (helper(index + i, nums, cache)) return true;

    cache[index] = false;
    return false;
}
// canJump: vector<int> mem(n, -1); return helper(0, nums, mem);
```
**Correct, but the wrong complexity class.** The memo is used *safely* — `true` short-circuits before caching, so the cached value is only ever `0`, and `cache[index] != -1 → return cache[index]` can only mean false. Nothing here is wrong logically.
The problem is the inner loop: it spends **`nums[index]` iterations per index**, most of them on out-of-bounds jumps that instantly return false. Worst case is the decreasing wall `nums = [n-2, n-3, …, 2, 1, 0, 0]` ⇒ ≈ **n²/2 ≈ 5·10⁷ recursive calls** at `n = 10⁴`, plus O(n) stack depth. That's **O(n²) / O(n)** — borderline TLE and not the answer to give for a problem with a 3-line O(n) greedy.
Fixes, in order of value:
- **Write the greedy.** The DP has no reason to exist once you see insight #3.
- If you keep the recursion, at minimum **clamp the loop** to `min(nums[index], n - 1 - index)` so you stop recursing past the end — still O(n²), just without the 10⁵ dead branches per index.
- `index >= nums.size()` compares **`int` vs `size_t`** (signed/unsigned warning — harmless here since `index ≥ 0`); hoist `int n = nums.size()` once.
- Ladder to say out loud in the interview: **plain recursion O(2ⁿ) → memoized O(n²) → greedy O(n)/O(1)**. Naming your own solution's tier before the interviewer does is worth as much as the optimal code.

## Other Approaches
- **Brute-force recursion — try every jump length from every index.** `helper(i)` = OR over `helper(i+1..i+nums[i])`. **O(2ⁿ) / O(n)** stack. The honest starting point; say it, don't submit it.
- **Top-down memo / bottom-up DP** — `dp[i] = can I reach the end from i`, either the recursion above with a cache, or backwards `dp[i] = any(dp[i+j]) for j = 1..nums[i]`. **O(n²) / O(n)**. Passes at `n ≤ 10⁴`, but the inner loop is pure waste — this is the tier your solution sits in.
- **Greedy furthest-reach** *(canonical)* — **O(n) / O(1)**. The expected answer.
- **Backwards greedy (shrinking goal)** *(alt-optimal)* — **O(n) / O(1)**. Same idea from the other end; useful when the follow-up asks "which index is the last blocker".
- **BFS layering** — treat `[i+1, i+nums[i]]` as edges and BFS. **O(n)** if you never re-scan a covered range, O(n²) if you do. Wrong tool for a bool, but it's *exactly* the machinery [[8-45-jump-game-ii|45]] needs to count jumps, so it's the right thing to mention as the bridge.

> **The greedy family to distinguish out loud:** *can I reach the end?* → **55**, one `reach`, bool. *how few jumps?* → [[8-45-jump-game-ii|45]], the same frontier split into **levels** (`curEnd` / `farthest`, jumps++ when `i == curEnd`) — BFS in O(1) space. *Which reach-style problems are NOT greedy?* — ones where jumps have **costs/weights** (LC 1696 Jump Game VI ⇒ monotonic-deque DP) or where you may move **backwards** (LC 1306 Jump Game III ⇒ plain BFS/DFS, since reachability is no longer a prefix). The moment the reachable set stops being a **contiguous prefix**, the single-variable greedy dies.

## Pitfalls
- **Returning false as soon as you see `nums[i] == 0`** — you can jump *over* zeros. `[2,0,0]` is **true**, `[1,0,1]` is **false**; the zero itself is never the test, standing on it with no momentum is.
- **`i >= reach` instead of `i > reach`** — `i == reach` means you're standing exactly on the frontier, which is perfectly legal (and is the whole of `[1,1,1,1]`). The `>=` version returns false on almost everything.
- **Forgetting `n == 1`** — the constraint allows `[0]`, and the answer is **true**: you start at the last index. Both loops handle it for free; a hand-rolled "did I jump at least once" check does not.
- **Overflow / OOB when indexing with `i + nums[i]`** — values reach `10⁵` while `n ≤ 10⁴`, so the frontier legitimately points far past the array. Fine as an `int` **comparison**, fatal if you use it as a subscript without clamping (the bug hiding in the memoized version).
- **Writing the O(n²) DP and stopping there** — it AC's, so nothing tells you it's wrong; the interviewer's "can you do better?" is the only signal, and by then you've spent the time.
- **Recursion depth** — a chain of 10⁴ frames is survivable in C++ but is a real stack-overflow risk once `n` grows in the follow-up; the greedy has no stack at all.
- **Confusing it with [[8-45-jump-game-ii|45]]** — 45 *guarantees* reachability and asks for the **count**; blindly counting `reach` updates in 55 does **not** give 45's answer (you'd count extensions, not jumps).
- **Sorting anything** — reflex from the interval half of this pattern. Order **is** the problem here; sorting destroys it.

**Family map:** the **non-interval, frontier** half of Greedy — direct prequel to [[8-45-jump-game-ii|45 Jump Game II]] (same `reach`, layered into a jump count) · shares the "one linear pass, one running extreme, prove the local choice is safe" skeleton with [[9-763-partition-labels|763 Partition Labels]] (which literally reuses *furthest last-occurrence* as its `reach`) and [[10-134-gas-station|134 Gas Station]] · contrast the **sort-first** interval greedies [[5-435-non-overlapping-intervals|435]] / [[6-452-minimum-number-of-arrows-to-burst-balloons|452]], where the safe choice is the earliest **end** rather than the furthest **reach** · escalates to **LC 1306 Jump Game III** (backwards moves ⇒ BFS) and **LC 1696 Jump Game VI** (weights ⇒ monotonic-deque DP), both of which break the prefix property that makes this O(1).
