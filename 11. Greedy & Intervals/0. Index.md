# Greedy & Intervals — Index

60-second whole-pattern recall. Read the **Trigger** column and try to recall the **Idea** before peeking.

**Core skeleton (intervals):** **sort first**, then make the locally best choice in one linear pass. Sorting by **start** turns an all-pairs O(n²) overlap question into an **adjacent-pair** O(n) question (if `next.start >= cur.end` holds for neighbours, it holds for every farther pair too). Sort by **start** to *merge / detect / count* overlaps; sort by **end** to *maximise how many non-overlapping intervals you keep* (earliest-finish-first). When you need **max concurrency**, stop scanning and sweep: `+1` on a start, `-1` on an end.

| 1 | [Merge Intervals](https://leetcode.com/problems/merge-intervals/) | 56 | M | "**merge all overlapping intervals**" / "return the intervals that **cover** all the input" (output is a **set of intervals**, overlap is defined **pairwise** ⇒ naive read is O(n²), and reordering the input is allowed) | **The ROOT of the pattern — every other interval problem here is this loop with the operator or the sort key changed.** `sort()` (default lexicographic on `vector<int>` = by **start**, tie-broken by end — exactly the key needed), then one pass: `if (result.empty() \|\| result.back()[1] < it[0]) result.push_back(it); else result.back()[1] = max(result.back()[1], it[1]);`. **Why start-sort collapses O(n²) → O(n):** after sorting, every later interval starts at or after `it[0]`, so if the current one doesn't touch the running `end`, **no future one can either** — the gap is permanent ⇒ comparing against a single running `end` suffices instead of all kept intervals. **`end = max(end, it[1])`, NEVER `end = it[1]`** — *the* signature bug: start-order ≠ end-order, so a **contained** interval shrinks the run (`[[1,9],[2,3]]` → `[[1,3]]` instead of `[[1,9]]`). **`end < it[0]` strict** — touching **merges** here (`[[1,4],[4,5]]` → `[[1,5]]`), the **opposite** convention from 252/435. | 2 | [Insert Interval](https://leetcode.com/problems/insert-interval/) | 57 | M | "insert `newInterval` into a **sorted, non-overlapping** list, **merging if necessary**" (the input is *already* sorted **and** already merged ⇒ **any sort you write is wasted work**; only **one** intruder ⇒ only **one** merge region) | **[[1-56-merge-intervals|56]] with the sort already done for you ⇒ O(n), not O(n log n).** Sorted + disjoint ⇒ the array splits into **three contiguous zones**, emitted by three sequential loops sharing one index `i` that **never resets**: (1) `while (i<n && intervals[i][1] < lo) push(intervals[i++]);` (2) `while (i<n && intervals[i][0] <= hi) { lo = min(lo, intervals[i][0]); hi = max(hi, intervals[i][1]); i++; }` (3) `push({lo,hi});` then `while (i<n) push(intervals[i++]);`. **Why three loops are legal: the overlapping zone is CONTIGUOUS** — sorted *and* mutually disjoint means everything the intruder touches is one unbroken run, never scattered ⇒ no index is revisited ⇒ O(n). **The two operators are opposites on purpose** — zone 1 **strict** `<`, zone 2 **non-strict** `<=`; that pair encodes "*share at least one point* ⇒ overlapping", so an interval ending exactly where `newInterval` starts is **absorbed, not skipped**. ## When to reach for Greedy / Intervals
1. **"Do these intervals overlap / merge them / insert one"** → sort by **start**, one pass comparing to the previous (or last merged) interval.
2. **"Minimum rooms / maximum concurrent X / peak load"** → **sweep line** or a **min-heap of end times** — you need the running count, not a bool.
3. **"Remove/keep the fewest-or-most intervals so none overlap"** → sort by **end**, earliest-finish-first greedy (LC 435, 452).
4. **"Minimum number of …" / "maximum number of …" on sortable input** → suspect greedy; be ready to justify why the local choice is globally safe (exchange argument).

## Common Pitfalls Across the Pattern
- **Forgetting to sort** — every proof in this pattern starts "after sorting". Unsorted input silently gives wrong answers, not crashes.
- **Sorting by the wrong key** — start for *merge/detect*, end for *keep-the-most*. Getting this backwards is the #1 bug in 435/452.
- **`<` vs `<=` on the boundary** — decided by whether the problem treats touching intervals (`[1,4],[4,7]`) as a conflict. Read the statement; never guess.
- **Unsigned `size()` arithmetic** — `size() - 1` wraps on an empty container; loop from 1 and look backwards.
- **Assuming greedy is safe** — it's only valid when the local choice provably can't hurt the future (see the [[7-1046-last-stone-weight|1046 vs 1049]] trap in the Heap pattern: forced order ⇒ greedy, chosen order ⇒ DP).
