# 2. 57. Insert Interval (LC 57) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/insert-interval/)

**Pattern:** Greedy / Intervals — **[[1-56-merge-intervals|56]] with the sort already done for you**. Because the input arrives **sorted and disjoint**, the array splits into **three contiguous zones** (before · overlapping · after) and one linear pass emits them in order. The sort is the only thing 56 pays for, so removing it is the whole point of this problem.
**Trigger:** "insert `newInterval` into a **sorted, non-overlapping** list, **merging if necessary**" — the tells are (a) the input is *guaranteed* sorted **and** already merged, so **any sort you write is wasted work**, and (b) only **one** new interval arrives, so only **one** merge region can exist. Whenever a problem hands you a pre-sorted disjoint structure and one intruder, think **three zones, O(n)**.

## Problem (1-liner)
Given non-overlapping intervals **sorted ascending by start**, insert `newInterval` so the list stays sorted and non-overlapping, merging whatever it touches. Two intervals overlap if they **share at least one point** (so touching **merges**).
**Examples:** `[[1,3],[6,9]], [2,5] → [[1,5],[6,9]]` · `[[1,2],[3,5],[6,7],[8,10],[12,16]], [4,8] → [[1,2],[3,10],[12,16]]` (swallows three) · `[[1,3],[6,9]], [3,6] → [[1,9]]` (**pure touching on both sides**) · `[[1,5]], [2,3] → [[1,5]]` (**newInterval contained** — the case that needs the `min`) · `[[2,3],[5,7]], [1,10] → [[1,10]]` (swallows everything).
**Constraints:** **`0 ≤ intervals.length ≤ 10⁴` — the list CAN BE EMPTY** (unlike [[1-56-merge-intervals|56]], where `n ≥ 1`), and then the answer is `[[newInterval]]`. `0 ≤ startᵢ ≤ endᵢ ≤ 10⁵` — no inverted intervals, non-negative, no overflow risk. **`intervals` is sorted by start** and non-overlapping — the two gifts that buy you O(n). The result has between `1` and `n+1` intervals, **never empty**.

## Idea (1-liner)
Walk once with a single index `i`: copy everything that **ends before** `newInterval` starts, absorb everything that **starts at or before** `newInterval` ends into `newInterval`, push it once, then copy the rest.

## Approach
1. `result`, `i = 0`, `n = intervals.size()`.
2. **Zone 1 — strictly before:** `while (i < n && intervals[i][1] < newInterval[0])` → `result.push_back(intervals[i++]);`
3. **Zone 2 — overlapping:** `while (i < n && intervals[i][0] <= newInterval[1])` → widen: `lo = min(lo, intervals[i][0]); hi = max(hi, intervals[i][1]); i++;`
4. **Push the grown interval exactly once**, *after* the loop: `result.push_back({lo, hi});`
5. **Zone 3 — strictly after:** `while (i < n) result.push_back(intervals[i++]);`

> **Load-bearing insight — the overlapping zone is CONTIGUOUS, and that's what makes three loops legal.** Because the input is sorted by start *and* mutually disjoint, everything `newInterval` touches forms one unbroken run; it can never be scattered. So you never need to revisit an index, `i` is shared across all three loops and **never resets**, and each interval is visited exactly once ⇒ **O(n)**. Nested loops or a restart would mean you've misread the guarantee.
>
> **Load-bearing insight #2 — the two boundary operators are opposites, on purpose.** Zone 1 tests `intervals[i][1] < newInterval[0]` (**strict**) and zone 2 tests `intervals[i][0] <= newInterval[1]` (**non-strict**). That exact pair encodes "*share at least one point* ⇒ overlapping": an interval ending exactly where `newInterval` begins must **not** be skipped as "before", it must be **absorbed**. Flip either operator and `[[1,3],[6,9]], [3,6]` returns `[[1,3],[3,6],[6,9]]` instead of `[[1,9]]`.
>
> **Load-bearing insight #3 — the push must live OUTSIDE loop 2.** Pushing inside emits one copy per absorbed interval; and if loop 2 never runs (the new interval fits in a gap, or `n == 0`), an inside-push would drop `newInterval` entirely. Outside, it fires exactly once in **every** case — which is precisely why the **empty-input case needs no special handling**.

## Code (clean canonical)
```cpp
class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intervals, vector<int>& newInterval) {
        vector<vector<int>> result;
        result.reserve(intervals.size() + 1);
        int i = 0, n = intervals.size();
        int lo = newInterval[0], hi = newInterval[1];   // don't mutate the caller's arg

        while (i < n && intervals[i][1] < lo)           // strictly before — strict <
            result.push_back(intervals[i++]);

        while (i < n && intervals[i][0] <= hi) {        // overlapping — non-strict <=
            lo = min(lo, intervals[i][0]);
            hi = max(hi, intervals[i][1]);
            i++;
        }
        result.push_back({lo, hi});                     // exactly once, outside the loop

        while (i < n)                                   // strictly after
            result.push_back(intervals[i++]);

        return result;
    }
};
```
**TC:** O(n) — three sequential loops share one index, so every interval is touched once. **No sort** — that's the entire gain over [[1-56-merge-intervals|56]].  **SC:** O(1) auxiliary (output excluded).
*`n == 0` needs no special case* — both loops skip and step 4 still emits `[[newInterval]]`.

## My Solution
```cpp
class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intervals, vector<int>& newInterval) {
        vector<vector<int>>result;
        int i = 0, n = intervals.size();
        // Strictly smaller
        while (i < n && intervals[i][1] < newInterval[0]) {
            result.push_back(intervals[i]); i++;
        }
        // Overlapping Part
        while (i < n && intervals[i][0] <= newInterval[1]) {
            newInterval[0] = min(newInterval[0], intervals[i][0]);
            newInterval[1] = max(newInterval[1], intervals[i][1]);
            i++;
        }
        result.push_back(newInterval);
        // Strictly greater
        while (i < n) {
            result.push_back(intervals[i]); i++;
        }

        return result;
    }
};
```
✅ **Correct — O(n) / O(1)**, the canonical three-zone sweep. Both boundary operators right, `min` and `max` both present, push correctly outside loop 2, `i` never resets, empty input handled for free.
**Refinements:** (1) it **mutates the caller's `newInterval`** (non-const ref, written on lines 47–48) — harmless on LeetCode, but the statement's "you don't need to modify in-place" hints the interviewer is thinking about side effects; copy into `lo`/`hi` first. (2) The `min` can only ever fire on the **first** absorbed interval — the input is start-sorted, so every later start is larger. Keeping it in the loop is clearer and costs nothing, but know the answer if asked to tighten it. (3) `result.reserve(n + 1)` — the final size is bounded exactly.

## Other Approaches
- **Brute force / "reuse 56" — `intervals.push_back(newInterval)`, sort, run the merge sweep.** **O(n log n) / O(1)**. Correct and three lines, and it's the right thing to say **first** — then immediately note that it **throws away the sorted-input guarantee**, which is the exact thing being tested. Say it, then beat it.
- **Three-zone linear sweep** *(canonical)* — **O(n) / O(1)**. The expected answer.
- **Binary-search the two zone boundaries** (`lower_bound` for where zone 1 ends and zone 3 begins, merge only the span between) — comparisons drop to **O(log n)**, but you still copy O(n) intervals into the output, so **TC stays O(n)**. Phrase it as "O(log n) to *locate*, O(n) to *build*" — it only becomes a real win in the persistent-structure follow-up below.
- **Repeated / streaming insertions** — if `insert` is called many times, rebuilding an O(n) array per call is O(n) each. Switch to a `std::map<int,int>` keyed by start and merge only the neighbours around the insertion point: **O(log n) amortised per insert**. This is **LC 715 Range Module** / **LC 352 Data Stream as Disjoint Intervals**, and it's the single most likely follow-up to 57.
- **"What if the input weren't guaranteed non-overlapping (or sorted)?"** → you are back to [[1-56-merge-intervals|56]] exactly: sort + sweep, **O(n log n)**.

> **56 vs 57 — the one-line distinction to say out loud:** *same merge logic, different starting gift*. 56 pays O(n log n) because it must sort; 57 is O(n) because the sort was already done, and that lets the single sweep of 56 become **three zones**. If you find yourself writing `sort()` in 57, you've solved 56 by accident.

## Pitfalls
- **Sorting the input** — the reflex from [[1-56-merge-intervals|56]]. It's not wrong, it's an **O(n log n) answer to an O(n) question**, and the interviewer will read it as "didn't use the constraints".
- **Pushing `newInterval` inside loop 2** — emits one copy per absorbed interval, and **drops it entirely** when the loop never runs (new interval lands in a gap, or `n == 0`). Push once, after.
- **Flipping either boundary operator** — zone 1 must be **strict** (`<`), zone 2 **non-strict** (`<=`). Getting it backwards stops touching intervals from merging: `[[1,3],[6,9]], [3,6]` → `[[1,3],[3,6],[6,9]]` instead of `[[1,9]]`. "Share at least one point" is the sentence that decides it — the **same** convention as 56, the **opposite** of [[3-252-meeting-rooms|252]] / [[5-435-non-overlapping-intervals|435]].
- **Omitting the `min` on the start** — `newInterval` can begin *after* an interval it overlaps: `[[1,5]], [2,3]` → `[[2,5]]` instead of `[[1,5]]`. Same containment trap as 56's `max`, just on the other end.
- **Forgetting `intervals` can be EMPTY** — `0 ≤ n`, unlike 56's `n ≥ 1`. Any code that seeds from `intervals[0]` is UB here. The three-loop form dodges it for free.
- **Resetting `i` between loops, or nesting them** — the zones are contiguous, so one shared index that only ever moves forward is both correct and what makes it O(n).
- **Mutating the caller's `newInterval`** — a side effect the statement quietly warns against; copy to locals.
- **Returning `intervals` instead of `result`** — you never wrote into `intervals`; it still holds the original.
