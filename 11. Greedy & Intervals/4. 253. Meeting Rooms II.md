# 4. 253. Meeting Rooms II (LC 253) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/meeting-rooms-ii/) · 🔗 [GfG — Attend All Meetings II](https://www.geeksforgeeks.org/problems/attend-all-meetings-ii/1)

**Pattern:** Greedy / Intervals — **max concurrency**, computed either with a **min-heap of end times** (rooms currently busy) or a **chronological sweep** (`+1` on a start, `-1` on an end).
**Trigger:** "**minimum number of rooms / machines / platforms / servers**" or "**maximum number of overlapping intervals**" → you need the **peak**, not a bool. The tell versus [[3-252-meeting-rooms|252]] is that the answer is a **count**, so a pairwise adjacent-neighbour scan can no longer produce it.

## Problem (1-liner)
Given `start[]` and `end[]` for `n` meetings, return the **minimum number of rooms** needed so every meeting can run.
**Note:** a meeting may start **exactly when** another ends and reuse its room — intervals are **half-open** `[start, end)`.
**Examples:** `start=[1,10,7], end=[4,15,10] → 1` (sorted: `1-4 · 7-10 · 10-15`, each begins at-or-after the last one ends, so one room recycles) · `start=[2,9,6], end=[4,12,10] → 2` (sorted: `2-4 · 6-10 · 9-12`; `9 < 10` so those two overlap).
**Constraints:** `1 ≤ n ≤ 10⁵`, `0 ≤ start[i] < end[i] ≤ 10⁶`. Never empty, so the answer is **≥ 1**; `start[i] < end[i]` is guaranteed so there are **no zero-length meetings** (which would otherwise make the touching rule ambiguous). Times fit `int`, and only comparisons are performed.

## Idea (1-liner)
The answer is the **maximum number of meetings live at any instant** — because at the busiest moment every live meeting needs its own room, and that many rooms provably suffice (a room freed at time `t` is immediately reusable). So don't reason about *rooms*, reason about **peak overlap**: sort by start, keep the busy rooms' end times in a **min-heap** (the earliest-finishing room is the only one worth reusing), and the heap's high-water mark is the answer.

## Approach
1. **Zip** `start[i]` with `end[i]` into pairs and **sort by start** — you must process meetings in the order they begin, and the pairing must survive the sort.
2. Keep a **min-heap of end times** = the rooms currently occupied. The **min** is the room that frees up soonest, which is the only candidate for reuse.
3. For each meeting `(s, e)`: if `!pq.empty() && pq.top() <= s`, that room has finished → `pop` (reuse it). Then **`push(e)`** unconditionally — this meeting occupies a room either way.
4. Return `pq.size()`.

> **Load-bearing insight #1 — why `pq.size()` at the end IS the maximum.** Each iteration pops **at most one** and pushes **exactly one**, so the heap size is **never decreasing**. A monotone sequence ends at its own maximum, so no separate `best` variable is needed. This is why the canonical code uses **`if`, not `while`**. If you *do* write `while (!pq.empty() && pq.top() <= s) pq.pop();` you are no longer monotone (the size can drop), and you **must** track `best = max(best, pq.size())` yourself — the `while` version with a bare `return pq.size()` is a real wrong answer, not a style nit.
>
> **Load-bearing insight #2 — push *inside* the loop.** The heap models rooms **in use right now**. An end time may only enter when its meeting **starts**. Pre-seeding the heap with all of `end[]` before the loop makes every room occupied from time zero: the size then only shrinks, and the final size counts something else entirely (ends never matched to a later start). See *Pitfalls*.
>
> **Load-bearing insight #3 — the min-heap is the whole greedy.** Why is reusing the **earliest-finishing** room optimal? Any room you could reuse has `end <= s`; picking the smallest such end can never leave you worse off, because it's the one whose availability is *least* useful later. That exchange argument is why one `pq.top()` check replaces searching all rooms.

## Code (clean canonical)
```cpp
class Solution {
public:
    int minMeetingRooms(vector<int> &start, vector<int> &end) {
        int n = start.size();
        vector<pair<int, int>> meetings(n);
        for (int i = 0; i < n; i++) meetings[i] = {start[i], end[i]};
        sort(meetings.begin(), meetings.end());              // by start, pairing intact

        priority_queue<int, vector<int>, greater<>> pq;       // end times of busy rooms
        for (auto &[s, e] : meetings) {
            if (!pq.empty() && pq.top() <= s) pq.pop();       // earliest room freed → reuse
            pq.push(e);                                       // this meeting takes a room
        }
        return pq.size();                                     // size is monotone ⇒ == peak
    }
};
```
**TC:** O(n log n) — sort dominates; `n` heap ops at O(log n).  **SC:** O(n) for the pairs + O(n) worst-case heap (all meetings overlap).

## My Solution
```cpp
class Solution {
  public:
    int minMeetingRooms(vector<int> &start, vector<int> &end) {
        int n = start.size();
        vector<pair<int, int>>meetings(n);
        for (int i = 0; i < n; i++) meetings[i] = {start[i], end[i]};
        sort(meetings.begin(), meetings.end());

        priority_queue<int, vector<int>, greater<>>pq;

        for (auto &[s, e] : meetings) {
            if (!pq.empty() && pq.top() <= s) pq.pop();
            pq.push(e);
        }

        return pq.size();
    }
};
```
**Correct** and already the canonical shape — O(n log n) / O(n). Every load-bearing detail is right: the pairs are zipped **before** sorting so `start[i]`/`end[i]` stay together, `push(e)` is **inside** the loop, `pop` is guarded by `!pq.empty()`, `<=` (not `<`) implements "a meeting may start when another ends", and the `if` (not `while`) keeps `pq.size()` monotone so the bare `return pq.size()` is genuinely the peak. Nothing to fix. Optional polish: `greater<>` needs the `vector<int>` middle argument — you have it; a comment on the `if`-vs-`while` monotonicity is worth writing down because it's the first thing an interviewer will poke at.

**The wrong version worth remembering** (an earlier attempt on this problem) was:
```cpp
for (int num : end) pq.push(num);      // ✗ every room occupied from time 0
sort(start.begin(), start.end());      // ✗ pairing destroyed
for (int num : start)
    while (!pq.empty() && num >= pq.top()) pq.pop();
return pq.size();                      // counts ends never matched to a later start
```

## Other Approaches
- **Brute force over event times** — for each meeting's start time `t`, count how many intervals contain `t`; answer = the max. **O(n²) / O(1)**. Correct (the peak always occurs *at* some start time), and a fine thing to state before optimising — but TLEs at `n = 10⁵`.
- **Min-heap of end times** *(canonical)* — **O(n log n) / O(n)**. The expected answer, and the one that generalises to "which room did meeting `i` get?" if you store room ids alongside the end times.
- **Chronological / two-array sweep** *(alt-optimal, and the one to name)* — sort `start[]` and `end[]` **independently** (the pairing genuinely doesn't matter once you only care about counts), then two pointers:
  ```cpp
  sort(start.begin(), start.end());
  sort(end.begin(), end.end());
  int n = start.size(), i = 0, j = 0, cur = 0, best = 0;
  while (i < n) {
      if (start[i] < end[j]) { cur++; best = max(best, cur); i++; }  // a meeting begins
      else                   { cur--; j++; }                         // a meeting ends
  }
  return best;
  ```
  **O(n log n) / O(1)** beyond the sorts — strictly better space, no heap, and often the cleaner thing to code live. `start[i] < end[j]` **strict** is what lets a start at `t` reuse a room ending at `t`; flip to `<=` for closed intervals. Only `i < n` is needed as the loop condition — `j` can never outrun `i`.
- **Event list with explicit sort** — build `(time, ±1)` pairs, sort with **`-1` before `+1`** on ties (touching is legal), sweep a counter, track the max. **O(n log n) / O(n)**. Same machine as the sweep above but with the tie rule made explicit — mention it when the input arrives as `vector<vector<int>> intervals` rather than two arrays. Get the tie order backwards and `[[1,4],[4,7]]` reports 2 rooms.
- **Difference array / bucket counting** — times ≤ 10⁶, so `diff[start]++`, `diff[end]--`, then a prefix-sum sweep and take the max. **O(n + T) / O(T)** with `T = 10⁶`. Beats the sort when `n` is huge and the time range is small (and it's *the* answer if times were guaranteed tiny), but it's O(T) memory and dies the moment coordinates aren't small integers. Name it, then reach for the heap or the sweep.

> **The trio to be able to distinguish out loud:** *can one room do it?* → [[3-252-meeting-rooms|252]], adjacent-pair scan, **bool**. *How many rooms?* → 253, **peak overlap**, heap or sweep. *Which meetings do I drop so one room suffices?* → [[5-435-non-overlapping-intervals|435]], and there the greedy flips to **sort by END** (earliest-finish-first). Same input shape, three different sorts, three different answers — that's the pattern's core exam question. Identical problem under other names: **Minimum Platforms** (railway), **Car Pooling (LC 1094)**, **My Calendar III (LC 732)**, **Maximum CPU Load**.

## Pitfalls
- **Pre-seeding the heap with all of `end[]`** — the #1 wrong submission. Rooms become occupied before their meetings start, the heap only shrinks, and the peak is never observed. Push `e` **inside** the loop.
- **Sorting `start` and `end` separately and then using them as pairs** — after `sort(start...)`, `start[i]` no longer belongs to `end[i]`. Independent sorts are legal **only** in the two-pointer sweep, which never pairs them.
- **`while` + `return pq.size()`** — popping every finished room breaks the monotonicity that makes the final size equal the maximum. Either use `if`, or use `while` **and** track `best = max(best, pq.size())`.
- **`<` instead of `<=` in the heap check** (or `<=` instead of `<` in the sweep) — refuses to reuse a room for a meeting that starts exactly when one ends, inflating the answer by 1 on `[1,4],[4,7]`. The note in the statement is the spec.
- **Forgetting `!pq.empty()`** — `pq.top()` on an empty `priority_queue` is **UB**, not 0, and the heap *is* empty on the very first meeting.
- **Default `priority_queue` is a max-heap** — without `greater<>` (plus the `vector<int>` middle argument) `top()` is the **latest**-finishing room, which is never reusable, so nothing is ever popped and you return `n`.
- **Returning the count of overlapping *pairs*** — the answer is peak concurrency, not the number of conflicting pairs. Three mutually overlapping meetings are 3 pairs but 3 rooms; scaling doesn't match in general.
- **Answering 0 for `n == 1`** — the input is never empty, so the answer is at least 1. The canonical loop handles it for free (one push, no pop).
- **`pq.size()` is unsigned** — returning it as `int` is fine here but warns; cast if the compiler is strict.
