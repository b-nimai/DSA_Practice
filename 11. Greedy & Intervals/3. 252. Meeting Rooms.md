# 3. 252. Meeting Rooms (LC 252) — Easy
🔗 [Open on LeetCode](https://leetcode.com/problems/meeting-rooms/) · 🔗 [GfG — Attend All Meetings](https://www.geeksforgeeks.org/problems/attend-all-meetings/1)

**Pattern:** Greedy / Intervals — **sort by start, then one linear neighbour check.** The seed problem of the whole pattern: it establishes that after sorting by start, *any* overlap in the set is guaranteed to show up between **adjacent** intervals.
**Trigger:** "can **one** person / **one** room handle **all** these intervals?" → sort by start, scan pairs, fail on `next.start < cur.end`. The tell is that the answer is a **bool** and the count of resources is fixed at **1** — the moment it asks *how many* rooms, it becomes [[4-253-meeting-rooms-ii|253]].

## Problem (1-liner)
Given intervals `arr[i] = [start, end]`, return whether **all** meetings can be attended by one person — i.e. whether **no two intervals overlap**.
**Note:** a meeting is attendable if its `start >= previous end`, so **touching is allowed** (`[1,4]` then `[4,7]` is fine).
**Examples:** `[[1,4],[10,15],[7,10]] → true` (sorted: `1-4 · 7-10 · 10-15`, each starts at-or-after the last end) · `[[2,4],[9,12],[6,10]] → false` (sorted: `2-4 · 6-10 · 9-12`, and `9 < 10`).
**Constraints:** `1 ≤ n ≤ 10⁵`, `0 ≤ times ≤ 2·10⁶`. Input is **never empty**; `n == 1` must return `true` (no pair exists to conflict). Values fit `int` easily, and no arithmetic is done on them — only comparisons.

## Idea (1-liner)
Overlap is a property of *pairs*, so the brute force is O(n²) — but **sort by start time and every overlap collapses onto a neighbour**: once starts are ascending, if meeting `i+1` doesn't clash with `i`, it can't clash with anything before `i` either (their ends are all bounded by the check that already passed). So one pass over adjacent pairs is enough.

## Approach
1. **Sort** `arr` ascending by start time.
2. Walk `i = 1 … n-1` and compare each meeting against **only its predecessor**.
3. If `arr[i][0] < arr[i-1][1]` — this meeting starts **strictly before** the previous one ends → overlap → `return false`.
4. Survive the loop → `return true`.

> **Load-bearing insight:** *why is checking only adjacent pairs sufficient?* After sorting by start, take any `j > i+1`. Then `arr[j][0] >= arr[i+1][0]`. If the adjacent check passed we know `arr[i+1][0] >= arr[i][1]`, so `arr[j][0] >= arr[i][1]` too — **the far pair is automatically safe**. Sorting turns a quadratic all-pairs question into a linear neighbour question. That single argument is the foundation of the entire Greedy/Intervals pattern ([[1-56-merge-intervals|56]], [[2-57-insert-interval|57]], [[5-435-non-overlapping-intervals|435]] all reuse it).
>
> **Second insight — `<` vs `<=` is dictated by the problem, not taste.** Here "start ≥ previous end" is attendable, so intervals are **half-open** `[start, end)` and only `next.start < cur.end` is a conflict. If a problem instead says meetings sharing an endpoint conflict (closed intervals), the test becomes `<=`. Read the note; don't guess.

## Code (clean canonical)
```cpp
class Solution {
public:
    bool canAttend(vector<vector<int>> &arr) {
        sort(arr.begin(), arr.end(),
             [](const vector<int> &a, const vector<int> &b) { return a[0] < b[0]; });

        for (size_t i = 1; i < arr.size(); i++) {
            if (arr[i][0] < arr[i - 1][1]) return false;   // starts before prev ends
        }
        return true;
    }
};
```
**TC:** O(n log n) — the sort dominates; the scan is O(n).  **SC:** O(log n) — sort's recursion stack only; the sort is in place and no extra structure is built.

## My Solution
```cpp
class Solution {
  public:
    bool canAttend(vector<vector<int>> &arr) {
        sort(arr.begin(), arr.end());

        for (int i = 0; i < arr.size() - 1; i++) {
            if (arr[i + 1][0] < arr[i][1]) return false;
        }

        return true;
    }
};
```
**Correct** — same O(n log n) / O(log n), and the `<` (not `<=`) matches the "start ≥ previous end is fine" rule exactly. Verified on both examples and on `n == 1` (`size()-1 == 0`, loop body never runs → `true`). Refinements: **(1)** `arr.size() - 1` is an **unsigned** expression — safe here *only* because the constraints promise `n ≥ 1`; with `n == 0` it wraps to `SIZE_MAX` and `arr[i+1]` reads out of bounds. Looping `for (size_t i = 1; i < arr.size(); i++)` with `arr[i-1]` can never underflow and also kills the signed/unsigned comparison warning from `int i < arr.size()`. **(2)** `sort(begin, end)` compares the whole vector (start, then end) — only the **start** matters, so a `[](a,b){ return a[0] < b[0]; }` comparator states the intent (and is marginally cheaper). **(3)** Worth saying out loud in an interview: this **mutates the caller's input**; if the input must be preserved, sort a copy or an index array at O(n) extra space.

## Other Approaches
- **All-pairs overlap check** *(brute)* — for every `i < j`, test `max(s_i,s_j) < min(e_i,e_j)`. **O(n²) / O(1)**. Correct and needs no sort, but TLEs at `n = 10⁵` (~5·10⁹ pairs). Say it, then say "sorting makes the far pairs redundant" — that sentence *is* the interview answer.
- **Sort by start + adjacent scan** *(canonical)* — **O(n log n) / O(log n)**. The expected solution. Sorting by **end** also works for this bool version, but sorting by **start** is the habit to build because every harder interval problem needs it.
- **Sweep line / chronological events** — emit `(start, +1)` and `(end, -1)`, sort by time (ties: process `-1` **before** `+1`, since touching is legal), sweep a running counter and fail if it ever exceeds 1. **O(n log n) / O(n)**. Overkill here, but it's the *general* machine: change the threshold from 1 to k and you've solved "can k rooms host everything", and track the counter's maximum and you've solved 253 outright.
- **Counting / bucket by time** — times ≤ 2·10⁶, so a `diff[]` array of size 2·10⁶+2 with `+1`/`-1` and a prefix sweep gives **O(n + T) / O(T)**. Beats the sort asymptotically when `n` is huge and `T` tiny; here `T ≫ n log n`, so mention it, don't code it.

> **The follow-up to expect: [LC 253 Meeting Rooms II](https://leetcode.com/problems/meeting-rooms-ii/)** — *minimum number of rooms*. The bool answer no longer generalises; you need the **peak concurrency**. Two ways: **(a) min-heap of end times** — sort by start, push each end, and pop while `heap.top() <= start` (those meetings have finished); the answer is the max heap size. **(b) Chronological/two-array sweep** — sort all starts and all ends separately, two pointers, `+1` on a start and `-1` on an end, track the maximum. Both **O(n log n)**, (a) O(n) space, (b) O(n) but usually cleaner to code. Being able to say "252 is a *pairwise* question, 253 is a *max-overlap* question, and that's why one is a scan and the other needs a heap" is the whole point of the pair.

## Pitfalls
- **Not sorting** — the raw input is deliberately shuffled in both examples (`[[1,4],[10,15],[7,10]]`). Without the sort the adjacent-pair argument is void and you'll return `false` on a perfectly attendable set.
- **`<=` instead of `<`** — turns the legal back-to-back `[1,4],[4,7]` into a false conflict. The note "start ≥ previous end" is the spec; intervals are half-open.
- **`i < arr.size() - 1` with unsigned `size()`** — only safe because `n ≥ 1`. Loop from `i = 1` and compare to `i-1` so an empty vector can never underflow into an out-of-bounds read.
- **Comparing against a running `maxEnd` instead of the previous end** — harmless *here* (after sorting by start, the previous end being exceeded is exactly what the check catches, and any earlier meeting was already validated), but it's the crutch that breaks when you carry it into problems where intervals get merged. Compare to the **predecessor**.
- **Sorting by end time and then reusing that habit** — fine for this bool, silently wrong for [[1-56-merge-intervals|merge]]-style problems, which need ascending starts.
- **Forgetting `n == 1`** — one meeting is always attendable; make sure the loop simply doesn't execute rather than special-casing it.
- **Mutating the caller's array without saying so** — a one-line remark that earns free points.
