# 12. 1326. Minimum Number of Taps to Open to Water a Garden (LC 1326) — Hard
🔗 [Open on LeetCode](https://leetcode.com/problems/minimum-number-of-taps-to-open-to-water-a-garden/)

**Pattern:** Greedy — **minimum interval cover** = [[8-45-jump-game-ii|45 Jump Game II]] with the ranges handed to you explicitly instead of read off `nums[i]`. Two shapes: **sort by start + level sweep** (general, O(n log n)) or **bucket by start into `maxReach[]` + the literal 45 loop** (O(n), available only because the taps sit on integer points). Sibling of **1024 Video Stitching** — same problem, different wrapper.
**Trigger:** "**cover the whole segment `[0, n]`**" + "**minimum number of intervals**" + "**return -1 if impossible**". The tells: each item is an **interval, not a point** (`[i − r[i], i + r[i]]`), the answer is a **count** (so merging — which only answers *"is it covered?"* — is the wrong tool), and a **gap ⇒ -1** (unlike 45, reachability is *not* guaranteed). Whenever the input converts to "intervals over a line, cover it with the fewest", this is the engine.

## Problem (1-liner)
Garden spans `[0, n]`; tap `i` (at point `i`, for `i = 0..n`) waters `[i − ranges[i], i + ranges[i]]`. Return the **minimum taps** to cover all of `[0, n]`, or `-1`.
**Examples:** `n=5, ranges=[3,4,1,1,0,0] → 1` (tap 1 covers `[-3,5]` ⊇ `[0,5]`) · `n=3, ranges=[0,0,0,0] → -1` (every tap covers a single point, gaps everywhere).
**Constraints:** `1 ≤ n ≤ 10⁴`, `ranges.length == n + 1`, `0 ≤ ranges[i] ≤ 100`. **Edges:** `ranges[i] == 0` ⇒ a **degenerate `[i,i]` interval** that covers nothing usable — it can never extend the frontier · left ends go **negative** (`i − ranges[i]` down to `−100`) ⇒ clamp to 0 or handle the sign · `n ≥ 1` so the answer is never 0 · coordinates are small (`≤ 10⁴ + 100`) which is exactly what unlocks the O(n) bucket.

## Idea (1-liner)
Repeatedly jump the covered frontier to the **furthest right end** among all intervals that **start at or before** it; each jump = one tap, no progress = `-1`.

## Approach
1. Convert tap `i` → interval `[i − ranges[i], i + ranges[i]]`.
2. Keep `covered = 0` (everything in `[0, covered]` is watered) and `taps = 0`.
3. Scan every interval whose **start ≤ `covered`**, tracking `farthest = max(end)`.
4. If `farthest == covered` → nothing reaches past the frontier ⇒ **`-1`**.
5. Else `covered = farthest`, `taps++`. Repeat until `covered ≥ n`.

> **Load-bearing insight #1 — it is Jump Game II, not Merge Intervals.** Merging answers a **bool** ("is `[0,n]` covered?"); a merged run of 5 intervals might need only 2 taps, so merging can never produce the **count**. The right frame is BFS levels on a line: level `k` = the contiguous prefix coverable by `k` taps. `covered` is 45's `curEnd`, `farthest` is 45's `farthest`, and `taps` is the BFS depth ⇒ first arrival is optimal by construction.

> **Load-bearing insight #2 — the pointer never resets, and that's the whole complexity argument.** In the sorted sweep, once an interval's start is `≤ covered` it stays usable forever (`covered` only grows), so the inner `while` consumes each interval **exactly once across the entire outer loop**. Re-scanning from the beginning each round is the natural-looking mistake and it's O(n²).

> **Load-bearing insight #3 — the sort is avoidable *here* only because taps sit on integer points.** `0 ≤ i ≤ n ≤ 10⁴` means you can bucket: `maxReach[max(0, i − r[i])] = max(…, i + r[i])`, keeping only the best interval per start. That collapses `n+1` intervals into an `n+1` array, and the problem becomes *literally* `nums[]` for Jump Game II ⇒ O(n), no comparator. With arbitrary real-valued intervals (1024's general form) the sort is mandatory.

> **Load-bearing insight #4 — you never choose *which* tap.** The greedy commits only to the next **window** and defers the pick; `farthest` already names the best member. Grabbing the tap with the largest range, or the one reaching furthest *right now* before finishing the window scan, is the classic wrong greedy.

## Code (clean canonical) — O(n) bucket version
```cpp
class Solution {
public:
    int minTaps(int n, vector<int>& ranges) {
        vector<int> maxReach(n + 1, 0);
        for (int i = 0; i <= n; i++) {
            int l = max(0, i - ranges[i]);              // covering left of 0 is wasted
            maxReach[l] = max(maxReach[l], i + ranges[i]);
        }

        int taps = 0, curEnd = 0, farthest = 0;
        for (int i = 0; i < n; i++) {                   // i = 0..n-1: points we DEPART from
            farthest = max(farthest, maxReach[i]);
            if (i == curEnd) {                          // frontier caught up ⇒ open a tap
                if (farthest <= i) return -1;           // stuck: nothing reaches past i
                taps++;
                curEnd = farthest;
            }
        }
        return taps;
    }
};
```
**TC:** **O(n)** — two linear passes, no sort.  **SC:** **O(n)** — the `maxReach` bucket.
*`maxReach` is only ever **read** at `i < n`, so `i + ranges[i]` overshooting past `n` is harmless — it's compared, never used as a subscript.*

## My Solution (sorted sweep — the general form)
```cpp
class Solution {
public:
    int minTaps(int n, vector<int>& ranges) {
        vector<vector<int>> range;
        for (int i = 0; i < (int)ranges.size(); i++)
            range.push_back({i - ranges[i], i + ranges[i]});

        sort(range.begin(), range.end());               // default = by start, then end

        int taps = 0, covered = 0, i = 0, m = range.size();

        while (covered < n) {
            int farthest = covered;
            while (i < m && range[i][0] <= covered)      // `i` NEVER resets ⇒ O(n) total
                farthest = max(farthest, range[i++][1]);

            if (farthest == covered) return -1;          // gap
            covered = farthest;
            taps++;
        }
        return taps;
    }
};
```
**TC:** **O(n log n)** (the sort dominates).  **SC:** **O(n)**.
**Two fixes from the first draft:** (1) `bool comparetor(...)` as a **non-static member function** doesn't compile as a comparator — the hidden `this` parameter breaks the signature; make it `static`, use a lambda, or drop it entirely since the **default `vector<int>` lexicographic sort already orders by start then end**. (2) The half-written `merge` loop was heading for **Merge Intervals**, which is the wrong algorithm — it yields a bool, not a minimum count (insight #1). The explicit `if (a[0]==b[0]) return a[1] > b[1];` tie-break is harmless but not load-bearing: the sweep takes a `max` over ends anyway.
**Say this version first in an interview** — it's the honest answer for arbitrary intervals — then note that *here* the taps are indexed by integer position, which buys the bucket and drops the sort.

## Other Approaches
- **Brute force — try every subset of taps.** Check coverage of each. **O(2ⁿ · n)**. Name it and kill it instantly at `n = 10⁴`; useful only as a random-test oracle at `n ≤ 15`.
- **Interval DP.** `dp[j] = min over intervals covering j of (dp[start] + 1)`, `dp[0] = 0`, answer `dp[n]` (`INT_MAX` ⇒ `-1`). **O(n · maxRange) / O(n)** — passes at `ranges[i] ≤ 100` (≈10⁶ ops) and is the **safe fallback if you can't prove the greedy**. Also the version that survives once taps get **weights/costs**, where greedy dies outright.
- **Sorted sweep** — **O(n log n) / O(n)**. The general minimum-interval-cover algorithm; write this if the intervals aren't point-indexed.
- **Bucket + Jump Game II** *(optimal)* — **O(n) / O(n)**. The expected answer here.
- **Follow-ups to pre-empt:** *"which taps?"* → store the argmax alongside `farthest` and backtrack. *"taps have costs?"* → greedy breaks (the cheapest cover ≠ the fewest); it becomes DP / shortest path. *"cover `[0,n]` with intervals given as an arbitrary list?"* → **LC 1024 Video Stitching**, same sweep. *"better than O(n)?"* → no, every tap must be read.

> **The one-pass-accumulator family to distinguish out loud:** *extend a frontier, **fail** when the index outruns it* → [[7-55-jump-game|55]]. *extend a frontier, **count** when the index catches it* → [[8-45-jump-game-ii|45]] and **1326**. *extend a frontier, **cut** when the index catches it* → [[9-763-partition-labels|763]]. *accumulate a signed sum, **restart** on negative* → [[10-134-gas-station|134]]. **1326 = 45 + the `-1` case**, because reachability is no longer guaranteed.

## Pitfalls
- **Merging intervals instead of sweeping levels** — *the* signature wrong turn (and the one this file started with). Merging tells you the garden *is* coverable; it cannot tell you with how few taps.
- **Loop to `n`, not `n-1`, in the bucket version** — inherited straight from [[8-45-jump-game-ii|45]]: index `n` is an **arrival**, not a departure, so including it counts a tap you never open.
- **Forgetting the `-1` path** — 45 guarantees reachability, 1326 does **not**. The signal is `farthest <= i` (bucket) / `farthest == covered` (sorted), and it must be checked **before** incrementing `taps`.
- **Not clamping `i - ranges[i]` to 0** — the left end goes as low as `−100`; unclamped it's an out-of-bounds subscript in the bucket version (UB, not a wrong answer).
- **Treating `ranges[i] == 0` as "skip this tap"** — it's a real but degenerate `[i,i]` interval. Don't special-case it; the `farthest` comparison already ignores it, exactly like the `nums[i] == 0` non-trap in [[7-55-jump-game|55]].
- **Resetting the scan pointer each round** in the sorted version — turns O(n log n) into O(n²); the monotonicity of `covered` is precisely what makes one pass legal.
- **Passing a non-`static` member function to `sort`** — doesn't compile (hidden `this`). Use `static`, a lambda, or the default `vector<int>` ordering.
- **`>=` vs `>` on the frontier test** — `farthest == covered` means *no progress*; `farthest > covered` is required to open a tap. Using `>=` loops forever.
- **Keeping every interval per start in the bucket version** — only the **furthest-reaching** one per start matters; the `max` on write is what makes an array (not a list of lists) sufficient.
- **Reaching for a heap or Dijkstra** — every tap costs 1, so all edges are unit-weight; BFS-by-levels is already optimal and a priority queue is pure overhead.

**Family map:** the **explicit-intervals** twin of [[8-45-jump-game-ii|45 Jump Game II]] — identical `curEnd`/`farthest`/`jumps` loop, with `maxReach[]` replacing `i + nums[i]` and a `-1` branch added because reachability isn't guaranteed · shares the frontier intuition with [[7-55-jump-game|55 Jump Game]] and the cut-on-catch-up loop with [[9-763-partition-labels|763 Partition Labels]] · direct alias **LC 1024 Video Stitching** (same sweep, intervals given as a raw list ⇒ sort mandatory) · the sorted version is the classic **minimum interval cover**, the *covering* dual of the *packing* greedies [[5-435-non-overlapping-intervals|435]] / [[6-452-minimum-number-of-arrows-to-burst-balloons|452]] (those sort by **end** to keep the most; this sorts by **start** to advance a frontier) · the DP fallback is the same shape as **LC 1235 Weighted Job Scheduling**, the tool you need the moment taps gain costs · breaks at **1306** (backwards moves ⇒ BFS) and **1696** (weights ⇒ monotonic-deque DP).
