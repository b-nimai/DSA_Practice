# 8. 45. Jump Game II (LC 45) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/jump-game-ii/)

**Pattern:** Greedy — **layered furthest-reach frontier** (implicit BFS on an array). Same `reach` engine as [[7-55-jump-game|55]], but instead of one flat frontier you cut it into **levels**: everything reachable in exactly `k` jumps forms a contiguous window, and the answer is the number of windows you cross.
**Trigger:** "**minimum number of jumps to reach the last index**" — reachability is *guaranteed*, the answer is a **count**, not a bool. Whenever a problem is "shortest number of moves on an unweighted line where each position advertises a range", it's **BFS**, and BFS-on-a-line collapses to two pointers (`curEnd`, `farthest`) in O(1) space. The tell versus [[7-55-jump-game|55]]: 55 asks *can I*, 45 asks *how few*.

## Problem (1-liner)
`nums[i]` = **maximum** forward jump from index `i` (you may jump any `j` with `0 ≤ j ≤ nums[i]` and `i + j < n`). Starting at index `0`, return the **minimum number of jumps** to reach index `n-1`. **The test cases guarantee the end is reachable**, so you never return `-1`.
**Examples:** `[2,3,1,1,4] → 2` (0→1, then 3 steps to the end) · `[2,3,0,1,4] → 2` · `[0] → 0` (**already at the last index — zero jumps**) · `[1,1,1,1] → 3` (forced single steps) · `[5,1,1,1,1,1] → 1` (one jump clears everything).
**Constraints:** `1 ≤ n ≤ 10⁴` — **never empty**, and `n == 1` must return **0**, not 1. `0 ≤ nums[i] ≤ 1000` — non-negative (no backwards moves) and **bounded by 1000 < n**, so unlike [[7-55-jump-game|55]] `i + nums[i]` can't blow far past the array, but it can still exceed `n-1`. Guaranteed reachable ⇒ **no zero-wall handling needed** (a `[3,2,1,0,4]` input simply won't appear). `n ≤ 10⁴` tolerates O(n²), but the intended answer is **O(n)**.

## Idea (1-liner)
Sweep once carrying `curEnd` = last index of the **current jump level** and `farthest` = furthest index anything in this level can reach; when `i` hits `curEnd`, you've exhausted the level ⇒ `jumps++` and the new level becomes `[curEnd+1, farthest]`.

## Approach
1. `jumps = 0`, `curEnd = 0`, `farthest = 0`.
2. For `i = 0 .. n-2` — **stop at `n-2`, this is load-bearing**:
   - `farthest = max(farthest, i + nums[i]);` — widen the *next* level.
   - `if (i == curEnd) { jumps++; curEnd = farthest; }` — the current level is spent; commit to a jump.
3. Return `jumps`.

> **Load-bearing insight — this is BFS, written without a queue.** Level 0 = `{0}`, level 1 = every index reachable in one jump = a **contiguous window** `[1, nums[0]]`, level 2 = `[curEnd+1, farthest]`, … Because each level is an unbroken interval (you may jump *any* length, so no holes), the queue is fully described by its two endpoints — so BFS's O(n) queue collapses to two ints. `jumps` is the BFS **depth**, which is exactly why the greedy is optimal: BFS's first arrival at `n-1` is the shortest path, by construction.
>
> **Load-bearing insight #2 — the loop MUST stop at `n-2`.** If `i` reaches `n-1` and it happens to equal `curEnd`, you increment `jumps` for a level you never needed to leave — `[2,3,1,1,4]` returns **3** instead of 2, and `[0]` returns **1** instead of 0. You are already *at* the destination when you arrive; the jump is counted when you **leave** a level, not when you land. This one bound is the single most common wrong submission.
>
> **Load-bearing insight #3 — you never pick *which* index to jump to.** The greedy commits only to "somewhere in the next window", deferring the actual choice. That's what makes it safe: the best index in a window is whichever has the max `i + nums[i]`, and `farthest` already tracks it without you naming it. Trying to greedily jump to the *furthest index* at each step instead (`i += nums[i]`) is **wrong** — `[2,3,1,1,4]`: 0→2→3→4 = 3 jumps, not 2. The optimal first hop is to index 1, which is *nearer* but launches further.

## Code (clean canonical)
```cpp
class Solution {
public:
    int jump(vector<int>& nums) {
        int n = nums.size();
        int jumps = 0, curEnd = 0, farthest = 0;
        for (int i = 0; i < n - 1; i++) {          // n-1, NOT n
            farthest = max(farthest, i + nums[i]);
            if (i == curEnd) {                     // level exhausted → must jump
                jumps++;
                curEnd = farthest;
            }
        }
        return jumps;
    }
};
```
**TC:** O(n) — one pass, each index touched once.  **SC:** O(1) — three ints, no queue, no table. Does **not** mutate the input.
*`n == 1` → the loop body never runs → returns `0`.* No special-case needed.

## Other Approaches
- **Brute-force recursion — try every jump length from every index and take the min.** `f(i) = 1 + min(f(i+1..i+nums[i]))`. **O(2ⁿ) / O(n)** stack. The honest baseline; name it, don't submit it.
- **Top-down memo / bottom-up DP** — `dp[i]` = min jumps from `i` to the end, filled backwards: `dp[i] = 1 + min(dp[i+1..i+nums[i]])`, `dp[n-1] = 0`, guard with `INT_MAX`. **O(n²) / O(n)**. AC's at `n ≤ 10⁴` and is the natural first *correct* answer — say it out loud, then note the inner loop re-scans ranges the greedy handles with one `max`.
- **Explicit BFS with a queue + visited array** — **O(n) / O(n)**. Correct and worth mentioning because it *names* the structure, but the queue is redundant once you see each level is an interval. Its one advantage: it survives the variant where jumps can go **backwards** (LC 1306), where the greedy dies.
- **Greedy level-sweep (`curEnd` / `farthest`)** *(canonical)* — **O(n) / O(1)**. The expected answer.
- **Two-pointer window form** *(same algorithm, alt phrasing)* — `while (curEnd < n-1) { farthest = max over [l..curEnd] of i+nums[i]; l = curEnd+1; curEnd = farthest; jumps++; }`. **O(n) / O(1)** since the windows partition the array. Reads more explicitly as BFS levels; some interviewers prefer it because the "level" is visible in the code. Also naturally returns `-1` (an unmoved `farthest`) if reachability *weren't* guaranteed — the clean way to answer the "what if I drop the guarantee?" follow-up.

> **The frontier family to distinguish out loud:** *can I reach the end?* → [[7-55-jump-game|55]], **one** `reach`, bool, fail on `i > reach`. *How few jumps?* → **45**, the **same** frontier split into levels, count the level changes. **Counting `reach` updates in 55 does not give 45's answer** — you'd count extensions, not jumps. *Backwards moves allowed?* → **LC 1306 Jump Game III** — the reachable set stops being a contiguous prefix ⇒ plain BFS/DFS + visited. *Jumps carry scores/costs?* → **LC 1696 Jump Game VI** — unweighted BFS is invalid ⇒ DP + monotonic deque. **The greedy lives exactly as long as "reachable in ≤ k jumps" stays a contiguous prefix.**

## Pitfalls
- **Looping to `n-1` instead of `n-2`** — *the* signature bug. Landing on the last index and finding `i == curEnd` bumps `jumps` for a departure you never make: `[2,3,1,1,4]` → 3, `[0]` → 1. Both wrong. Loop `i < n - 1`.
- **Greedily jumping to the furthest reachable index (`i += nums[i]`)** — intuitive and **wrong**. `[2,3,1,1,4]` gives 3; the optimal first hop lands on the *nearer* index 1 because it launches further. The greedy must commit to a **window**, never to an index.
- **Updating `curEnd` before `farthest`** — order matters inside the loop: extend `farthest` with the current `i` *first*, then test `i == curEnd`. Swapped, the level boundary is computed from stale data.
- **Returning `curEnd`/`farthest` instead of `jumps`** — those are indices, not a count.
- **Forgetting `n == 1` in a hand-rolled variant** — the answer is **0**. The canonical loop gets it free; a `do/while` or a `jumps = 1` seed does not.
- **Treating an unreachable input as possible** — the constraints *guarantee* reachability, so no `-1` path is needed here; but if the interviewer removes the guarantee, the correct signal is `curEnd` failing to advance (`farthest == curEnd`), **not** `nums[i] == 0` (you can jump over zeros — inherited from [[7-55-jump-game|55]]).
- **Reaching for Dijkstra / a weighted graph** — every edge costs 1, so BFS is the right tool and Dijkstra is a `log n` you pay for nothing.
- **Sorting anything** — reflex from the interval half of this pattern. Order **is** the problem.
