# 9. 763. Partition Labels (LC 763) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/partition-labels/)

**Pattern:** Greedy — **furthest-reach frontier on a string**. Literally [[8-45-jump-game-ii|45]]'s loop with `curEnd` renamed `end`: extend a frontier, cut when the index catches it. Equivalently, an **interval-merge in disguise** — each letter is the interval `[first(c), last(c)]`, and the parts are the merged connected components.
**Trigger:** "**partition into as many parts as possible so that each letter appears in at most one part**" — the tells are (a) **as many as possible** (maximise the count ⇒ cut as early as legally allowed ⇒ greedy), (b) **order is preserved** (concatenating the parts must rebuild `s`, so you may not sort or regroup), (c) the alphabet is **bounded at 26** ⇒ an O(1) table exists. Whenever "this element can't cross the boundary" means "the boundary must stretch to its last occurrence", you're in this problem.

## Problem (1-liner)
Given a string `s`, cut it into the **maximum number of contiguous parts** such that **every letter lives in exactly one part** (a letter may repeat *inside* a part, never across two). The parts concatenated in order must equal `s`. Return the **sizes** of the parts, in order.
**Examples:** `"ababcbacadefegdehijhklij" → [9,7,8]` (`"ababcbaca"`, `"defegde"`, `"hijhklij"`) · `"eccbbbbdec" → [10]` (`e` first appears at 0 and last at 9 ⇒ nothing can be cut) · `"a" → [1]` · `"abc" → [1,1,1]` (all distinct ⇒ every char is its own part) · `"aaaa" → [4]`.
**Constraints:** `1 ≤ |s| ≤ 500` — **never empty**, and the result is **never empty** (there is always ≥ 1 part). `s` is **lowercase English only** ⇒ a `int[26]` table, **O(1) space**. `n ≤ 500` means even O(n²) passes, but the intended answer is **O(n)**.

## Idea (1-liner)
Precompute each letter's **last index**; sweep left→right stretching `end = max(end, last[s[i]])`, and the moment `i == end` **every letter opened in this window is finished** ⇒ cut here.

## Approach
1. Pass 1 — `last[c] = i` for every `i` (the final write wins, so `last[c]` ends up as the **last occurrence**).
2. `start = 0`, `end = 0`.
3. Pass 2 — for `i = 0 .. n-1`:
   - `end = max(end, last[s[i] - 'a']);` — this letter forces the part to stretch at least to its last occurrence.
   - `if (i == end) { res.push_back(i - start + 1); start = i + 1; }` — the frontier has been caught; nothing inside can appear later.
4. Return `res`.

> **Load-bearing insight — the cut condition is "the window has caught its own frontier", not "this letter ended".** `end` is the max over the last-occurrences of **every letter seen so far**, so `i == end` certifies *all* of them are exhausted simultaneously. Checking only `i == last[s[i]]` is wrong: in `"abab..."`, index 2 is the last `a` in a prefix sense but `b` is still open.
>
> **Load-bearing insight #2 — greedy is optimal because the cut is FORCED, not chosen.** Every index in `[start, end]` is *provably* stuck in the same part (letter `c` at `start` mandates everything up to `last[c]`, transitively). So `end` is the **earliest legal cut**, and cutting at the earliest legal point at every step maximises the number of parts — there is no alternative to weigh, hence no exchange argument needed. This is stronger than the usual greedy: it's a **connected-components** argument.
>
> **Load-bearing insight #3 — this is interval merging with the sort for free.** Each letter is the interval `[first(c), last(c)]`; the parts are exactly the merged overlapping groups. Normally merging costs O(n log n) for the sort — here the sweep visits indices in increasing order, so the intervals arrive **already sorted by start**. That's why it's O(n) and why "sort the intervals" is a wasted reflex.

## Code (clean canonical)
```cpp
class Solution {
public:
    vector<int> partitionLabels(string s) {
        int n = s.size();
        int last[26] = {};
        for (int i = 0; i < n; i++) last[s[i] - 'a'] = i;   // last write wins

        vector<int> res;
        int start = 0, end = 0;
        for (int i = 0; i < n; i++) {
            end = max(end, last[s[i] - 'a']);               // stretch the frontier
            if (i == end) {                                  // caught it → safe cut
                res.push_back(i - start + 1);
                start = i + 1;
            }
        }
        return res;
    }
};
```
**TC:** O(n + 26) = **O(n)** — two linear passes.  **SC:** **O(1)** — a fixed 26-int table (output excluded).
*Unlike [[8-45-jump-game-ii|45]] the loop runs to `n-1`, not `n-2`* — here the last index **must** trigger a cut (it closes the final part); there, arriving at the end must **not** count a departure.

## My Solution
```cpp
class Solution {
public:
    vector<int> partitionLabels(string s) {
        vector<int>freq(26, 0), count(26, 0), result;
        for (char ch : s) freq[ch - 'a']++;

        int numOfChar = 0, filled = 0, start = 0;
        for (int end = 0; end < (int)s.size(); end++) {
            char ch = s[end];
            if (count[ch - 'a']++ == 0) numOfChar++;   // first sighting → new open letter
            if (count[ch - 'a'] == freq[ch - 'a']) filled++;   // this letter is exhausted
            if (numOfChar == filled) {                 // every open letter is closed
                result.push_back(end - start + 1);
                start = end + 1;
            }
        }
        return result;
    }
};
```
✅ **Correct — same O(n)/O(1)**, just a different certificate for the same cut. Instead of "the window caught its furthest last-index", it counts **distinct letters opened** vs **distinct letters fully consumed**; `numOfChar == filled` ⟺ `i == end`. `filled` can't double-count because `count[c]` reaches `freq[c]` exactly once and never exceeds it. Arguably more intuitive; the canonical version has fewer moving parts.
**Refinements:** `end < s.size()` compares `int` to `size_t` ⇒ `-Wsign-compare` (hoist `int n = s.size()`); and you can drop the `count` array entirely by **decrementing** `freq` — `if (!seen[c]) { seen[c] = true; numOfChar++; } if (--freq[c] == 0) filled++;`.

## Other Approaches
- **Brute force — for every candidate cut, verify no letter straddles it.** Try each prefix length, scan the rest of the string for a repeat of any letter in the prefix. **O(n³)** naive / **O(n²)** with a per-prefix seen-set. Name it as the baseline; the O(n²) form even AC's at `n ≤ 500`, which is worth saying out loud before optimising.
- **Explicit intervals + merge** — build `[first(c), last(c)]` for the ≤ 26 present letters, sort by start, merge overlapping, output the merged lengths. **O(26 log 26 + n) ≈ O(n) / O(1)**. Slower constant and more code, but it's the version to reach for when the "letters" become **arbitrary keys** (unbounded alphabet, words, IDs) — then the table dies and the sort is real. Best answer to "what if `s` were Unicode?".
- **Last-index + reach sweep** *(canonical)* — **O(n) / O(1)**. The expected answer.
- **Open-count sweep (your version)** — **O(n) / O(1)**. Equally optimal; mention it as the "count what's open" phrasing of the same frontier.
- **Follow-up worth pre-empting: "minimise the parts instead"** → trivially `[n]` (one part is always legal), which is a nice way to show you understand *why* maximising is the interesting direction.

> **The frontier family to distinguish out loud:** *can I reach the end?* → [[7-55-jump-game|55]], one `reach`, bool. *How few jumps?* → [[8-45-jump-game-ii|45]], the same frontier cut into levels, count the cuts. *Where are the cuts?* → **763**, the same frontier again, but the frontier is set by **last-occurrence** instead of `i + nums[i]`, and you emit the **widths**. All three are one loop, one running max, and a `i == end` test. The variant to know: **LC 768 Max Chunks To Make Sorted II** — identical shape (`cut when prefix-max ≤ suffix-min`), and **LC 769** is its `[0..n-1]`-permutation special case (`cut when max(prefix) == i`).

## Pitfalls
- **Cutting on `i == last[s[i]]` instead of `i == end`** — *the* signature bug. It ignores the letters still open from earlier in the window: `"ababcbaca..."` would cut at the last `a` of a prefix while `b` is unfinished. You must carry the **running max**, not the current letter's last index.
- **Using `first` occurrence, or `last[c] = i` written only when `last[c]` is unset** — that stores the **first** index. The final write must win; just assign unconditionally in a forward pass.
- **Pushing `end - start` instead of `end - start + 1`** — inclusive window, off by one on every part. Sanity check: the sizes must sum to `n`.
- **Forgetting `start = i + 1`** — every part after the first is measured from 0 and the sizes explode past `n`.
- **Looping to `n-2`** — muscle memory from [[8-45-jump-game-ii|45]], where that bound is mandatory. Here it **drops the final part** entirely. Same skeleton, opposite bound: 45 counts *departures*, 763 counts *arrivals*.
- **`int` vs `size_t` in `i < s.size()`** — signed/unsigned comparison warning; hoist `int n = s.size()`.
- **Sorting the string or the intervals** — order **is** the problem (the parts must concatenate back to `s`), and the sweep already delivers the intervals in start-order.
- **Reaching for DP** — "partition a string into parts" screams DP, but the cut points here are **forced**, not chosen, so there is nothing to optimise over. O(n²) DP is a correct-but-embarrassing answer.
- **Assuming the alphabet stays at 26** — the O(1) table is a *constraint gift*. If the interviewer widens the alphabet, switch to a hash map (still O(n), now O(k) space) and be ready for the explicit-interval-merge variant.
