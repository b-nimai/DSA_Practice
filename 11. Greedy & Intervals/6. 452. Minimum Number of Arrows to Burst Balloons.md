# 6. 452. Minimum Number of Arrows to Burst Balloons (LC 452) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/minimum-number-of-arrows-to-burst-balloons/)

**Pattern:** Greedy / Intervals — **earliest-finish-first**. Sort by **end**, shoot at the earliest end, and every balloon that starts at-or-before it is free. Same engine as [[5-435-non-overlapping-intervals|435]], but here you **count the groups you keep** instead of the intervals you drop.
**Trigger:** "**minimum number of points/arrows/shots that stab every interval**" — i.e. the **minimum number of common points covering all intervals** (*minimum piercing set*). Whenever the answer is "how few positions do I need so that every interval contains one of them", it is this greedy. The tell versus [[5-435-non-overlapping-intervals|435]]: 435 asks *which intervals do I delete*, 452 asks *how many groups remain* — and the answer to 452 **is** the count of survivors of 435, with one boundary rule flipped.

## Problem (1-liner)
Given `points[i] = [xstartᵢ, xendᵢ]` (balloon diameters on the x-axis), return the **minimum number of vertical arrows** needed to burst them all; an arrow at `x` bursts every balloon with `xstart <= x <= xend` and keeps flying forever.
**Note:** the interval is **closed** `[start, end]`, so balloons that merely **touch count as overlapping** — one arrow at `x = 2` bursts both `[1,2]` and `[2,3]`. This is the **opposite** of 435's touching rule.
**Examples:** `[[10,16],[2,8],[1,6],[7,12]] → 2` (shoot at 6 and 11) · `[[1,2],[3,4],[5,6],[7,8]] → 4` (disjoint, one each) · `[[1,2],[2,3],[3,4],[4,5]] → 2` (shoot at 2 and 4) · `[[1,2]] → 1`.
**Constraints:** `1 ≤ n ≤ 10⁵` ⇒ **O(n log n) is the target**. `−2³¹ ≤ xstart < xend ≤ 2³¹−1` — coordinates span the **entire int range**, which is the whole trap of this problem (see Pitfalls: subtraction in the comparator is UB). Never empty ⇒ `points[0]` is safe and the answer is always ≥ 1 — **never 0**.

## Idea (1-liner)
Sort by **end**, then greedily fire an arrow at the **smallest end you haven't covered yet**: that x is the rightmost point still inside the earliest-finishing balloon, so it is the single position that sweeps up the most of what follows. Every subsequent balloon starting at-or-before that x rides the same arrow for free; the first one that starts **after** it forces a new arrow.

## Approach
1. **Sort by end** ascending: `a[1] < b[1]` — a plain **comparison**, never `a[1] - b[1]`.
2. `arrows = 1`, `end = points[0][1]` — the first arrow is fired at the earliest end.
3. For `i = 1 .. n-1`: if `points[i][0] > end`, this balloon starts beyond the current arrow ⇒ `arrows++`, `end = points[i][1]` (re-anchor at the new earliest end). Otherwise it's already burst — do nothing.
4. Return `arrows`.

> **Load-bearing insight — why the arrow goes at the END.** Within one group, the arrow must sit in the intersection of all its balloons; that intersection's **right edge is the smallest end**. Placing the arrow anywhere left of it covers strictly fewer of the balloons still to come, and placing it right of it misses the earliest finisher entirely. So "smallest uncovered end" is the unique locally-safe choice, and the **exchange argument** closes it: any optimal solution's leftmost arrow can be slid right to that end without losing a balloon.
>
> **Load-bearing insight #2 — `>` here vs `>=` in 435.** Balloons are **closed** intervals, so `[1,2]` and `[2,3]` **share** the point `2` and one arrow kills both ⇒ they must stay in the same group ⇒ start a new arrow only on `s > end`. In [[5-435-non-overlapping-intervals|435]] intervals are effectively **half-open**, touching is *not* a conflict, so the keep test is `s >= end`. **One character, opposite semantics** — this is the single most quizzed difference between the twins.
>
> **Load-bearing insight #3 — `end` never needs a `min`.** In end-sorted order every balloon you meet has `e >= end`, so the arrow already sits at the group's true minimum end. In **start**-sorted order this breaks and you must write `end = min(end, points[i][1])`.

## Code (clean canonical)
```cpp
class Solution {
public:
    int findMinArrowShots(vector<vector<int>>& points) {
        sort(points.begin(), points.end(),
             [](const vector<int>& a, const vector<int>& b) { return a[1] < b[1]; });

        int arrows = 1;
        long long end = points[0][1];                 // x of the last arrow fired
        for (size_t i = 1; i < points.size(); i++) {
            if (points[i][0] > end) {                 // starts past the arrow → need a new one
                arrows++;
                end = points[i][1];
            }
        }
        return arrows;
    }
};
```
**TC:** O(n log n) — the sort dominates; the scan is O(n).  **SC:** O(1) extra (in-place sort, O(log n) introsort stack). It **mutates the caller's vector** — worth saying out loud.

## My Solution
```cpp
sort(points.begin(), points.end(),
     [](vector<int>&a, vector<int>&b) { return a[1] < b[1]; });

int numberOfArrow = 1, end = points[0][1];
for (int i = 1; i < points.size(); i++) {
    if (end >= points[i][0]) continue;
    else {
        numberOfArrow++;
        end = points[i][1];
    }
}
return numberOfArrow;
```
**Correct.** Every load-bearing detail is right: sorted by **end**, `end >= points[i][0]` is exactly the closed-interval overlap test (`continue` = same arrow), and the seed `arrows = 1` is safe because `n ≥ 1`. Crucially the comparator uses **`a[1] < b[1]`, not `a[1] - b[1] < 0`** — that subtraction is the classic overflow UB on this problem's `±2³¹` range, and it was dodged.
Polish only, nothing wrong:
- take the lambda params by **`const&`** — a non-const ref comparator won't bind to const elements on some STL implementations;
- drop the `continue; else` and flip to the positive case `if (points[i][0] > end) { … }` — it reads as the greedy invariant directly;
- `int i < points.size()` is a **signed/unsigned** comparison (warning, not a bug at `n ≤ 10⁵`) — use `size_t i` or cast.

## Other Approaches
- **Brute force — try every candidate arrow position** (each balloon's endpoints), repeatedly picking the x that bursts the most remaining balloons. **O(n²)** at best, and greedy-by-most-burst is **not** even optimal. Name it only as the baseline.
- **Sort by end + earliest-finish-first greedy** *(canonical)* — **O(n log n) / O(1)**. The expected answer.
- **Sort by start + `min` on the end** *(alt-optimal)* — **O(n log n) / O(1)**: `if (points[i][0] > end) { arrows++; end = points[i][1]; } else end = min(end, points[i][1]);`. Equally correct, one extra moving part. Worth knowing because start-sorting is the reflex shared with [[1-56-merge-intervals|56]] / [[2-57-insert-interval|57]] / [[4-253-meeting-rooms-ii|253]] — just remember the `min`.
- **Via 435 —** `arrows = n − (removals computed with the strict `>` rule)`. Same computation relabelled; say it out loud to show you've seen the equivalence, but don't code the detour.

> **The quartet to distinguish out loud:** *can one room take them all?* → [[3-252-meeting-rooms|252]], sort by **start**, adjacent-pair scan, **bool**. *How many rooms?* → [[4-253-meeting-rooms-ii|253]], **peak concurrency**, min-heap / sweep, **count**. *Which do I drop?* → [[5-435-non-overlapping-intervals|435]], sort by **end**, count the **dropped**. *How few points stab everything?* → **452**, sort by **end**, count the **groups kept**, touching = overlap. Aliases: **minimum piercing set / interval stabbing / minimum number of taps-points**. Unrelated despite the name: **LC 312 Burst Balloons** is interval **DP**, not greedy — don't let the title collide.

## Pitfalls
- **`return a[1] - b[1];` in the comparator** — *the* signature bug of 452. With ends up to `2³¹−1` and starts down to `−2³¹`, the subtraction **overflows** ⇒ signed-overflow UB ⇒ a scrambled sort and a wrong answer on the adversarial test. Always compare: `a[1] < b[1]`.
- **`>=` instead of `>` on the boundary** — balloons are **closed**, so touching is burst by one arrow. Using `s >= end` splits `[1,2],[2,3]` into 2 arrows and returns 3 instead of 2 on example 3. Exact opposite of [[5-435-non-overlapping-intervals|435]] — the flip that trips everyone.
- **Initialising `arrows = 0` or `end = INT_MIN`/`0`** — with `end = INT_MIN` seeded, the first balloon may fail `s > end` and never get its own arrow; and coordinates are negative-capable, so `0` is meaningless. Seed from `points[0][1]` with `arrows = 1`.
- **Updating `end` on a *covered* balloon** — in end-sorted order it can only push the arrow later and lose coverage. Leave it alone (see insight #3).
- **Forgetting the comparator** — a bare `sort(points.begin(), points.end())` sorts by **start**, silently switching to the algorithm that needs the `min`, without erroring.
- **Sorting by the wrong key, generally** — start for *merge / detect / count concurrency*, end for *keep-the-most*. Inherited from the pattern index.
- **Returning 0 for a valid input** — the answer is always ≥ 1; a 0 means you seeded the count wrong.
- **An O(n²) pairwise grouping** — TLEs at `n = 10⁵`; sorting is what collapses it to one pass. Same for a debug `cout` inside the loop.
- **Confusing it with LC 312 Burst Balloons** — that one is O(n³) interval DP on the *order* of popping, nothing to do with this greedy.

**Family map:** the **sort-by-end** half of the pattern, twin of [[5-435-non-overlapping-intervals|435 Non-overlapping Intervals]] (same greedy, flipped boundary, counts survivors instead of deletions) · contrast the **sort-by-start** scan of [[1-56-merge-intervals|56 Merge Intervals]], [[2-57-insert-interval|57 Insert Interval]] and [[3-252-meeting-rooms|252 Meeting Rooms]] · complement of the peak-concurrency heap in [[4-253-meeting-rooms-ii|253 Meeting Rooms II]] · escalates to **Weighted Interval Scheduling** (LC 1235) once intervals carry weights and greedy breaks.
