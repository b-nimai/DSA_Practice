# 1. 56. Merge Intervals (LC 56) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/merge-intervals/)

**Pattern:** Greedy / Intervals — **the root of the whole pattern**. Sort by **start**, then one linear pass comparing each interval to the **last kept** one. Every other interval problem in this folder is this loop with the comparison operator or the sort key changed.
**Trigger:** "**merge all overlapping intervals**" / "return the intervals that **cover** all the input" — the tells are (a) the output is a **set of intervals**, not a count or a bool, (b) overlap is defined **pairwise**, so the naive read is O(n²), and (c) nothing forbids reordering the *input*. Whenever the question is "collapse overlapping ranges into their union", the answer is **sort by start + sweep**.

## Problem (1-liner)
Given `intervals[i] = [startᵢ, endᵢ]` in **arbitrary order**, merge every group of overlapping intervals and return the resulting **non-overlapping** intervals covering the same points.
**Examples:** `[[1,3],[2,6],[8,10],[15,18]] → [[1,6],[8,10],[15,18]]` · `[[1,4],[4,5]] → [[1,5]]` (**touching counts as overlapping here**) · `[[4,7],[1,4]] → [[1,7]]` (**input is not pre-sorted**) · `[[1,9],[2,3]] → [[1,9]]` (**containment**, the case that punishes `end = it[1]`) · `[[1,4]] → [[1,4]]`.
**Constraints:** `1 ≤ n ≤ 10⁴` — **never empty**, so `intervals[0]` is always safe and the result always has ≥ 1 interval. `0 ≤ startᵢ ≤ endᵢ ≤ 10⁴` — **no inverted intervals** (no need to normalise), non-negative, and small enough that a **bucket/sweep in O(n + V)** is legal. `n ≤ 10⁴` tolerates O(n²) but the intended answer is **O(n log n)**.

## Idea (1-liner)
Sort by start, then walk once: if the current interval starts **after** the running `end`, the previous run is closed — emit it and start a new one; otherwise absorb it with `end = max(end, it[1])`.

## Approach
1. `sort(intervals.begin(), intervals.end());` — default lexicographic compare on `vector<int>` sorts by **start**, tie-broken by end. That is exactly the key needed.
2. Seed `start = intervals[0][0]`, `end = intervals[0][1]`.
3. For each interval `it`:
   - `if (end < it[0])` → **gap**: `result.push_back({start, end}); start = it[0]; end = it[1];`
   - `else` → **overlap**: `end = max(end, it[1]);`
4. **Flush the final run** — `result.push_back({start, end});` after the loop.

> **Load-bearing insight — sorting by start is what collapses O(n²) into O(n).** Overlap is a pairwise relation, so the naive question is "does interval `i` overlap interval `j`?" for all pairs. After a start-sort, every later interval starts at or after `it[0]`, so if the current one doesn't touch the running `end`, **no future one can either** — the gap is permanent. That's why comparing against a single running `end` (rather than all previously kept intervals) is sufficient. Every proof in this pattern begins "after sorting".
>
> **Load-bearing insight #2 — `end = max(end, it[1])`, never `end = it[1]`.** Start-order does **not** imply end-order: `[[1,9],[2,3]]` is sorted, but `[2,3]` is *contained* in `[1,9]`. Assigning would shrink the run to `[1,3]` and wrongly emit `[[1,3]]`. The `max` is the entire handling of the containment case — the single most common wrong submission.
>
> **Load-bearing insight #3 — the trailing `push_back` is mandatory.** The loop only emits a run when it discovers the **next** gap, so the final run is never closed from inside. Forgetting it silently drops the last interval on **every** input (`[[1,3]] → []`). The `result.back()` formulation below sidesteps this entirely, which is why many prefer it.

## Code (clean canonical)
```cpp
class Solution {
public:
    vector<vector<int>> merge(vector<vector<int>>& intervals) {
        sort(intervals.begin(), intervals.end());          // by start, then end

        vector<vector<int>> result;
        for (auto &it : intervals) {
            if (result.empty() || result.back()[1] < it[0])  // gap → new run
                result.push_back(it);
            else                                             // overlap → absorb
                result.back()[1] = max(result.back()[1], it[1]);
        }
        return result;
    }
};
```
**TC:** O(n log n) — the sort dominates the O(n) sweep.  **SC:** O(log n) auxiliary (sort's recursion stack); output excluded. **Mutates the caller's array** — say so out loud, and copy first if the interviewer cares.
*No trailing flush needed here* — the run under construction *is* `result.back()`, so it's already in the output.

## My Solution
```cpp
class Solution {
public:
    vector<vector<int>> merge(vector<vector<int>>& intervals) {
        sort(intervals.begin(), intervals.end());

        vector<vector<int>>result;
        int start = intervals[0][0], end = intervals[0][1];
        for (auto &it : intervals) {
            if (end < it[0]) {                  // strict → touching intervals merge
                result.push_back({start, end});
                start = it[0];
                end = it[1];
            } else {
                end = max(end, it[1]);          // handles containment
            }
        }
        result.push_back({start, end});         // flush the last run — mandatory

        return result;
    }
};
```
✅ **Correct — O(n log n) / O(1)**, the explicit-`start`/`end` form. Every trap is handled: `<` strict (so `[1,4],[4,5]` merges), `max` (so `[1,9],[2,3]` survives), and the trailing flush is present. `intervals[0]` is safe because `n ≥ 1`.
**Refinement:** the loop starts at index **0**, which *looks* like it might double-push the first interval. It can't — on iteration 0, `end == intervals[0][1] >= intervals[0][0] == it[0]`, so the `if` is false and it falls into a no-op `max`. Correct, but a reader has to prove that to themselves; **start the loop at index 1** to remove the pause. Or switch to the `result.back()` form above and drop `start`/`end` and the flush entirely.

## Other Approaches
- **Brute force — repeatedly scan all pairs, merge any two that overlap, restart until nothing changes.** **O(n³)** worst case, O(n²) space if you rebuild the list each round. No sort needed, which is the only reason to mention it: it's the honest baseline that motivates sorting.
- **Sort + sweep** *(canonical)* — **O(n log n) / O(1)**. The expected answer.
- **Sort starts and ends independently** — legal here because you only want the **union**, so nothing needs to stay paired: a run ends wherever `end[i] < start[i+1]`. **O(n log n) / O(n)**. A curiosity for 56, but it *is* the engine of [[4-253-meeting-rooms-ii|253]], so it's worth being able to name.
- **Counting / sweep-line over coordinates** — `0 ≤ s ≤ e ≤ 10⁴`, so bucket `+1` at each start and `−1` at each end and sweep the axis: **O(n + V)**, which **beats the sort** when `V` is small. The right answer to "can you do better than O(n log n)?" — and the right thing to *reject* the moment coordinates become unbounded or fractional.
- **Input already sorted?** Then the whole thing is **O(n) / O(1)** — a very common follow-up. Say it before they ask.
- **Streaming / online follow-up** ("intervals arrive one at a time") → the sort is unavailable; keep a `std::map` or `std::set` keyed by start and merge neighbours on insert, **O(log n) per insert**. That is literally **LC 715 / 352 (Data Stream as Disjoint Intervals)** and **LC 57 Insert Interval** repeated.

> **The boundary operator is the whole pattern — keep these three straight:** *merge the union* → **56**, touching **merges**, `end < it[0]`. *Fewest arrows to stab everything* → [[6-452-minimum-number-of-arrows-to-burst-balloons|452]], intervals are **closed**, touching **counts as overlap**, `s > end`. *Keep the most non-overlapping* → [[5-435-non-overlapping-intervals|435]], touching is explicitly **not** a conflict, `s >= end`. Same three-line loop, three different operators, decided only by the statement — **never guess it**.

## Pitfalls
- **`end = it[1]` instead of `end = max(end, it[1])`** — *the* signature bug. Start-order ≠ end-order, so a **contained** interval shrinks the run: `[[1,9],[2,3]] → [[1,3]]` instead of `[[1,9]]`.
- **Forgetting the trailing `push_back`** — the last run is only ever closed by discovering a *following* gap, so it's dropped on every input. `[[1,3]] → []`.
- **`end <= it[0]` instead of `end < it[0]`** — touching intervals stop merging and `[[1,4],[4,5]]` returns `[[1,4],[4,5]]` instead of `[[1,5]]`. The statement calls touching intervals overlapping; this is the **opposite** convention from [[3-252-meeting-rooms|252]]/[[5-435-non-overlapping-intervals|435]].
- **Not sorting** — the inputs are deliberately shuffled (`[[4,7],[1,4]]` is example 3). Unsorted input gives a **wrong answer, not a crash**, which is how it survives your own testing.
- **Writing a custom comparator that subtracts** (`return a[0] - b[0];`) — pure reflex from other problems, and it's **signed-overflow UB** the moment coordinates are allowed near `INT_MAX`. Safe at 10⁴ here, fatal in [[6-452-minimum-number-of-arrows-to-burst-balloons|452]]. Always *compare*, never subtract.
- **Sorting by end** — works for the bool in [[3-252-meeting-rooms|252]] and is *required* in [[5-435-non-overlapping-intervals|435]], but it's wrong for merging: it breaks the "no future interval can start earlier" argument the sweep depends on.
- **Mutating the caller's `intervals`** — `sort` rewrites the input in place. Harmless on LeetCode, worth flagging in an interview (and worth a defensive copy if the caller reuses it).
- **Indexing `intervals[0]` without checking `n`** — safe here (`n ≥ 1` is guaranteed) but a habit that breaks the moment a variant allows an empty list. The `result.back()` form never needs the seed.
