# 11. 295. Find Median from Data Stream (LC 295) — Hard
🔗 [Open on LeetCode](https://leetcode.com/problems/find-median-from-data-stream/)

**Pattern:** Heap — **Two Heaps / balanced halves.** The stream's *middle* is wanted, not its extremes ⇒ one heap can't help; **split the data into a low half (max-heap) and a high half (min-heap)** so both medians sit on the two tops.
**Trigger:** "**median** of everything seen **so far**, `addNum` + `findMedian` interleaved on a stream" → **two heaps, sizes kept within 1**. Any phrase like *running median / balance the two halves / middle of a stream* is this. (Contrast: "kth largest so far" → one size-K heap, [[2-703-kth-largest-element-in-a-stream|703]].)

## Problem (1-liner)
Design `MedianFinder` with `addNum(int)` and `findMedian()` returning the median of **all** numbers added so far — for an even count, the **mean of the two middle values** (so the answer is a `double`, and it need not be an element of the stream).
**Examples:** `add(1), add(2), findMedian() → 1.5` (mean of both) · `add(3), findMedian() → 2.0` (odd ⇒ the true middle) · `add(-1), add(1)` → `0.0` (negatives are legal, median can be 0 or fractional).
**Constraints:** `-10^5 ≤ num ≤ 10^5`, **at most 5·10⁴ calls** to `addNum`/`findMedian`, and **`findMedian` is never called on an empty structure**. **Edge cases:** the very first `addNum` (one heap is empty — `top()` on it is **UB**); all values equal; strictly increasing / strictly decreasing input (the adversarial case that must not degenerate); the even/odd flip on *every* insert.
**Follow-ups:** (1) all values in `[0, 100]`; (2) **99%** of values in `[0, 100]`.

## Idea (1-liner)
Keep the data **permanently cut in half**: a **max-heap `left`** holding the smaller half (its top = largest of the small half) and a **min-heap `right`** holding the larger half (its top = smallest of the large half). Maintain **`max(left) ≤ min(right)`** and **`|left| − |right| ∈ {0, 1}`** — then the median is `left.top()` when the total is odd, or the mean of the two tops when it's even. You never sort, and you never touch anything but the two tops.

## Approach
1. **Two heaps.** `priority_queue<int> left` (max-heap, low half) and `priority_queue<int, vector<int>, greater<>> right` (min-heap, high half).
2. **Insert** `num` into `left` unconditionally.
3. **Repair the ordering:** move `left.top()` over to `right`. After this, everything in `left` is ≤ everything in `right`, whatever `num` was.
4. **Repair the sizes:** if `right.size() > left.size()`, move `right.top()` back to `left`. This pins the invariant to `|left| == |right|` or `|left| == |right| + 1` — i.e. **`left` is the one allowed to be bigger**, which is why the odd median is always `left.top()`.
5. **`findMedian`:** sizes equal → `(left.top() + right.top()) / 2.0`; else → `left.top()`.

> **Load-bearing insight:** the invariant `|left| ∈ {|right|, |right|+1}` does double duty. It makes `findMedian` O(1) *and* it guarantees **`left` is empty only when `right` is empty** — so the odd branch's `left.top()` can never touch an empty heap, and the "at least one element before `findMedian`" precondition is enough. If you let `right` be the larger heap instead, the odd median becomes `right.top()` and every branch flips; pick one convention and never mix them. The second insight: **you only ever need the two boundary elements**, so a structure that keeps the *whole* stream ordered (multiset, sorted vector) is doing strictly more work than the problem asks.

## Code (clean canonical)
```cpp
class MedianFinder {
    priority_queue<int> left;                                  // max-heap, smaller half
    priority_queue<int, vector<int>, greater<>> right;         // min-heap, larger half
public:
    MedianFinder() {}

    void addNum(int num) {
        left.push(num);                    // 1. always land in left
        right.push(left.top());            // 2. hand its max to right → ordering repaired
        left.pop();
        if (right.size() > left.size()) {  // 3. left is the one allowed to be bigger
            left.push(right.top());
            right.pop();
        }
    }

    double findMedian() {
        if (left.size() == right.size())
            return (left.top() + right.top()) / 2.0;           // even → mean of the tops
        return left.top();                                      // odd  → left holds the extra
    }
};
```
**TC:** `addNum` **O(log n)** (≤ 3 heap ops), `findMedian` **O(1)**.  **SC:** **O(n)** — every number is stored exactly once across the two heaps. This is the expected answer; the 3-line unconditional shuffle needs no `empty()` guard and no case analysis.

## My Solution
```cpp
class MedianFinder {
    priority_queue<int>left_max_heap;
    priority_queue<int, vector<int>, greater<>>right_min_heap;
public:
    MedianFinder() {}

    void addNum(int num) {
        if (left_max_heap.empty() || left_max_heap.top() > num) {   // route directly
            left_max_heap.push(num);
        } else {
            right_min_heap.push(num);
        }
        // left heap should not exceed right heap size + 1
        if (left_max_heap.size() > right_min_heap.size() + 1) {
            right_min_heap.push(left_max_heap.top());
            left_max_heap.pop();
        }
        // right min heap size should not exceed left heap size
        if (right_min_heap.size() > left_max_heap.size()) {
            left_max_heap.push(right_min_heap.top());
            right_min_heap.pop();
        }
    }

    double findMedian() {
        if (left_max_heap.size() == right_min_heap.size()) {
            return (left_max_heap.top() + right_min_heap.top()) / 2.0;
        }
        return left_max_heap.top();
    }
};
```
**Correct, and actually a touch faster than the canonical** — the common case does **1** heap op instead of 3, because it routes `num` to the right heap up front instead of pushing-then-moving. Same O(log n)/O(1)/O(n). Two things to be able to defend out loud: (1) the **`empty()` short-circuit is mandatory** — it's the only thing stopping `left.top()` on an empty heap for the very first `addNum`, and `||` short-circuits so the order of the two conditions is load-bearing; (2) **strict `>` vs `>=` doesn't matter** — a `num` equal to `left.top()` goes right, and since `num ≥ max(left)` the invariant still holds (checked: `2,2,2` → `left=[2,2]`, `right=[2]`, median `2`). Both rebalance clauses are needed *as a pair*: yours caps `left` at `|right|+1` and `right` at `|left|`, which is exactly the canonical invariant. Only nit: name them `left`/`right` (the `_max_heap` suffix is already in the type) and add the space in `priority_queue<int> left`.

## Other Approaches
- **Store everything in a vector, sort on every query** *(brute)* — `addNum` **O(1)**, `findMedian` **O(n log n)** → **O(q·n log n)** overall ≈ 5·10⁴ · 5·10⁴ · log ⇒ **hard TLE**. Say it as the baseline, then kill it.
- **Keep a sorted vector, binary-search the insert position** *(better)* — `findMedian` becomes **O(1)** (index the middle), but `addNum` is **O(log n)** to *find* the slot and **O(n)** to *shift* the tail ⇒ **O(n)** per insert, **O(n·q)** total. Passes on small inputs, and worth naming because it shows you spotted that only the middle index matters. `vector::insert` after `lower_bound` is the 2-liner.
- **`multiset` + an iterator parked on the middle** *(alternative optimal)* — `insert` **O(log n)**, median **O(1)** by dereferencing the kept iterator. Same asymptotics as two heaps, but you must nudge the iterator ±1 on the correct side of every insert and it's easy to invalidate under pressure. Mention it as a valid answer; **don't** choose it in an interview.
- **Two heaps** *(optimal / expected)* — **O(log n)** add, **O(1)** median, O(n) space. See above.
- **Follow-up 1 — all values in `[0, 100]`:** drop the heaps entirely. Keep `int cnt[101]` and a running `total`. `addNum` is **O(1)**; `findMedian` walks prefix sums to find the `⌈total/2⌉`-th (and, if even, also the next) element in **≤ 101 steps ⇒ O(1)**. Space **O(1)** — independent of `n`, which is the real win on a long stream. Use a **BIT / Fenwick tree** over the 101 buckets if you want `O(log C)` queries over a wider range instead.
- **Follow-up 2 — 99% in `[0, 100]`:** **hybrid**. `cnt[101]` for the in-range bulk, plus a **max-heap of the values `< 0`** and a **min-heap of the values `> 100`** for the 1% outliers. To find the k-th: subtract the low-outlier count, walk the bucket prefix, and spill into the high outliers only if k runs past the buckets. Effectively **O(1) amortised** with **O(#outliers)** extra space. The point of the question is that you *don't* throw away the O(1) bucket structure just because the range isn't airtight.

## Pitfalls
- **`top()` on an empty heap is UB, not an exception.** The first `addNum` is the trap: any version that reads `left.top()` before checking `empty()` is broken. The canonical 3-line form sidesteps it (it pushes first); the routing form needs the `empty() ||` short-circuit.
- **Pick which heap may be larger and never waver.** With `|left| ∈ {|right|, |right|+1}` the odd median is `left.top()`; if you instead let `right` grow, it's `right.top()`. Mixing the two conventions across `addNum` and `findMedian` is the classic silent wrong-answer.
- **One rebalance is not enough — you need both the ordering fix and the size fix.** Pushing `num` into the "right" heap by size alone (without moving a boundary element) breaks `max(left) ≤ min(right)`, and then the tops are no longer the middle elements at all.
- **`/ 2.0`, never `/ 2`.** `(left.top() + right.top()) / 2` is integer division — `[1,2]` returns `1.0` instead of `1.5`. Same bug family as **LC 4 Median of Two Sorted Arrays**.
- **Don't over-guard the sum for overflow, but know the bound** — here `|num| ≤ 10^5` so the sum fits in `int`; on a variant with `±10^9` values `left.top() + right.top()` overflows and you need `(double)a + b` or `long long`.
- **`greater<>` needs the `vector<int>` middle argument** — `priority_queue<int, greater<>>` doesn't compile. Default `priority_queue` is a **max**-heap.
- **Unsigned `size()`** — `left.size() > right.size() + 1` is fine (both unsigned), but comparing a `size()` against a signed `int` warns and can wrap; keep both sides unsigned.
- **`findMedian` must not mutate.** Popping to inspect (then pushing back) is O(log n) per call and destroys the const-ness an interviewer expects; the whole design exists so a *read* is a peek.
- **No `erase` ⇒ this design does not extend to a sliding window.** `priority_queue` can't remove an arbitrary element, so **LC 480 Sliding Window Median** needs **two `multiset`s** (or lazy deletion with a "to-remove" hash-map). Knowing *why* 295's answer breaks is the natural follow-up question.
