# 8. 621. Task Scheduler (LC 621) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/task-scheduler/)

**Pattern:** Heap — **simulation frontier** (pop the most frequent, cool it down, push it back) … **but the intended answer is the O(n) greedy-math formula.** This is the pattern's "the heap is the *explanation*, not the *solution*" problem.
**Trigger:** "same item can't repeat within **n** slots / **cooldown** between identical tasks, minimise total time (idles allowed)" → **the most frequent task is the skeleton**; everything else fills its gaps. Formula first, heap only if they want the actual schedule.

## Problem (1-liner)
Given tasks `A–Z` and a cooldown `n`, each CPU interval runs one task or **idles**; two tasks with the **same label** must be ≥ `n` intervals apart. Return the **minimum number of intervals**.
**Examples:** `["A","A","A","B","B","B"], n=2 → 8` (`A B _ A B _ A B`) · `["A","C","A","B","D","B"], n=1 → 6` (`A B C D A B`, **zero idles**) · `["A","A","A","B","B","B"], n=3 → 10` (`A B _ _ A B _ _ A B`).
**Constraints:** `1 ≤ tasks.length ≤ 10^4`, uppercase letters only (**≤ 26 distinct**), `0 ≤ n ≤ 100`. Edge cases: **`n = 0`** ⇒ answer is exactly `tasks.size()` (no cooldown, never idle) · all tasks distinct ⇒ also `tasks.size()` · a single task type ⇒ pure skeleton, `(f-1)*(n+1)+1`.

## Idea (1-liner)
Only the **most frequent** task matters — it's the bottleneck. Lay it out as `maxFreq-1` blocks of width `n+1`, then a final column: `(maxFreq-1)*(n+1) + (#tasks tied at maxFreq)`. Fill the gaps with everything else. If there are so many other tasks that the gaps **overflow**, there are no idles at all — so clamp with `max(..., tasks.size())`.

## Approach
1. Count frequencies into a `vector<int> freq(26)`.
2. `maxFreq = max(freq)`; `maxCount = ` how many labels hit `maxFreq` (the ties).
3. `slots = (maxFreq - 1) * (n + 1) + maxCount`.
4. Return `max(slots, (int)tasks.size())`.

> **Load-bearing insight — draw the grid.** Put the most frequent task at the start of each row, each row `n+1` wide (1 run + `n` cooldown):
> ```
> tasks = [A,A,A,B,B,B], n = 2
> A B _ | A B _ | A B          ← 2 full blocks of width 3, then the last column
> └─ n+1 ─┘        (maxFreq-1 = 2 blocks)   + maxCount = 2  →  8
> ```
> The `maxFreq-1` full blocks are **forced** (each `A` must wait `n`). The last row has **no** trailing cooldown, so it contributes only the tied tasks — hence `+ maxCount`, not `+ (n+1)`.
> **Why the `max` clamp:** the underscores are free capacity. With enough distinct tasks (`ACABDB, n=1` → `slots = 4` but 6 tasks) the gaps fill up and spill past the skeleton — but a spilled task is *never* idle, so the answer is just `tasks.size()`. The formula can **under**count, never overcount, so one `max` fixes it.

## Code (clean canonical)
```cpp
class Solution {
public:
    int leastInterval(vector<char>& tasks, int n) {
        vector<int> freq(26, 0);
        for (char c : tasks) freq[c - 'A']++;

        int maxFreq  = *max_element(freq.begin(), freq.end());
        int maxCount = count(freq.begin(), freq.end(), maxFreq);   // ties at the top

        int slots = (maxFreq - 1) * (n + 1) + maxCount;            // the skeleton
        return max(slots, (int)tasks.size());                      // gaps may overflow
    }
};
```
**TC:** O(N) — one pass to count, then a fixed 26-element scan.  **SC:** O(1) — 26 buckets.

### Dry run
| Input | maxFreq | maxCount | slots | size | answer |
|---|---|---|---|---|---|
| `AAABBB, n=2` | 3 | 2 | `2*3 + 2 = 8` | 6 | **8** |
| `ACABDB, n=1` | 2 | 2 | `1*2 + 2 = 4` | 6 | **6** ← clamp wins |
| `AAABBB, n=3` | 3 | 2 | `2*4 + 2 = 10` | 6 | **10** |
| `AAAA, n=2`   | 4 | 1 | `3*3 + 1 = 10` | 4 | **10** |

## Heap solution (the pattern-consistent simulation)
The Heap version is what this problem sits in this folder for — and it's the one to reach for when the interviewer asks for the **actual schedule**, or changes the cooldown rule so the closed form dies.

**Idea:** each round is one full cooldown window of `n+1` slots. Greedily run the **currently most frequent** remaining tasks first (a max-heap of counts), because the task with the most left is the one most likely to force idles later. Anything you popped in this round is **cooling** — park it in a queue and only return it to the heap after the round ends.

```cpp
class Solution {
public:
    int leastInterval(vector<char>& tasks, int n) {
        vector<int> freq(26, 0);
        for (char c : tasks) freq[c - 'A']++;

        priority_queue<int> pq;                     // max-heap of remaining counts
        for (int f : freq) if (f > 0) pq.push(f);

        int time = 0;
        while (!pq.empty()) {
            vector<int> cooling;                    // popped this round, can't reuse yet
            for (int slot = 0; slot <= n; ++slot) { // one window = n+1 slots
                if (!pq.empty()) {
                    int c = pq.top(); pq.pop();
                    if (--c > 0) cooling.push_back(c);
                }
                ++time;                             // counts the idle slots too
                if (pq.empty() && cooling.empty()) break;   // last round: stop early
            }
            for (int c : cooling) pq.push(c);       // cooldown served, back in
        }
        return time;
    }
};
```
**TC:** O(N · log 26) = **O(N)** in practice (each of the `N` task instances is popped once; heap size ≤ 26) — often quoted as O(N·n) if you count the idle slots of the inner loop.  **SC:** O(26) = O(1).

> **The two load-bearing lines:** (1) `++time` sits **outside** the `if`, so an empty heap mid-round still burns the slot — that's exactly how idles get counted. (2) The `break` when *both* the heap and `cooling` are empty stops the **final** round from padding trailing idles — without it `AAABBB, n=2` returns 9 instead of 8. That's the #1 bug in this solution.

**Formula vs heap — say this out loud in the interview:** the formula is O(N)/O(1) and is the expected answer; the heap is O(N)/O(1) too but ~5× the code — **its value is that it generalises**. Per-task cooldowns, priorities, or "print the schedule" all break the closed form and the heap just keeps working.

## Other Approaches
- **Brute force / backtracking over orderings** — try every permutation of tasks, check the cooldown constraint, keep the shortest. **O(N!)**. Never code it; name it in one sentence to justify the greedy.
- **Slot-by-slot simulation with a `lastUsed[26]` array** — at each tick scan all 26 labels, pick the one with the highest remaining count whose `lastUsed + n < t`, else idle. **O(answer · 26)** — the answer can be ~`10^4 · 101 ≈ 10^6`, so it passes but is the slowest accepted route. Good stepping stone if you can't see the formula.
- **Heap + cooldown queue** *(pattern-canonical, above)* — **O(N)**, O(1). The general-purpose answer; the only one that yields the schedule.
- **Heap + queue of `{count, readyTime}`** — the streaming variant: instead of rounds, keep a `queue<pair<int,int>>` of cooling tasks and jump `time` forward to the front's `readyTime` when the heap is empty. Same O(N), avoids simulating idle ticks one at a time — strictly better if `n` is huge.
- **Greedy math formula** *(optimal)* — **O(N)**, O(1). What to write first.

**Follow-up worth knowing: [LC 1834 Single-Threaded CPU](https://leetcode.com/problems/single-threaded-cpu/) and [LC 1953 Maximum Number of Weeks](https://leetcode.com/problems/maximum-number-of-weeks-for-which-you-can-work/).** 1953 is 621's formula with **`n = 1`** and no idles allowed: if `maxFreq > rest + 1` you're capped at `2*rest + 1`, else `total`. Same "the biggest pile is the bottleneck" reasoning.

## Pitfalls
- **`+ maxCount`, not `+ 1`** — every task tied at `maxFreq` needs its own column in the final row. `AAABBB, n=2` gives 8, not 7. This is the most-missed term.
- **`(n + 1)`, not `n`** — the block is *one run plus `n` cooldown slots*. Off-by-one here silently underestimates every answer.
- **Forgetting `max(slots, tasks.size())`** — `ACABDB, n=1` returns 4 instead of 6. The formula counts the **skeleton**, not the tasks that overflow it.
- **`n = 0`** — `slots = (maxFreq-1)*1 + maxCount ≤ tasks.size()`, so the clamp is what returns the right answer. Don't special-case it; it already works.
- **Cast `tasks.size()`** — `max(int, size_t)` doesn't compile (no common type deduced). Same unsigned trap as [[1-215-kth-largest-element-in-an-array|215]]'s `size() > k`.
- **Heap version: `++time` must be outside the `if`** — inside it, idle slots vanish and you return `tasks.size()` every time.
- **Heap version: break out of the last round** — without the `pq.empty() && cooling.empty()` check you pad trailing idles onto the final block (`AAABBB, n=2` → 9).
- **Heap version: never push a zero count back** — decrement first, push only `if (c > 0)`; a 0 keeps a finished task alive forever. Same trap as the zero residue in [[7-1046-last-stone-weight|1046]].
- **Don't sort by count once and cycle** — counts change every round, which is exactly why the heap exists (the [[7-1046-last-stone-weight|1046]] lesson repeated).
- **This is not Top-K** — nothing is capped at `k`, nothing is evicted; the heap *is* the working set.
