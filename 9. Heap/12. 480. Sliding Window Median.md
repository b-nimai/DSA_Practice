# 12. 480. Sliding Window Median (LC 480) — Hard
🔗 [Open on LeetCode](https://leetcode.com/problems/sliding-window-median/)

**Pattern:** Heap — **Two Heaps + lazy (deferred) deletion.** [[11-295-find-median-from-data-stream|295]] with an **expiry date** on every element: the window *evicts* as well as inserts, and `priority_queue` has no `erase` ⇒ you either swap in `multiset` or bolt a **"to-delete" hash-map** onto the heaps and pop stale tops only when they surface.
**Trigger:** "**median of every window of size k**" → **two heaps + lazy deletion** (or `multiset` + a mid iterator). The tell is **"sliding window" + "median"**: sliding window ⇒ deletion, median ⇒ two halves. Any *"running statistic that needs the middle, over a fixed-size window"* is this. (Contrast: window **max** → monotonic deque, [[LC 239]]; median **so far** with no eviction → [[11-295-find-median-from-data-stream|295]].)

## Problem (1-liner)
For every window of size `k` sliding left→right over `nums`, return its **median** — the middle value when `k` is odd, the **mean of the two middle values** when `k` is even (so the answer is `vector<double>` and need not contain window elements).
**Examples:** `nums=[1,3,-1,-3,5,3,6,7], k=3 → [1,-1,-1,3,5,6]` · `nums=[1,2,3,4,2,3,1,4,2], k=3 → [2,3,3,3,2,3,2]` (heavy duplicates — the case that breaks naive lazy deletion).
**Constraints:** `1 ≤ k ≤ nums.length ≤ 10^5` ⇒ **O(n log n) required, O(n·k) is TLE**; `-2^31 ≤ nums[i] ≤ 2^31 - 1` ⇒ **`nums[i]` can be `INT_MIN`/`INT_MAX`, so `a + b` overflows `int`**. Output length is `n - k + 1`. **Edge cases:** `k == 1` (median = the element itself, and a heap empties on every step); `k == n` (one window); all values equal; `INT_MAX + INT_MAX` in the even branch.

## Idea (1-liner)
Keep 295's two heaps — max-heap `small` (low half), min-heap `large` (high half) — but **never physically remove the expiring element**: mark it in a `delayed{value → count}` map, decrement the *logical* size counter of whichever half owns it, and **only actually pop it when it bubbles to a top**. Because you track sizes yourself, the heaps may hold garbage while `smallSize`/`largeSize` stay exact — the tops are the only positions that must be clean.

## Approach
1. **Two heaps + three pieces of bookkeeping:** `small` (max-heap), `large` (min-heap), `delayed` (value → pending deletions), and **`smallSize` / `largeSize` = counts of *valid* elements** (never `small.size()`, which includes garbage).
2. **`insert(num)`:** `num <= small.top()` (or `small` empty) → `small`, else `large`; bump that side's size; `rebalance()`.
3. **`erase(num)`:** `delayed[num]++`, then **decide which half owned it by value**: `num <= small.top()` ⇒ it was in `small` (`smallSize--`), else `large` (`largeSize--`). If `num` **is** the top, `prune` that heap right now. Then `rebalance()`.
4. **`prune(heap)`:** while the top carries a `delayed` mark, consume one mark and pop. Called after **every** pop so the tops stay valid.
5. **`rebalance()`:** hold `smallSize ∈ {largeSize, largeSize+1}` — move one boundary element across and `prune` the heap you popped from.
6. **Driver:** insert the first `k`, record the median, then for each `i ≥ k` **`insert(nums[i])` first, then `erase(nums[i-k])`** — inserting first keeps both heaps non-empty so `erase`'s `small.top()` is always safe.

> **Load-bearing insight (the whole problem):** `delayed` is keyed by **value**, not identity — so with duplicates a mark meant for `small` could in principle be eaten while pruning `large`. It can't, because of a chain: (a) every valid element of `small` ≤ every valid element of `large`; (b) so if `num <= max(small)` a copy **must** live in `small` — a copy in `large` would force `num >= max(small)` — which is what makes routing-by-value legitimate; (c) pruning **immediately when the erased value equals the top** guarantees every *pending* mark satisfies `v < small.top() <= large.top()` **strictly**, so `pruneLarge` can never consume a `small`-side mark. Delete either immediate-prune and duplicates silently corrupt the sizes. Second insight: **stale entries cost you nothing asymptotically** — each element is pushed once and popped at most once, so the amortised cost stays `O(log n)` (note `log n`, not `log k`: the heaps can hold up to `n` entries).

## Code (clean canonical)
```cpp
class Solution {
    priority_queue<int> small;                              // max-heap, low half
    priority_queue<int, vector<int>, greater<>> large;      // min-heap, high half
    unordered_map<int, int> delayed;                        // value → pending deletions
    int smallSize = 0, largeSize = 0;                       // VALID counts, not .size()

    template <typename PQ>
    void prune(PQ& heap) {                                  // pop garbage sitting on top
        while (!heap.empty()) {
            int num = heap.top();
            if (!delayed.count(num)) break;
            if (--delayed[num] == 0) delayed.erase(num);
            heap.pop();
        }
    }

    void rebalance() {                                      // small ∈ {large, large+1}
        if (smallSize > largeSize + 1) {
            large.push(small.top()); small.pop();
            smallSize--; largeSize++;
            prune(small);                                   // every pop is followed by a prune
        } else if (smallSize < largeSize) {
            small.push(large.top()); large.pop();
            largeSize--; smallSize++;
            prune(large);
        }
    }

    void insert(int num) {
        if (small.empty() || num <= small.top()) { small.push(num); smallSize++; }
        else                                     { large.push(num); largeSize++; }
        rebalance();
    }

    void erase(int num) {
        delayed[num]++;
        if (num <= small.top()) {                           // owned by small (see insight)
            smallSize--;
            if (num == small.top()) prune(small);           // mandatory: keeps the top valid
        } else {
            largeSize--;
            if (!large.empty() && num == large.top()) prune(large);
        }
        rebalance();
    }

    double getMedian() {                                    // sizes already know the parity
        if (smallSize > largeSize) return small.top();
        return ((double)small.top() + (double)large.top()) / 2.0;   // casts stop overflow
    }
public:
    vector<double> medianSlidingWindow(vector<int>& nums, int k) {
        vector<double> ans;
        for (int i = 0; i < k; i++) insert(nums[i]);
        ans.push_back(getMedian());

        for (int i = k; i < nums.size(); i++) {
            insert(nums[i]);                                // insert BEFORE erase
            erase(nums[i - k]);
            ans.push_back(getMedian());
        }
        return ans;
    }
};
```
**TC:** **O(n log n)** — every element is pushed once and popped at most once, each op `O(log n)` amortised. **SC:** **O(n)** — heaps + `delayed` can hold up to `n` entries before garbage is collected (not `O(k)`, and saying so is a plus in the interview).
*Stress-tested vs a sorted brute force: 200k random cases with heavy duplicates, `INT_MIN`/`INT_MAX` windows exact, `n=10^5, k=5·10^4` in **13 ms**.*

## My Solution
Structurally identical to the canonical above and **correct** — separate `pruneSmall()`/`pruneLarge()` instead of one template, and `getMedian(int k)` taking `k` to test `k & 1`. Three refinements to state out loud:
1. **Collapse the two prune functions into one template** — the copy-paste is the first thing a reviewer's eye lands on.
2. **`getMedian()` shouldn't take `k`** — `smallSize > largeSize` already encodes the parity; a parameter that can go stale is a parameter you don't need.
3. **Members are per-run state.** `small`/`large`/`delayed`/the counters live on the object, so a second call on the same `Solution` returns garbage. LeetCode builds a fresh object so it passes, but say it: *"I'd wrap these in a `MedianTracker` constructed inside the function"* — free points.
The `(double)` casts and the immediate-prune-on-equal-top were both already right; those are the two lines that actually matter.

## Other Approaches
- **Sort every window** *(brute)* — for each of the `n-k+1` windows, copy and sort: **O(n·k log k)** / O(k). At `n = 10^5, k = 5·10^4` that's ~10^10 ops ⇒ **hard TLE**. Name it as the baseline, then kill it.
- **Keep one sorted `vector`, `lower_bound` insert + erase** *(better)* — the window stays ordered so the median is an O(1) index lookup, but each slide **shifts the tail**: **O(n·k)** / O(k). Passes small inputs; worth naming because it shows you spotted that only the middle index matters and that the window is *mostly* unchanged between steps.
- **`multiset` + an iterator parked on the median** *(alternative optimal — tighter than heaps)* — **O(n log k) / O(k)**, better than the heaps on *both* axes because nothing stale is ever retained:
  ```cpp
  multiset<int> win(nums.begin(), nums.begin() + k);
  auto mid = next(win.begin(), k / 2);              // odd → the median; even → upper middle
  vector<double> ans;
  for (int i = k; ; i++) {
      ans.push_back(((double)*mid + *prev(mid, 1 - k % 2)) / 2.0);   // even → average two
      if (i == nums.size()) break;
      win.insert(nums[i]);
      if (nums[i] < *mid) --mid;                    // new value landed left of mid
      if (nums[i - k] <= *mid) ++mid;               // outgoing sits at/left of mid
      win.erase(win.lower_bound(nums[i - k]));      // erase ONE copy, BY ITERATOR
  }
  ```
  *(Also stress-tested clean; 36 ms on the max case — slower in wall-clock than the heaps despite the better bound, because node-based `multiset` cache-misses.)* Shorter, but the ±1 iterator nudges are easy to get backwards under pressure, and `win.erase(value)` **deletes every duplicate**. Offer it as the tighter answer; pick whichever you can write bug-free.
- **Two heaps + lazy deletion** *(the expected answer)* — O(n log n) / O(n). See above. **Lead with this one**: it's the direct evolution of [[11-295-find-median-from-data-stream|295]], and "lazy deletion" is a transferable technique the interviewer wants to hear named.
- **Indexed BIT / order-statistic tree over compressed values** *(the "what if k is huge / values stream in" answer)* — coordinate-compress `nums`, keep a Fenwick tree of counts, and binary-search the tree for the `⌈k/2⌉`-th element: **O(n log n)** with **O(1)** per-update deletion and no iterator gymnastics. Overkill here, but it's the honest answer to *"now support arbitrary rank, not just the median"*.

## Pitfalls
- **`priority_queue` has no `erase` — that's the entire difficulty.** Copy-pasting [[11-295-find-median-from-data-stream|295]] and hoping is the #1 failure. You must add lazy deletion or switch container.
- **Never use `small.size()` for the balance test.** Physical size includes garbage; only your own `smallSize`/`largeSize` counters are truthful. Mixing the two is the classic silent wrong answer.
- **Prune after *every* pop, and immediately when the erased value equals a top.** Both preserve the invariant "the tops are valid", which `erase`'s `num <= small.top()` routing depends on. Drop either and duplicates corrupt the sizes.
- **`(double)a + (double)b`, never `(a + b) / 2.0`.** `nums[i]` reaches `2^31 - 1`, so `INT_MAX + INT_MAX` is **signed overflow = UB** *before* the division ever happens. Distinct from 295's `/2` vs `/2.0` trap — here it's the **sum**, not the divide. (`/ 2` integer division is still a bug too: `[1,2] → 1.0` not `1.5`.)
- **Insert before erase in the driver.** Erasing first can empty a heap and make `erase`'s `small.top()` **UB**; going to `k+1` elements first keeps both sides populated.
- **`multiset::erase(value)` removes ALL equal copies** — always `erase(s.find(x))` / `erase(s.lower_bound(x))`. Silently wrong on `[1,2,2,3]`.
- **`k == 1`** — a heap fully empties every step; the size counters (not `empty()` checks scattered around) are what keep it correct. Test it.
- **`top()` on an empty heap is UB, not an exception** — inherited from the whole Heap pattern.
- **`greater<>` needs the `vector<int>` middle argument**; default `priority_queue` is a **max**-heap.
- **Don't claim O(k) space** for the lazy-deletion version — garbage makes it **O(n)**. The `multiset` version is the one that's genuinely O(k).
