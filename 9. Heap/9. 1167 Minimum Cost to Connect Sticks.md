# 9. 1167 Minimum Cost to Connect Sticks (LC 1167) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/minimum-cost-to-connect-sticks/) · [TUF](https://takeuforward.org/plus/dsa/problems/minimum-cost-to-connect-sticks) · [GfG "Minimum Cost of Ropes"](https://www.geeksforgeeks.org/problems/minimum-cost-of-ropes-1587115620/1)

**Pattern:** Heap — **simulation frontier**, the exact **mirror of [[7-1046-last-stone-weight|1046]]**: pop the **two smallest**, push their **sum** back. This is **Huffman coding**.
**Trigger:** "merge two items at a cost equal to their **sum**, repeat until one remains, **minimise total cost**" → min-heap, `n-1` merges. The tell is that the merged item **re-enters the pool** (so a single sort is useless) *and* the cost is **additive**, which is what makes greedy optimal.

## Problem (1-liner)
Connect all sticks into one; joining two sticks costs the **sum of their lengths** and produces a stick of that length. Return the **minimum total cost**.
**Examples:** `[2,4,3] → 14` (2+3=5, then 4+5=9) · `[1,8,3,5] → 30` (1+3=4, 4+5=9, 8+9=17).
**Constraints:** `1 ≤ n ≤ 10^4`, `1 ≤ sticks[i] ≤ 10^4`. **`n == 1` costs 0** — no connection ever happens, and that's the case that crashes a naive loop.

## Idea (1-liner)
Total cost = **Σ (stick × its depth in the merge tree)** — every merge re-charges everything beneath it — so the **smallest sticks must sit deepest**. Greedily merging the current two minimums produces exactly that tree: min-heap, pop two, push the sum, accumulate.

## Approach
1. **Heapify** into a min-heap: `priority_queue<int, vector<int>, greater<int>> pq(sticks.begin(), sticks.end())`.
2. While `pq.size() > 1`: pop `a`, pop `b` (the two smallest).
3. `cost += a + b`, then **push `a + b` back** — the merged stick competes in later rounds.
4. Return `cost`. With `n == 1` the loop never runs → `0`, for free.

> **Load-bearing insight:** a stick's length is paid **once per merge it participates in**, i.e. once per level from its leaf up to the root ⇒ `cost = Σ len(i) · depth(i)`. That's the **Huffman objective** verbatim (lengths = frequencies), so the classic exchange argument applies: the two smallest items can always be placed as the deepest sibling pair without hurting the optimum. Greedy is **provably optimal here** — unlike 1046's sibling [LC 1049](https://leetcode.com/problems/last-stone-weight-ii/), where you also pick the order but greedy is *wrong*. The difference: here the objective is a **sum of merge costs**; there it's an **absolute difference**.

## Code (clean canonical)
```cpp
class Solution {
public:
    int connectSticks(vector<int>& sticks) {
        priority_queue<int, vector<int>, greater<int>> pq(sticks.begin(), sticks.end()); // heapify O(n)

        int cost = 0;
        while (pq.size() > 1) {                 // exactly n-1 merges
            int a = pq.top(); pq.pop();
            int b = pq.top(); pq.pop();
            cost += a + b;
            pq.push(a + b);                     // merged stick re-enters the pool
        }
        return cost;
    }
};
```
**TC:** O(n log n) — `n-1` merges, each a constant number of O(log n) heap ops.  **SC:** O(n).

## My Solution
```cpp
class Solution {
public:
    int connectSticks(vector<int>& sticks) {
        if (sticks.size() == 1) return 0;
        priority_queue<int, vector<int>, greater<>> pq;
        for (int val : sticks) pq.push(val);

        int cost = 0;
        while (!pq.empty()) {
            int val1 = pq.top(); pq.pop();
            int val2 = pq.top(); pq.pop();

            int sum = val1 + val2;
            cost += sum;
            if (pq.empty()) break;
            pq.push(sum);
        }
        return cost;
    }
};
```
**Correct** — same O(n log n)/O(n), and the `size() == 1` guard is **genuinely required** here: without it the second `pq.top()` reads an empty heap (**UB**). Refinements: (1) `while (pq.size() > 1)` folds the guard **and** the mid-loop `break` into the loop condition and makes the "`n-1` merges" invariant obvious; (2) the **range constructor** heapifies in **O(n)** instead of `n` pushes at O(log n) — same overall bound, but it's the idiom to show; (3) `greater<>` (C++14 transparent) is fine, `greater<int>` is the safer habit on older judges.

## Other Approaches
- **Brute force — rescan for the two minimums each round.** Linear scan × `n-1` rounds ⇒ **O(n²)**, O(1) extra. Correct, but 10^4 sticks makes it pointless; it exists to show *why* the heap is there.
- **Sort + re-insert into a sorted vector.** Sort once O(n log n), then each merged sum is inserted in place — the insert is O(n) ⇒ **O(n²)** overall. Strictly worse than the heap; naming it shows you know insertion is the bottleneck, not the sort.
- **Sort + two queues (heap-free, Huffman's linear trick)** — sort the sticks into queue `A`; merged sums go into queue `B` and come out **already non-decreasing** (each new sum ≥ every previous one). Each step pops the two smallest across the two fronts. **O(n log n)** dominated by the sort, then **O(1) per merge**; **O(n)** space. Same bound, no heap — the answer that says "I know *why* the sums are sorted."
- **Min-heap greedy** *(canonical)* — **O(n log n)**, O(n). The expected answer.

> **Follow-ups worth naming:** [LC 1642 Furthest Building](https://leetcode.com/problems/furthest-building-you-can-reach/) (heap-greedy on which jumps to pay for) and the real Huffman question — **build the encoding tree** — which is this exact loop with tree nodes instead of ints. If asked for the *k*-way version (merge `k` at a time), you must **pad with zero-length sticks** until `(n-1) % (k-1) == 0`, else the top of the tree is under-filled.

## Pitfalls
- **`n == 1` → 0, and it's a crash, not a wrong answer.** Popping twice from a 1-element heap is **UB**. `while (pq.size() > 1)` kills it; `while (!pq.empty())` needs an explicit guard. Same family as the unconditional pop in [[2-703-kth-largest-element-in-a-stream|703]] and the empty-heap `top()` in [[7-1046-last-stone-weight|1046]].
- **You must push the sum back.** Merged sticks are ordinary sticks and get **re-charged** in later merges. Forgetting the push turns this into "sum of adjacent pairs" — a different, wrong problem.
- **Min-heap, not max-heap.** `priority_queue<int>` defaults to a **max**-heap; merging the two *largest* first maximises the cost. Needs the full `<int, vector<int>, greater<int>>` triple.
- **The last merge is not free — but it is not extra either.** Exactly `n-1` merges happen; don't "skip" the final push *and* the final cost. The `break`-before-push version is right only because the cost was already added first.
- **Overflow (the GfG variant's trap).** Here max cost ≈ `10^8 total × depth ~14 ≈ 1.4·10^9` — `int` survives, barely. On the GfG "Minimum Cost of Ropes" version the bounds are bigger: use **`long long`** for both `cost` and the merged sum.
- **Don't greedy-ify the wrong twin.** Additive merge cost ⇒ greedy optimal (Huffman). "Minimise the final difference" ([LC 1049](https://leetcode.com/problems/last-stone-weight-ii/)) ⇒ **subset-sum DP**, greedy wrong. Same-shaped statement, opposite technique.
- **Not Top-K.** Nothing is capped at k, nothing is evicted — every pop is *work*, not pruning. Don't reach for [[1-215-kth-largest-element-in-an-array|215]]'s `size() > k` skeleton.
