# 6. 658. Find K Closest Elements (LC 658) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/find-k-closest-elements/)

**Pattern:** Heap — **Top-K with a size-K max-heap** ([[5-973-k-closest-points-to-origin|973]] on a 1-D metric) — but the array is **sorted**, so the real answer is **binary search on the window's left edge**
**Trigger:** "k **closest** to `x`, output **sorted**, and the input is **already sorted**" → the answer is a **contiguous window** of length k ⇒ binary-search `lo ∈ [0, n-k]` comparing the element you'd **drop** vs the one you'd **gain**. If you forget the sorted trick, the size-K max-heap keyed by `{|num-x|, num}` still passes at O(n log k).

## Problem (1-liner)
Given a **sorted** array `arr`, return the **k closest integers to `x`**, in **ascending order**; ties (`|a-x| == |b-x|`) go to the **smaller** value.
**Examples:** `arr=[1,2,3,4,5], k=4, x=3 → [1,2,3,4]` — `1` and `5` both sit at distance 2, and the tie rule keeps the **smaller**, so `1` is in and `5` is out · `arr=[1,1,2,3,4,5], k=4, x=-1 → [1,1,2,3]` — `x` lies **outside** the array, so the answer is just the leftmost k.
**Constraints:** `1 ≤ k ≤ n ≤ 10^4`, `-10^4 ≤ arr[i], x ≤ 10^4`. So `k` is always valid and the result is never empty. **Edge cases:** `k == n` (return the whole array), `x` far left / far right of the array (answer is a prefix / suffix), heavy duplicates.

## Idea (1-liner)
Two facts collapse the problem: (1) since `arr` is **sorted**, the k closest are always **contiguous** — you can never skip an element that lies *between* your pick and `x`, because it would be closer; (2) so the only unknown is the **starting index `lo ∈ [0, n-k]`**. Comparing window `lo` to window `lo+1` is just "is the element I **drop** (`arr[mid]`) farther than the one I **gain** (`arr[mid+k]`)?" — and that predicate is **monotonic**, so binary search it. **O(log(n-k) + k)**, O(1) extra.

## Approach
1. Search space = the window's left edge: `lo = 0`, `hi = n - k` (`hi` is inclusive — the last legal start).
2. While `lo < hi`, take `mid`. Windows `[mid, mid+k-1]` and `[mid+1, mid+k]` differ by exactly two elements: you **drop `arr[mid]`** and **gain `arr[mid+k]`**.
3. If `x - arr[mid] > arr[mid+k] - x` → the gained element is strictly closer ⇒ **shift right**, `lo = mid + 1`. Else keep the left window, `hi = mid`.
4. Return `arr[lo .. lo+k-1]` — already sorted, no post-sort needed.

> **Load-bearing insight:** on a **sorted** array the answer is a **contiguous window**, so "pick k elements" degenerates to "pick one index". The comparison `x - arr[mid]` vs `arr[mid+k] - x` needs **no `abs`**: as `mid` grows the left gap only grows and the right gap only shrinks, which is exactly the monotonicity that legalises binary search. Using **strict `>`** (not `>=`) is what implements the tie rule "prefer the smaller value" — on a tie you stay left.

## Code (clean canonical)
```cpp
class Solution {
public:
    vector<int> findClosestElements(vector<int>& arr, int k, int x) {
        int lo = 0, hi = (int)arr.size() - k;              // hi = last legal window start
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            // shift right only if the element we'd GAIN is strictly closer than the one we'd DROP
            if (x - arr[mid] > arr[mid + k] - x) lo = mid + 1;
            else                                 hi = mid;
        }
        return vector<int>(arr.begin() + lo, arr.begin() + lo + k);
    }
};
```
**TC:** O(log(n-k) + k) — binary search over `n-k` starts, then copy k.  **SC:** O(1) extra (output aside). The expected answer once the interviewer says "arr is sorted".

## My Solution
```cpp
class Solution {
public:
    vector<int> findClosestElements(vector<int>& arr, int k, int x) {
        priority_queue<pair<int, int>> pq;                 // max-heap by {distance, value}
        for (int num : arr) {
            int dis = abs(num - x);
            pq.push({dis, num});
            if (pq.size() > k) pq.pop();                   // evict the current WORST
        }
        vector<int> ans;
        while (!pq.empty()) { ans.push_back(pq.top().second); pq.pop(); }
        sort(ans.begin(), ans.end());
        return ans;
    }
};
```
**Correct**, O(n log k + k log k) / O(k). The bounded max-heap keeps "the k best so far" by always evicting the current worst — and the **tie rule falls out for free**: `pair` compares **lexicographically**, so on equal distance the **larger value** sits on top and is popped first, leaving the smaller one — exactly what the problem asks. (Storing `{num, dis}` instead would order by value and silently break.) The final `sort` is needed because a heap drains in *distance* order, not value order. Refinements: (1) `pq.size() > k` mixes `size_t` with `int` → cast `(int)pq.size()`; (2) it **ignores that `arr` is sorted** — state the binary-search window version as the follow-up, that's the point of this problem.

## Other Approaches
- **Sort by `{|num-x|, num}`, take first k, re-sort** *(brute)* — **O(n log n)**, O(n). Works on unsorted input; the obvious first answer.
- **Size-K max-heap keyed by `{|num-x|, num}`** *(your solution / [[5-973-k-closest-points-to-origin|973]] transplanted)* — **O(n log k)**, **O(k)**. The right answer if the array were **unsorted** or arriving as a **stream**. Note it still needs a final sort for ascending output — 973 didn't, because there any order was allowed.
- **Two-pointer shrink** *(easy to derive under pressure)* — `l = 0, r = n-1`; while `r - l + 1 > k`, drop the farther end (`x - arr[l] > arr[r] - x ? ++l : --r`), tie → drop the right (keeps the smaller value). **O(n-k)**, O(1). Great middle ground: uses sortedness, no binary-search index gymnastics.
- **Binary search the window start** *(optimal)* — **O(log(n-k) + k)**, O(1). See canonical above.
- *(Variant)* **`lower_bound` + expand outward** — find the insertion point of `x`, then walk two pointers outward k times. O(log n + k) too, but the tie/bounds handling is fiddlier than the window search; mention it, don't code it.

## Pitfalls
- **`hi = n - k`, not `n - 1`** — `hi` is a *window start*, and a window of length k can't start past `n-k`. Off-by-one here is the #1 bug; note `hi` is **inclusive** and the loop condition is `lo < hi` (never `lo <= hi`, which would infinite-loop with `hi = mid`).
- **Compare gaps, not `abs`** — `x - arr[mid]` and `arr[mid+k] - x` can be negative if `x` sits outside the window, and that's *fine*: the signs still make the monotonic comparison come out right. Wrapping them in `abs()` breaks it.
- **`>` vs `>=`** — strict `>` keeps the left window on a tie, implementing "smaller value wins". `>=` silently fails cases like `arr=[1,2,3,4,5], k=4, x=3`.
- **Heap version: store `{dis, num}`, not `{num, dis}`** — the distance must be the primary key, and value-second is what gives you the tie rule for free.
- **Heap version needs the final `sort`** — output must be ascending; unlike [[5-973-k-closest-points-to-origin|973]], "any order" is *not* allowed here.
- **`pq.size()` is unsigned** — `pq.size() > k` mixes `size_t` and `int`; cast `k` (or `size()`).
- **Don't re-derive `abs` into a comparator when `pair` already does it** — a custom lambda comparator here is strictly more code and more ways to invert the polarity.
