# 7. 1046. Last Stone Weight (LC 1046) — Easy
🔗 [Open on LeetCode](https://leetcode.com/problems/last-stone-weight/)

**Pattern:** Heap — **priority queue as a live simulation frontier** (the *first* non-Top-K use in this pattern: the heap **isn't** capped at k, it **is** the data structure)
**Trigger:** "repeatedly take the **largest** (or two largest), transform, **put the result back**" → `priority_queue<int>` and loop until it drains. The tell is that the collection **mutates every round**, so sorting once is useless.

## Problem (1-liner)
Repeatedly smash the **two heaviest** stones `x ≤ y`: both vanish if `x == y`, else a stone of weight `y - x` remains. Return the last stone's weight, or **0** if none remain.
**Examples:** `[2,7,4,1,8,1] → 1` (8,7→1 · 4,2→2 · 2,1→1 · 1,1→gone · leaves `[1]`) · `[1] → 1` (no smash ever happens).
**Constraints:** `1 ≤ n ≤ 30`, `1 ≤ stones[i] ≤ 1000`. Input is **never empty**, but the *heap* can end empty (e.g. `[2,2] → 0`), so the final guard is real. Weights stay positive and shrink, so no overflow.

## Idea (1-liner)
Each round needs the **current** two maxima of a set that just changed — a sorted array would need re-sorting every round (O(n² log n)), but a **max-heap** gives `top()` in O(1) and re-inserts the residue in O(log n). Pop two, push back `y - x` **only if nonzero**; when fewer than two remain, the heap holds the answer (or is empty → 0).

## Approach
1. **Heapify** all stones into a `priority_queue<int>` (default = max-heap).
2. While `size() >= 2`: pop `y` (largest), pop `x` (second largest) — the max-heap guarantees `x ≤ y`.
3. If `x != y`, push `y - x` back. If equal, push nothing (both destroyed).
4. Return `pq.empty() ? 0 : pq.top()`.

> **Load-bearing insight:** this is **not** a Top-K problem — nothing is capped at k and nothing is evicted. The heap is the *working set itself*, and it earns its keep because the multiset **changes every iteration** and you always need the fresh max. Popping twice from a max-heap is what makes `x ≤ y` **free** — no `min`/`max`/swap needed. Also note the greedy is **safe here** because the "smash the two heaviest" order is *dictated by the problem*, not chosen by you — see the 1049 trap below.

## Code (clean canonical)
```cpp
class Solution {
public:
    int lastStoneWeight(vector<int>& stones) {
        priority_queue<int> pq(stones.begin(), stones.end());   // heapify: O(n)
        while (pq.size() >= 2) {
            int y = pq.top(); pq.pop();                          // heaviest
            int x = pq.top(); pq.pop();                          // second heaviest, x <= y
            if (x != y) pq.push(y - x);                          // survivor goes back in
        }
        return pq.empty() ? 0 : pq.top();
    }
};
```
**TC:** O(n log n) — at most `n-1` smashes, each a constant number of O(log n) heap ops.  **SC:** O(n) for the heap.

## My Solution
```cpp
class Solution {
public:
    int lastStoneWeight(vector<int>& stones) {
        int n = stones.size();
        priority_queue<int> pq;
        for (int w : stones) pq.push(w);

        while (pq.size() >= 2) {
            int l = pq.top(); pq.pop();
            int s = pq.top(); pq.pop();
            if (l - s) pq.push(l - s);
        }
        return pq.empty() ? 0 : pq.top();
    }
};
```
**Correct**, same O(n log n) / O(n). The `pq.empty()` guard and the "push only if nonzero" check are both exactly right. Refinements: (1) `int n` is **unused** — delete it; (2) `if (l - s)` leans on int-as-bool — correct (a max-heap guarantees `l ≥ s`, so nonzero ⇒ positive), but `if (l != s)` states the intent and reads as deliberate rather than as a typo for `l > s`; (3) the `for` loop of `n` pushes is O(n log n) — the **range constructor** `priority_queue<int> pq(stones.begin(), stones.end())` heapifies in **O(n)** and removes the loop (doesn't change the overall bound, but it's the idiom to show).

## Other Approaches
- **Sort + re-sort each round** *(brute)* — sort descending, take the last two, insert the residue in place, repeat. **O(n² log n)** (or O(n²) with an insertion into a sorted vector). Correct but exposes exactly why the heap exists.
- **`multiset<int>`** — `rbegin()` for the max, `erase` + `insert` for the update. **O(n log n)**, O(n). Equivalent complexity; worth naming as the "I need ordered *and* erasable" alternative, but strictly more code here.
- **Counting / bucket array** — weights ≤ 1000, so keep `cnt[w]` and sweep from the top. **O(n·W)** in the worst case; only attractive when `n` is huge and `W` tiny. With `n ≤ 30` it's a pessimisation — mention, don't code.
- **Heap simulation** *(canonical)* — **O(n log n)**, O(n). The expected answer.

> **The real follow-up: [LC 1049 Last Stone Weight II](https://leetcode.com/problems/last-stone-weight-ii/).** Same story, but *you* choose the smash order — and then greedy is **wrong**. Any sequence of smashes assigns each stone a `+` or `−`, so the answer is `min |sum(S) − sum(S̄)|` over subsets ⇒ **subset-sum DP** toward `total/2`, **O(n · total)**. Being able to say "1046 is greedy-safe *because the order is forced*; 1049 isn't, so it's a partition DP" is the whole point of the pair.

## Pitfalls
- **Guard the empty heap** — `[2,2]` destroys everything; `pq.top()` on an empty `priority_queue` is **UB**, not 0. Same family of trap as the unconditional pop in [[2-703-kth-largest-element-in-a-stream|703]].
- **Don't push a zero residue** — it models a destroyed stone as a live one. *Honest note:* it happens to still return the right number (a `0` is the heap's minimum, and later `y - 0 = y` re-pushes the same value), so it's **wasteful, not wrong** — but it burns extra rounds, makes the `empty()` branch dead code, and an interviewer will read it as "didn't notice both stones are destroyed."
- **`while (size() >= 2)`, not `> 0`** — a single stone can't be smashed; looping on one element pops from an empty heap.
- **Pop order gives you `x ≤ y` for free** — don't re-derive it with `min`/`max`; and don't compute `x - y` (negative weight) by mixing up which pop came first.
- **This is not Top-K** — no size cap, no eviction. Don't pattern-match it onto [[1-215-kth-largest-element-in-an-array|215]]'s "pop when `size() > k`" skeleton; here every pop is *work*, not pruning.
- **`if (l - s)` is truthiness, not comparison** — correct only because the max-heap guarantees `l ≥ s`. Prefer `l != s`.
- **Don't confuse it with 1049** — identical wording, completely different solution (greedy vs subset-sum DP).
