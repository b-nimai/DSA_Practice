# Linked List / Design (Hash Map + DLL) — Index

60-second whole-pattern recall. Read the **Trigger** column and try to recall the **Idea** before peeking.

**Core skeleton:** when a design statement demands **two things at once that no single structure gives you** — O(1) *lookup* **and** O(1) *ordering / eviction* — **compose two structures and keep a pointer from each key to its position in the other**. Hash map covers lookup; a **doubly** linked list covers order (splice in O(1), because `prev` is what makes a mid-list pointer usable). Wrap the list in **two dummy sentinels** so no operation ever needs an empty/first/last branch, and **store the key inside the node** so you can walk *backwards* from the evicted node to its map entry in O(1). Front = most recently used, `tail->prev` = the victim. Everything in this family is that sentence with the second structure swapped: DLL → recency (146), freq-buckets of DLLs → frequency (460), array → uniform random (380).

Any design asking for **O(1) lookup *and* O(1) ordering** ⇒ hash map + **doubly** linked list | **`unordered_map<int, Node*>` for lookup + DLL with head/tail sentinels for recency; front = MRU, `tail->prev` = victim.** `get`: miss ⇒ `-1` **and touch nothing**; hit ⇒ `moveToFront` + return val. `put`: **hit ⇒ update value + `moveToFront`, no eviction, no allocation** (merging this with the insert branch is *the* correctness bug — a full cache re-putting a held key would drop a live entry); miss ⇒ if `mpp.size() == cap` take `victim = tail->prev`, `mpp.erase(victim->key)`, unlink, `delete`; then new node, `insertAfterHead`, `mpp[key] = node`. **Why the node stores the KEY as well as the value:** eviction runs **backwards** — you find the *node* via `tail->prev` but must erase a *map entry*, and without `node->key` that's an O(n) map scan and the whole O(1) guarantee dies. **Why DOUBLY:** unlinking needs the **predecessor**, and the map drops you into the *middle* of the list with no context — a singly linked list forces an O(n) walk. **Why sentinels:** with dummy `head`/`tail`, `node->prev`/`node->next` are never null, so `unlink` is 2 unconditional assignments and `insertAfterHead` is 4 — no empty/first/last branches, which is exactly where hand-rolled LRUs break under time pressure. **Use-after-free trap:** copy `victim->key` (or `mpp.erase`) **before** `delete victim`. **Dangling-pointer trap:** forgetting the `mpp.erase` leaves the map pointing at freed memory — the next `get` "hits" and derefs it (silent corruption, not a clean WA). Wiring order in `insertAfterHead`: fix `head->next->prev` **before** overwriting `head->next`. `capacity ≥ 1` per constraints, so `tail->prev` is never the head sentinel; a countdown-style `cap` (free slots remaining, evict when it hits 0) is valid but relies on exactly that. Ladder: array scan **O(n)** → map + timestamp, eviction still **O(n)** → map + min-heap **O(log n)** (and `priority_queue` has no `decrease-key` ⇒ lazy deletion) → **map + DLL O(1)** (expected) → `std::list` + iterator map + `splice()`, same O(1) in ~15 lines (offer it, but many interviewers want the hand-rolled DLL). Follow-ups: **thread-safe** ⇒ shard by `hash(key) % N`, one lock each, not one global mutex · **TTL** ⇒ expiry heap, purged lazily · **approximate LRU at scale** ⇒ random sampling (Redis) or CLOCK/second-chance. ## When to reach for Hash Map + Doubly Linked List
1. **"Implement a class with O(1) `get`/`put`/`insert`/`remove`"** — the O(1) demand on *more than one* operation is the whole tell.
2. **Cache eviction by recency or frequency** (LRU / LFU / TTL) — you need to both *find* a key fast and *reorder / drop* it fast.
3. **You need a "move this element to one end" operation on a collection you also look up by key** — that is `splice`, and it needs `prev`.
4. **Contrast — reach elsewhere when:** you need the *k*th largest or a running median ⇒ heaps ([[../9. Heap/0. Index|Heap]]) · you need uniform random removal ⇒ array + index map (380) · you only ever append/pop one end ⇒ a plain deque is enough.

## Common Pitfalls Across the Pattern
- **Singly linked list.** Unlinking needs the predecessor; the map hands you a mid-list pointer. It must be doubly linked.
- **Node doesn't store its key.** Eviction can then only find the node, not its map entry — O(n) scan, O(1) gone.
- **Erasing the map entry after `delete`ing the node** — use-after-free; or forgetting the erase entirely — a dangling `Node*` that the next `get` happily dereferences.
- **Treating an update as an insert** — `put` on a held key must refresh recency without evicting or allocating.
- **Letting a lookup *miss* mutate the order** — a miss returns the sentinel value and touches nothing.
- **Skipping the sentinels** and hand-writing empty/first/last special cases — the highest-density bug region in the whole pattern.
- **Mixing the two ends mid-solution** — write "front = most recently used" as a comment above the class and never re-derive it.
- **No destructor in C++** — leaks every node. Irrelevant to the judge, visible to an interviewer.
- **Reaching for a heap because "eviction sounds like priority"** — recency is a *queue* discipline; a heap costs O(log n) and needs a `decrease-key` you don't have.
