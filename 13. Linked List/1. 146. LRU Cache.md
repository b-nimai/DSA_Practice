# 1. 146. LRU Cache (LC 146) — Medium
🔗 [Open on LeetCode](https://leetcode.com/problems/lru-cache/)
*Solved **early** on 2026-08-18 (D78) — scheduled for D100 · Wed Sep 9. Home pattern: **Hash Map + Doubly Linked List (Design)**.*

**Pattern:** Linked List / **Design — two structures composed so that every required operation is O(1)**. A hash map gives **O(1) lookup but no order**; a doubly linked list gives **O(1) splice but no lookup**. Neither alone can do the job; **together each covers the other's blind spot** — the map stores `key → Node*`, the list stores recency. This "compose two structures until every operation is O(1)" move is the whole Design pattern (**460 LFU**, **380 GetRandom**, **432 All O(1)**), and 146 is its canonical instance.
**Trigger:** "**least recently used**" / "**evict**" / "**cache**" + an explicit "**`get` and `put` must run in O(1) average time**". That O(1) clause is not decoration — it is the problem: it single-handedly kills every array, `list::remove`, timestamp-scan and priority-queue answer, and leaves exactly one shape standing. The moment a design statement demands **O(1) lookup *and* O(1) ordering/eviction**, reach for **hash map + doubly linked list**, and say "doubly" out loud — the reason is in the pitfalls.

## Problem (1-liner)
Design a fixed-capacity cache: `get(key)` returns the value or `-1`, `put(key, value)` inserts/updates, and when the cache **overflows** it evicts the **least recently used** key. **Both operations O(1).**
**Examples:** `cap = 2` · `put(1,1)`, `put(2,2)`, `get(1)→1`, `put(3,3)` **evicts 2** (1 was just touched), `get(2)→-1`, `put(4,4)` **evicts 1**, `get(1)→-1`, `get(3)→3`, `get(4)→4`.
**Constraints:** `1 ≤ capacity ≤ 3000` (**never 0** — worth noting, it removes a whole edge case), `0 ≤ key ≤ 10⁴`, `0 ≤ value ≤ 10⁵`, up to **2·10⁵** calls ⇒ anything worse than O(1) amortised times out.
**Edges:** `capacity == 1` (a `put` of a new key evicts the *only* node — the eviction target must never be the head sentinel) · `put` on an **existing** key is a **use**, so it refreshes recency **and must not evict** · `get` on a miss must **not** disturb the order · `put` of the **same key** when full must not evict anything.

## Idea (1-liner)
`unordered_map<int, Node*>` for O(1) find + a **doubly** linked list with **head/tail sentinels** for O(1) unlink & push-front; **front = most recently used, `tail->prev` = the eviction victim**.

## Approach
1. `Node { key, val, prev, next }`. Build a list with two **dummy** nodes, `head ⇄ tail`, so no real node is ever first or last.
2. **Invariant:** order from `head->next` to `tail->prev` is **most-recent → least-recent**. Every touch re-establishes it.
3. `get(key)`: miss ⇒ `-1`. Hit ⇒ `moveToFront(node)` (unlink, then insert after head), return `node->val`.
4. `put(key, val)`: **hit** ⇒ overwrite `node->val`, `moveToFront(node)`, **done — no eviction**. **Miss** ⇒ if full, take `victim = tail->prev`, `mpp.erase(victim->key)`, unlink + `delete`; then create the node, insert after head, `mpp[key] = node`.

> **Load-bearing insight #1 — the node stores the KEY as well as the value, and that is not redundant.** Eviction runs **backwards**: you find the victim *node* via `tail->prev`, but you must also erase it from the *map*, which is keyed by `key`. Without `node->key` you'd have to scan the map to find which entry points at that node — **O(n)**, and the whole design collapses. This one field is the thing interviewers check for.

> **Load-bearing insight #2 — "doubly" is forced by O(1) deletion.** To unlink a node you need its **predecessor**. A singly linked list makes you walk from the head to find it (**O(n)**), so O(1) `get` is impossible. The map hands you a `Node*` in the *middle* of the list with no context — `prev` is what makes that pointer usable. Say this sentence before you draw anything.

> **Load-bearing insight #3 — the two sentinels exist to delete the `if`s.** With dummy `head` and `tail`, `node->prev` and `node->next` are **never null** for any real node, so `unlink` is unconditionally two assignments and `insertAfterHead` is four. Without them, every operation grows "is it the first node? is it the last? is the list empty?" branches — which is where hand-rolled LRU implementations actually break in interviews.

> **Load-bearing insight #4 — `put` on an existing key is a UPDATE, not an insert.** It must refresh recency but **must not** evict and **must not** allocate. Merging the two branches is the classic correctness bug: a full cache doing `put` on a key it already holds would wrongly drop the LRU entry.

## Code (clean canonical)
```cpp
class LRUCache {
    struct Node {
        int key, val;
        Node *prev = nullptr, *next = nullptr;
        Node(int k = -1, int v = -1) : key(k), val(v) {}
    };

    int cap;
    Node *head, *tail;                       // sentinels: head <-> ... <-> tail
    unordered_map<int, Node*> mpp;

    void unlink(Node *node) {                // never null-checks: sentinels guarantee both sides
        node->prev->next = node->next;
        node->next->prev = node->prev;
    }
    void insertAfterHead(Node *node) {
        node->next = head->next;
        node->prev = head;
        head->next->prev = node;
        head->next = node;
    }
    void moveToFront(Node *node) { unlink(node); insertAfterHead(node); }

public:
    LRUCache(int capacity) : cap(capacity) {
        head = new Node();
        tail = new Node();
        head->next = tail;
        tail->prev = head;
    }

    ~LRUCache() {                            // not needed by the judge; say it in an interview
        for (Node *cur = head; cur; ) { Node *nxt = cur->next; delete cur; cur = nxt; }
    }

    int get(int key) {
        auto it = mpp.find(key);
        if (it == mpp.end()) return -1;      // a miss must NOT touch the order
        moveToFront(it->second);
        return it->second->val;
    }

    void put(int key, int value) {
        auto it = mpp.find(key);
        if (it != mpp.end()) {               // UPDATE: refresh recency, never evict
            it->second->val = value;
            moveToFront(it->second);
            return;
        }
        if ((int)mpp.size() == cap) {        // full -> evict tail->prev (the LRU)
            Node *victim = tail->prev;
            mpp.erase(victim->key);          // <- why Node stores `key`
            unlink(victim);
            delete victim;
        }
        Node *node = new Node(key, value);
        insertAfterHead(node);
        mpp[key] = node;
    }
};
```
**TC:** **O(1)** worst case for the list surgery, **O(1) average** for `get`/`put` (hash lookup is amortised O(1); adversarial collisions are the only worst case, and the problem says *average*).  **SC:** **O(capacity)** — one node + one map entry per key, never more.
*`capacity == 1` falls out free: `mpp.size() == cap` fires on the second distinct key and `tail->prev` is the single real node, never `head`.*

## My Solution (kept — `cap` as a countdown of REMAINING slots)
```cpp
class Node {
    public:
    int key, val;
    Node *prev, *next;

    Node () { key = val = -1; prev = next = nullptr; }
    Node (int key, int val) { this->key = key; this->val = val; prev = next = nullptr; }
};

class LRUCache {
    int cap;
    Node *head, *tail;
    unordered_map<int, Node*> mpp;

    void removeLink(Node *node) {
        node->prev->next = node->next;
        node->next->prev = node->prev;
    }
    void deleteNode(Node *node) {
        node->prev->next = node->next;
        node->next->prev = node->prev;
        delete(node);
    }
    void insertAfterHead(Node *node) {
        node->next = head->next;
        node->prev = head;
        head->next = node;
        node->next->prev = node;
    }
public:
    LRUCache(int capacity) {
        cap = capacity;
        head = new Node(), tail = new Node();
        head->next = tail;
        tail->prev = head;
    }

    int get(int key) {
        auto it = mpp.find(key);
        if (it == mpp.end()) return -1;

        Node *node = it->second;
        removeLink(node);
        insertAfterHead(node);
        return node->val;
    }

    void put(int key, int value) {
        auto it = mpp.find(key);
        if (it != mpp.end()) {
            Node *node = it->second;
            removeLink(node);
            node->val = value;
            insertAfterHead(node);
        } else {
            Node *node = new Node(key, value);
            if (cap == 0) {
                Node *dNode = tail->prev;
                int delKey = dNode->key;
                deleteNode(dNode);
                cap++;
                mpp.erase(delKey);
            }
            insertAfterHead(node);
            mpp[key] = node;
            cap--;
        }
    }
};
```
✅ **Correct — O(1) get/put, O(capacity) space.** Traced against the full example: `[null,null,null,1,null,-1,null,-1,3,4]`. The design decisions that matter are all present and right: **sentinels**, **`key` stored on the node** (grabbed as `delKey` *before* the delete — the right instinct, since reading `dNode->key` after `delete` is use-after-free), **update-branch separated from insert-branch**, and a **miss in `get` leaving the order untouched**.
**The one thing to be deliberate about:** here `cap` is not the capacity, it is the **number of free slots remaining**, counted down. That's a valid encoding, and the eviction test `cap == 0` is safe **only because the constraints promise `capacity ≥ 1`** — so whenever `cap` hits 0 there is at least one real node and `tail->prev` can never be the `head` sentinel. Worth stating out loud; with `capacity == 0` allowed it would deref the sentinel.
**Refinements (all stylistic, none are bugs):**
- **`deleteNode` duplicates `removeLink` verbatim** — compose instead: `void deleteNode(Node *n) { removeLink(n); delete n; }`. Two copies of pointer surgery is exactly where a later edit desynchronises.
- **`get` and put's hit-branch share the same two lines** — extract `moveToFront(node) { removeLink(node); insertAfterHead(node); }`. `get` becomes 3 lines and the intent ("a touch = move to front") becomes visible instead of inferred.
- **Prefer `mpp.size() == cap` with `cap` immutable** over the countdown. Same O(1), but a reader (and an interviewer) checks it in one glance instead of reconstructing that `cap` means "free slots".
- **Allocate the new node *after* the eviction**, not before — currently `new Node(key, value)` runs first and the eviction block sits between it and its insertion. Harmless, but it keeps the allocation next to its use.
- **No destructor** ⇒ every node leaks. The judge doesn't care; an interviewer does. Adding `~LRUCache` (or using `unique_ptr`/an intrusive pool) is a free point.
- `delete(node)` → `delete node;` — `delete` is an operator, not a function; the parens read as a typo.

## Other Approaches
- **Brute force — array/vector of pairs, scan on every op.** `get` scans O(n); `put` erases from the middle O(n) and evicts by finding the oldest O(n). **O(n) / O(n)**. State it in one sentence purely to name what the O(1) requirement forbids; 2·10⁵ ops × 3000 capacity is ~10⁸ pointer-chasing steps ⇒ TLE.
- **Hash map + timestamp counter.** `map[key] = {value, lastUsed}`, evict by scanning for the minimum timestamp. `get`/`put` are O(1) **except** eviction, which is **O(n)**. The tempting half-answer; kill it by noting eviction is the operation that actually needs to be fast.
- **Hash map + min-heap on timestamp.** Eviction drops to **O(log n)**, but "refresh recency" needs `decrease-key`, which `priority_queue` lacks ⇒ lazy deletion and a heap that grows to O(#ops). **O(log n)** — better, still not O(1), and strictly more code than the right answer.
- **`std::list` + `unordered_map<int, list<...>::iterator>` with `splice`** *(the 15-line version)* — **O(1) / O(capacity)**. `splice(lst.begin(), lst, it)` moves a node to the front in O(1) **without invalidating the iterator**, which is the whole trick; evict with `lst.back()` (again: the list stores the **key** as well, so you can `mpp.erase(lst.back().first)`). Worth knowing cold, but **many interviewers explicitly want the hand-rolled DLL** — offer it as "I can do this in 15 lines with `std::list::splice`, or hand-roll the doubly linked list; which would you prefer?"
- **`LinkedHashMap` (Java) / `OrderedDict.move_to_end` (Python)** — one-liners in those languages, and usually **disallowed**; name them so the interviewer knows you know, then write the real thing.
- **Follow-ups to pre-empt:** *"make it thread-safe"* → one mutex around both ops is correct but serialises everything; the real answer is **sharding by `hash(key) % N`** into N independent LRUs, each with its own lock (what production caches do). *"evict by frequency instead"* → **LC 460 LFU**, a map from frequency to its own DLL bucket plus a `minFreq` pointer. *"add TTL / expiry"* → LRU list + a min-heap or timing wheel on expiry, lazily purged on access. *"approximate LRU over millions of keys"* → sampling (Redis picks k random keys, evicts the oldest) or **CLOCK / second-chance**, trading exactness for one bit per entry.

> **The Design-pattern sentence to say out loud:** *"No single structure gives me both O(1) lookup and O(1) ordering, so I'll compose two — a hash map for lookup and a doubly linked list for recency — and keep a pointer from each key to its node so I can move between them in O(1)."* That framing is what generalises to **460 LFU** (map + freq→DLL buckets + `minFreq`), **380 Insert Delete GetRandom** (array for random + map for index, swap-with-last to delete), and **432 All O(1)** (DLL of frequency buckets).

## Pitfalls
- **Singly linked list** — you can't unlink in O(1) without the predecessor, and the map drops you into the *middle* of the list. It **must** be doubly linked; this is the first thing to state.
- **Not storing `key` inside the node** — *the* signature design bug. Eviction finds a *node* and must erase a *map entry*; without `node->key` that's an O(n) map scan and the O(1) guarantee is gone.
- **Reading `victim->key` after `delete victim`** — use-after-free. Either `erase` from the map first, or copy the key into a local before deleting (the target file does the latter, correctly).
- **Forgetting to erase from the map on eviction** — the list shrinks but the map keeps a **dangling `Node*`**; the next `get` on that key returns a hit and dereferences freed memory. Silent corruption, not a clean WA.
- **Treating `put` on an existing key as an insert** — it must **update + refresh**, never allocate and never evict. A full cache re-`put`ting a held key would otherwise drop a live entry.
- **Letting a `get` miss reorder anything** — return `-1` and touch nothing.
- **Skipping the sentinels** — every operation then needs empty-list / first-node / last-node branches, and one of them will be wrong under time pressure. Two dummy nodes delete all of them.
- **Evicting `head->next` instead of `tail->prev`** — pick the orientation (front = most recent) and write it as a comment above the class; mixing the two ends mid-solution is the most common trace failure.
- **`insertAfterHead` wiring in the wrong order** — you must fix `head->next->prev` **before** overwriting `head->next`, or stash the old `head->next` first. Setting `head->next = node` too early loses the rest of the list.
- **Testing fullness against a counter you also mutate elsewhere** — either keep `cap` immutable and compare `mpp.size()`, or count down consistently; a hybrid drifts.
- **Assuming `capacity` can be 0** — constraints say `≥ 1`. Note it once; if the interviewer relaxes it, guard `tail->prev != head`.
- **No destructor / leaked nodes** — irrelevant to the judge, a visible miss in a C++ interview.
- **Reaching for `priority_queue` because "eviction sounds like a heap"** — recency is a *queue* discipline, not a priority; a heap buys O(log n) and costs `decrease-key` you don't have.
